In two sentences: Playwright drives real browser engines (Chromium, WebKit, Firefox) against a production build of the app, and one config file decides which build, which 12 projects (an API-only one plus 11 device profiles), which spec files each runs, how failures are recorded, and what is cleaned up afterwards. The shared helpers read credentials safely, create and delete throwaway users without sending emails, and wait for the app the way a person would; the HTTP spec checks routing, caching, SEO files and that no secret is ever served, and its three bugs teach three ways a test can quietly test the wrong thing.

2

The problem this solves

You could test in the browser by hand: open the site on your phone, tap around. You'd test one device, one engine, once. After the next change you'd have to do it again, and you wouldn't, so regressions ship.

The idea: describe every check once in code, and let a runner execute it on every engine and screen size that matters, against the same production build users get, on demand.

3

Concepts

3.1 Playwright Test in one page

  1. Definition. Playwright is a browser automation library; Playwright Test is its test runner. It launches Chromium, WebKit (Safari's engine) and Firefox builds it downloads itself (npx playwright install).
  2. Why here. One API for three engines, built-in device profiles (viewport, user agent, touch, pixel ratio), automatic waiting, traces of failures, and parallel workers.
  3. How it works. Each test gets fixtures: page (a fresh tab in a fresh browser context: no cookies, no storage), request (an HTTP client), and info like browserName and isMobile. A project is a named configuration (a device, a set of spec files); every test runs once per project that matches it.
  4. Minimal example.
    TypeScript5 lines
    import { test, expect } from "@playwright/test";test("title", async ({ page }) => {  await page.goto("https://example.com");  await expect(page).toHaveTitle(/Example/);});
  5. In the project. Five spec files, 12 projects, 253 test runs.
  6. Without it. Manual checks on whichever device is in your pocket.
  7. Try it. npx playwright test --list | tail -1 prints Total: 253 tests in 5 files.

3.2 Locators and auto-waiting (preview; L4.04 goes deep)

page.locator(".fc").last() doesn't find anything immediately: it's a recipe for finding elements, re-evaluated each time it's used. Actions (click) and web-first assertions (expect(locator).toContainText(…)) retry until the condition holds or the timeout expires (8 s here). That's what makes tests robust to animations and network delays, as long as you assert on a state, not on a fixed sleep.

3.3 The request fixture

For checks that don't need a rendered page (status codes, headers, file contents), request.get(url) sends a plain HTTP request from Node. It's fast and doesn't execute JavaScript. That's exactly right for "does /robots.txt exist" and exactly wrong for "does the page render".

Lines 1–7, the target.

  • BASE_URL defaults to the local preview on port 4174. Setting BASE_URL=https://psychology-of-learning-nptel.vercel.app (the test:prod script does) runs the same suite against production.
  • local is true when no BASE_URL is set; it decides whether to start a server.
  • ui is a shared fragment: device projects run ui.spec.ts and a11y.spec.ts unless they say otherwise.

Lines 9–24, the runner.

  • testDir: where spec files live.
  • timeout: 90_000 per test (the signed-in journey sets its own, longer one). expect.timeout: 8_000: how long web-first assertions retry.
  • fullyParallel: true + workers: 4: tests (not only files) are spread over four worker processes. Four is a measured compromise on this laptop: more workers made WebKit slow enough to time out the 100-question journey.
  • retries: 1: a failed test is re-run once; if it then passes it's reported as flaky, not passed. Use --retries=0 when debugging so failures aren't hidden (every diagnosis in this series was run that way).
  • Reporters: list in the terminal and an html report in test-results/report (git-ignored), not auto-opened.
  • globalTeardown runs once after everything, even if tests crashed (§4.3).
  • use: defaults for every project. trace: "retain-on-failure" records a full timeline (DOM snapshots, network, console) and keeps it only for failures; screenshot: "only-on-failure".

Lines 25–27, the server.

  • webServer builds the app (tsc -p . && vite build) and serves dist/ with vite preview on a fixed port. --strictPort fails instead of silently picking another port; --host 127.0.0.1 avoids IPv6/localhost ambiguity on Windows.
  • url: Playwright polls it until it answers before starting tests. reuseExistingServer: true: if something already serves 4174, use it (fast reruns, but see §7.3's lesson about stale servers). timeout: 180_000: the build can take a while on a cold machine.
  • Testing the production build, not vite dev, matters: the dev server has no hashed files, no minification, no dist/ file list, and it reloads modules (which caused L4.07's flake).

  • Secrets and sources are never served: request files that must not exist on the site (/Supabase.txt, .env files, source files, the SQL, package.json, .vercel/project.json). Because of the SPA rewrite they usually return index.html with 200; the test checks the body for leaks rather than the status. Then it fetches every JavaScript chunk referenced by the HTML and scans it too: the bundle may contain the publishable key (that's normal) but never a secret.
  • The short link psychologyoflearning.vercel.app must answer with a permanent redirect (301 or 308) to the same path on the main domain, preserving the query string (maxRedirects: 0 so the test sees the redirect itself).
  • HSTS: production must send Strict-Transport-Security, telling browsers to use HTTPS only.

Bug journal: three ways a test tests the wrong thing

Incident ticket · #01

Git Bash rewrote /study into C:/Program Files/Git/study

Fixed
  1. Symptom
    A screenshot script run from Git Bash on Windows, called with the routes to capture, crashed on the first navigation:
    Text1 line
    ProtocolError: Protocol error (Page.navigate): Cannot navigate to invalid URL
  2. Diagnosis
    Printing the argument the script received showed the problem. Reproduced for this lesson:
    Terminal4 lines
    $ node -e 'console.log(JSON.stringify(process.argv.slice(1)))' /study["C:/Program Files/Git/study"]$ node -e 'console.log(JSON.stringify(process.argv.slice(1)))' "/,/study,/test"["C:/Program Files/Git/,/study,/test"]
    The script built http://127.0.0.1:4173 + C:/Program Files/Git/study, an invalid URL.
  3. Root cause
    Git Bash (MSYS2) converts arguments that look like POSIX paths into Windows paths before starting a native Windows program, so that /usr/bin/x works for Windows tools. A URL path like /study looks like a POSIX path.
  4. Fix
    Turn conversion off for that command:
    Diff2 lines
    node devices.mjs ../shots "/,/study,/test,/ranks,/me"MSYS_NO_PATHCONV=1 node devices.mjs ../shots "/,/study,/test,/ranks,/me"
    (Playwright's own tests weren't affected: their paths are in code, not command-line arguments.)
  5. Lesson
    When a script misbehaves only from one shell, print the arguments it actually received. Keep routes and URLs inside code or config files rather than passing them through a shell.
Incident ticket · #02

The secret scanner flagged the Supabase library's own source

Fixed
  1. Symptom
    "secrets and source files are never served" failed on the bundle:
    Text4 lines
    Error: /assets/supabase-C3nyvjhK.jsexpect(received).not.toMatch(expected)Expected pattern: not /sb_secret_|service_role/Received string:  "const Nr=Symbol.for(\"@supabase/supabase-js.traceContextExtractor\");…
  2. Diagnosis
    A real leak? The secret key wasn't in any environment variable that starts with VITE_, so Vite couldn't have inlined it. Searching the chunk showed the match: supabase-js itself contains the prefix sb_secret_ in code that warns developers who put a secret key in a browser (something like startsWith("sb_secret_")). The pattern matched the library's warning, not a key.
  3. Root cause
    A pattern that matches a prefix matches any code that talks about the prefix. Good scanners match the shape of the value or the value itself.
  4. Fix
    Diff7 lines
    expect(js, src).not.toMatch(/sb_secret_|service_role/);// real secret values from the local, git-ignored credentials file (if present)const SECRETS = existsSync("Supabase.txt") ? [...readFileSync("Supabase.txt", "utf8")  .matchAll(/^(?:Secret keys|Service role)\s*:\s*(\S+)/gim)].map((m) => m[1]) : [];const leaks = (body: string) => SECRETS.some((s) => body.includes(s))  || /sb_secret_[A-Za-z0-9_-]{16,}|VERCEL_OIDC_TOKEN|create table public\./.test(body);expect(leaks(await (await request.get(base + src)).text()), `${src} contains a secret key`).toBe(false);
    Then the scanner itself was tested: it found 2 secret values in Supabase.txt, detected a planted one ("x" + secret + "y" → true), and ignored the library text (startsWith("sb_secret_") → false).
  5. Lesson
    Scan for the secret's value when you have it, and for its full shape (prefix plus length) when you don't. Test the scanner with a planted positive and a known false positive.
Incident ticket · #03

The HTTP tests silently checked production

Fixed
  1. Symptom
    In the final full run, one test failed after the switch to WebP images:
    Text4 lines
    ✘ [api] › tests\e2e\http.spec.ts:22:1 › search & sharing files are served correctly  Error: /brand/mascot.webp  Expected pattern: /image\/(png|webp)/  Received string:  "text/html; charset=utf-8"
  2. Diagnosis
    • The file existed in dist/brand/.
    • Hypothesis: a stale preview server that started before the WebP files were built and didn't know about them. Checked: nothing was listening on 4174 (4174 not running). Ruled out.
    • Rerunning only the HTTP spec failed the same way, against a fresh state. The status was 200 but the body was HTML: the SPA rewrite answering a missing file with index.html. Missing where? Reading the spec: const base = process.env.BASE_URL ?? PROD;. Unlike every other spec, it defaulted to production, where the WebP files hadn't been deployed yet.
  3. Root cause
    One file had its own default target. Every earlier run had "passed" against production, so the HTTP spec had been testing the last deploy, not the code under test, without anyone noticing.
  4. Fix
    Diff4 lines
    const base = process.env.BASE_URL ?? PROD;// same target as the rest of the suite: local production build unless BASE_URL is setconst base = process.env.BASE_URL ?? "http://127.0.0.1:4174";const isProd = base.startsWith("https://");
    The production-only checks (redirect, HSTS, cache headers) became test.skip(!isProd, "production only"). Result: 5 passed, 2 skipped locally; all 7 pass with npm run test:prod.
  5. Lesson
    A suite needs one notion of "the system under test", set in one place. And because SPA rewrites turn every missing file into a 200, assert content types or content, never status alone.

Check yourself

Answer each one before you look. Multiple-choice questions mark your pick and let you try again; for open questions, answer aloud, then reveal and grade yourself honestly.

Q1
A test passes on retry. What does the report say, and what should you do?
Did you have it?
It's marked flaky. Treat it as a bug: open the trace of the failed attempt and find the race (usually an assertion that read state too early).
Q2
Why does /brand/mascot.webp return status 200 even when the file doesn't exist?
Did you have it?
The SPA rewrite /(.*) → /index.html serves the app shell for any unknown path, with 200. Only the content type (text/html) or the body reveals the file is missing.
Q3
Why does deleteMyTestUsers delete only the users in created, and not every e2e-bot- user?
Did you have it?
Four workers run concurrently; another file may be mid-test with its users. Deleting by prefix would sign them out (and cascade-delete their data) under them. Only global teardown, after all workers, deletes by prefix.
Q4
The pixel-7 project runs auth.spec.ts, but galaxy-s9-320 doesn't. Why?
Did you have it?
The signed-in journey creates a real user and takes minutes; one project per engine (Chromium on pixel-7, WebKit on iphone-13, Gecko on desktop-firefox) covers engine differences without multiplying the cost.
Q5
Predict: you run npx playwright test while npm run preview (port 4173) is open in another terminal. Which server do the tests use?
Did you have it?
Neither of yours: the config's webServer builds and starts its own on 4174 (unless something already listens on 4174, which it then reuses).
Q6
Why does the leak pattern require sb_secret_[A-Za-z0-9_-]{16,} rather than sb_secret_?
Did you have it?
The library's own code mentions the bare prefix; a real key has many characters after it. The shape avoids the false positive while still catching any real secret-format key.

Flashcards

See all 11 cards as a listfor a quick scan
  1. What is a Playwright project?
    A named configuration (device, spec files); every matching test runs once per project.
  2. Why 253 tests?
    20+16×11+6×9+1×3=253 (api; ui on 11 devices; a11y on 9; auth on 3).
  3. What does webServer do?
    Builds and serves the production build on 4174, waits for it, reuses one already running.
  4. What does retries: 1 report when a retry passes?
    "Flaky".
  5. How are test users created without emails?
    Admin createUser({ email_confirm: true }); the code comes from generateLink(...).properties.email_otp.
  6. Why @example.com?
    A reserved domain that can never receive mail.
  7. Why per-file cleanup plus global teardown?
    Parallel-safe cleanup of your own users, plus a safety net for crashes.
  8. Why check content type, not just status, for files?
    The SPA rewrite returns index.html with 200 for any missing file.
  9. How should a secret scanner match?
    By the secret's value, or its full shape (prefix + length), never the bare prefix.
  10. What does Git Bash do to /study as an argument?
    Converts it to C:/Program Files/Git/study; disable with MSYS_NO_PATHCONV=1.
  11. Why must every spec share one base URL?
    Otherwise a file can silently test production (or another build) instead of the code under test.

Glossary

Browser context
an isolated browser profile (cookies, storage) inside one browser instance.
Device profile
viewport, user agent, touch and pixel ratio of a device.
Fixture
an object Playwright provides to a test (page, request).
Flaky test
one that sometimes passes and sometimes fails without code changes.
Global teardown
a function run once after all tests.
HSTS
the Strict-Transport-Security header forcing HTTPS.
Import attribute
with { type: "json" }, telling the runtime a module's type.
MSYS path conversion
Git Bash's rewriting of POSIX-looking arguments for Windows programs.
Project (Playwright)
a named run configuration.
SPA rewrite
serving index.html for every path so the client router handles it.
Trace
Playwright's recording of a test (DOM snapshots, network, console).
Worker
a process running tests in parallel.
