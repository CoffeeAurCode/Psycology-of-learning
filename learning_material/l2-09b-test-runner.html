The ranked test II: the runner

Recipe card75 min

Lines 192–477 of src/pages/Test.tsx: the Run component

In two sentences: The runner is a focused, full-screen exam room. One question at a time, a ticking clock, a progress bar, auto-advance after you answer, flags, a jump grid, swipe between questions, and a confirmation before submitting. Every change is persisted, so a reload drops you back exactly where you were.

By the end, without notes, you can

  1. Keep the attempt in state and storage with one effect, and redirect when there's no attempt.
  2. Write choose with toggle-off and a 320 ms auto-advance that can't fire on the wrong question.
  3. Write go with clamping and direction, used by buttons, keys, swipes and the grid.
  4. Build the three sheets (grid, submit, leave) and explain what each protects against.
  5. Write submit: map null → -1, call submit_test, store the result, clear the attempt, and navigate with replace.

2

The problem this solves

Phone exams fail on small things: a mis-tap that can't be undone, losing your place, an accidental swipe away, not knowing how many you skipped. The runner removes each of those risks.

3

Concepts

3.1 State as the single writer, storage as a mirror

All changes go through setA(...), and one effect writes a to storage whenever it changes. Nothing writes storage directly during the run, so state and storage can't disagree.

3.2 Delayed actions must check they still apply

Auto-advance runs 320 ms after you choose. In those 320 ms you might tap Prev, or open the grid and jump. So the timeout doesn't blindly do pos + 1. It advances only if you're still on the question you answered (cur.pos === p). That is the general rule for timers in UI: capture the context, and verify it on fire.

3.3 beforeunload

Registering a beforeunload listener that calls preventDefault() asks the browser to show its "Leave site? Changes may not be saved" dialog when the tab is closed or reloaded. Browsers show their own wording; you can't customise it. Tests must accept it (page.on("dialog", d => d.accept())), or navigation hangs (L4.05).

  • L1if (!a) return null after all hooks; the redirect effect handles navigation.
  • L2BY_ID.get(...)!: ids come from our own server's draw of our own questions, so a lookup miss would mean data drift. The ! is reasonable here, and the data tests guard drift (L2.01).
  • Parameter names match the SQL (p_attempt, p_answers). supabase-js sends them as named JSON arguments.
  • null → -1: the SQL encoding for "skipped", which never matches a real answer (L2.03).
  • On error: stay in the runner and show the message in the sheet. "This test expired…", "already submitted" and network errors are all recoverable or explainable. The UI test proves an anonymous submit shows .sheet .banner and stays on /test/run (L4.05).
  • On success:
    • save the server result plus our question order and answers (for review);
    • delete the attempt (so "Resume" disappears);
    • navigate with replace, so "Back" from results doesn't reopen the finished runner (which would redirect anyway).
  • L19state: { fresh: true } is never read by ResultView: dead data left from an idea (play the confetti only on fresh results). Harmless; worth knowing it's unused.

Flashcards

See all 7 cards as a listfor a quick scan
  1. How is the attempt kept safe across reloads?
    All changes go through setA; one effect mirrors a to localStorage; mount reads it back.
  2. Why does auto-advance check cur.pos === p?
    To avoid advancing if the user already moved during the 320 ms.
  3. How do you un-answer a question?
    Tap the selected option again.
  4. What does the leave sheet warn about?
    Answers are saved but the (server) clock keeps running.
  5. What happens on submit success?
    Save the result (+ order + answers), delete the attempt, and navigate to results with replace.
  6. Why no right/wrong colours during the test?
    Exam realism, and the client doesn't have the key.
  7. Swipe threshold between questions?
    ±70 px offset (the card barely moves: elastic 0.25).
