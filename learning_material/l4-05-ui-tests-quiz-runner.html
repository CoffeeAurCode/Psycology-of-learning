L4.05

Test it V: UI tests for quiz, list, theme, test runner and results

Recipe card70 min
You need
L4.04 (locators, waiting, deckFoot), L4.03 (currentQuestion, questionFromScreen), L2.08b (quiz and list), L2.09a–c (runner, results)
You'll produce
Lines 165–304 of tests/e2e/ui.spec.ts: the remaining 7 UI tests, including a 100-question runner test that needs no server, and a results test driven entirely by injected state

In two sentences: The second half of the UI suite tests screens whose content is random (the quiz order), remote (the leaderboard), or long and stateful (a 100-question test with a clock, flags, a grid and resume), so it leans on two techniques: identifying what's on screen from the data instead of assuming an order, and injecting state into localStorage so a screen can be tested without the steps or the server that normally produce it. Its bug story is a two-layer one: a real app bug (the quiz shuffling twice) hid behind a test bug (reading the card that was sliding out), and both had to be found.

Session 2 update

The "real OTP sign-in" in the diagram is now a real session injected for a throwaway user (L4.09).

By the end, without notes, you can

  1. Test a randomised quiz by reading the question from the screen and choosing right or wrong answers deliberately.
  2. Test list search, the theme toggle (including persistence across reloads) and the signed-out gate.
  3. Write the runner test from an injected attempt: answer, auto-advance, previous, flag, grid, jump, resume, submit sheet, error path, exit.
  4. Write the results test from an injected result, and compute every expected value from the injected data.
  5. Diagnose a test that reads stale content during a transition, and separate it from an app bug with the same symptom.

The problem this solves

Three obstacles make these screens hard to test end to end:

  • Randomness. The quiz shuffles; a test can't hard-code "question 1 is X".
  • Remote state. The real runner needs a signed-in user and start_test on the server, and the results screen needs a real submission. Doing that 11 times per run is slow and needs secrets.
  • Length. A full test is 100 questions; a UI test that clicks through all of them on 11 devices would take most of an hour.

The idea: test the rendering and behaviour of each screen from state you control (injected into localStorage), and leave the real server round trip to one signed-in journey (L4.06), run on three projects.

3

Concepts

3.1 Identify, don't assume

currentQuestion reads the question text and options from the card and finds the matching item in questions.json (questionFromScreen, L4.03). Knowing the real question, the test can choose a right answer (q.answer) or a guaranteed wrong one ((q.answer + 1) % q.options.length, the next option round-robin). The expected score is then computed by the test, not read from the app.

3.2 State injection

A test can write the same localStorage keys the app writes, then load the page. The app can't tell the difference, so the screen renders exactly as it would after the real steps. Two rules make it honest:

  • Use the app's real schema (field names and types), or the test proves nothing about real data.
  • Cover the real producer elsewhere: the signed-in journey (L4.06) creates both keys for real, so injection isn't the only evidence.

3.3 Waiting through a content swap

When content is replaced (a new question slides in), "wait until visible" isn't enough: the old content is visible too. Wait until the old content is gone, or the new content is present:

TypeScript1 line
await expect(page.locator(".q-card .q-text")).not.toHaveText(oldText);

not.toHaveText retries like any web-first assertion: it passes as soon as the element's text is different (or the old element is gone and the new one has different text).

test("quiz mode scores right and wrong answers and finishes the round", async ({ page }) => {  await goto(page, "/study?week=5");  await page.locator(".seg button", { hasText: "Quiz" }).click();  let expected = 0;  for (let i = 0; i < 10; i++) {    const q = await currentQuestion(page);    const right = i % 2 === 0;    const pick = right ? q.answer : (q.answer + 1) % q.options.length;    await page.locator(".q-card .opt").nth(pick).click();    await expect(page.locator(".q-card .opt.correct")).toHaveCount(1);    await expect(page.locator(".q-card .opt.wrong")).toHaveCount(right ? 0 : 1);    if (right) expected++;    await expect(page.locator(".deck-foot")).toContainText(`Score ${expected}`);    await page.getByRole("button", { name: /Next question|See score/ }).click();    // wait until the next question has slid in (the old card animates out first)    if (i < 9) await expect(page.locator(".q-card .q-text")).not.toHaveText(q.q);  }  await expect(page.getByRole("heading", { name: `${expected}/10` })).toBeVisible();  await page.getByRole("button", { name: /Retry the 5 you missed/ }).click();  await expect(page.locator(".deck-foot")).toContainText("1 / 5");});
  • Week 5, Quiz tab: ten questions in random order.
  • Alternate right and wrong: even i right, odd i wrong, so the expected final score is 5/10 whatever the order.
  • Click the chosen option by index (.nth(pick)): the options are rendered in the data's order, so index = answer index.
  • Feedback assertions: always exactly one .opt.correct (the right answer is revealed either way), and one .opt.wrong only when the pick was wrong.
  • The running score in the deck foot ("Score 3") after every answer.
  • Next: the button says "Next question" until the last, then "See score"; one role locator with a regex covers both.
  • The wait that fixed the test (§7): before reading the next question, wait until the card's text is no longer the old question.
  • The end: a heading 5/10 (by role, so it's announced as a heading), and "Retry the 5 you missed" starts a 5-card round.

test("theme toggle switches light/dark and is remembered", async ({ page }) => {  await goto(page, "/");  const bg = () => page.evaluate(() => getComputedStyle(document.body).backgroundColor);  const before = await bg();  const toggle = isRail(page) ? page.locator(".rail-theme") : page.locator(".topbar .icon-btn");  await toggle.click();  await expect.poll(bg).not.toBe(before);  const theme = await page.evaluate(() => document.documentElement.dataset.theme);  expect(["light", "dark"]).toContain(theme);  await page.reload();  expect(await page.evaluate(() => document.documentElement.dataset.theme)).toBe(theme);  expect(await bg()).not.toBe(before);  // explicit choice from the account page  await goto(page, "/me");  await page.locator(".seg button", { hasText: "Dark" }).click();  await expect.poll(() => page.evaluate(() => document.documentElement.dataset.theme)).toBe("dark");});

Bug journal

Incident ticket · #01

The quiz test read the card that was sliding out (with a real bug underneath)

Fixed
  1. Symptom
    Text4 lines
    ✘ [pixel-7] › ui.spec.ts › quiz mode scores right and wrong answers and finishes the round  Error: expect(locator).toHaveCount(expected) failed  Expected: 0  Received: 1
    The test chose what it believed was the right answer, and the app marked it wrong.
  2. Diagnosis
    • Layer 1, a real app bug. Reading the quiz code showed it shuffled twice when opened: once in useState(() => shuffleArr(pool)), and again in an effect that called restart() on mount. The first question could change right after it appeared, so a fast tap (by a test or a quick human) could land on a question that had just been replaced. Fixed in the app (L2.08b): reshuffle only when the week (pool) actually changes, tracked with a ref.
    • Still failing, so the first theory was incomplete. A throwaway debug spec logged, per iteration, the .q-text elements before and after reading, and 600 ms later. Iteration 1 read the previous question: the old card was still in the DOM, animating out, and currentQuestion read it. (Side lesson: the first debug file, zz-debug.spec.ts, ran zero tests ("No tests found") because no project's testMatch matched its name; renamed to debug-ui.spec.ts, it ran.)
  3. Root cause
    Two different problems with one symptom: an app race (double shuffle on mount), and a test race (reading during the slide transition, when two cards exist).
  4. Fix
    Diff13 lines
    // src/pages/Study.tsx (app)  // eslint-disable-next-line react-hooks/exhaustive-deps  useEffect(() => {    restart();  }, [pool]);  // reshuffle only when the week changes (not on mount, which would swap the first question)  const lastPool = useRef(pool);  useEffect(() => {    if (lastPool.current === pool) return;    lastPool.current = pool;    restart();    // eslint-disable-next-line react-hooks/exhaustive-deps  }, [pool]);
    Diff4 lines
    // tests/e2e/ui.spec.ts (test)    await page.getByRole("button", { name: /Next question|See score/ }).click();    // wait until the next question has slid in (the old card animates out first)    if (i < 9) await expect(page.locator(".q-card .q-text")).not.toHaveText(q.q);
    and later, in support.ts, currentQuestion itself waits for a single card (toHaveCount(1)), so every caller is protected.
  5. Lesson
    When a fix doesn't make a test pass, don't stack more fixes on the same theory; log what the test actually reads. And when content is replaced in place, wait for the old content to disappear, not merely for content to be visible.

Check yourself

Answer each one before you look. Multiple-choice questions mark your pick and let you try again; for open questions, answer aloud, then reveal and grade yourself honestly.

Q1
Why does the quiz test pick (q.answer + 1) % q.options.length for a wrong answer instead of a random other option?
Did you have it?
It's deterministic and always different from the right answer, for both 4-option and 2-option (true/false) questions.
Q2
The injected attempt uses the zero UUID as attempt_id. Which assertion depends on that, and why is it safe?
Did you have it?
The error path: submitting must fail and show the banner. No real attempt has that id, and there's no session anyway, so the server rejects it without touching real data.
Q3
Compute what the results screen should show for duration_ms: 3_725_000.
Did you have it?
3,725 s = 1 h 2 min 5 s → 1:02:05 (fmtDuration adds hours when ≥ 1 h, L2.04).
Q4
Why is the ring assertion given timeout: 5000 instead of the default 8 s, and what does it prove besides the score?
Did you have it?
A tighter bound that still covers the ~1.1 s count-up (and the card's entrance); it proves the count-up actually finishes at the stored score. (The default would also pass; the explicit value documents the expectation.)
Q5
The leaderboard test uses .or(). What would go wrong with expect(page.getByText("No scores yet")).toBeVisible() alone?
Did you have it?
It would fail as soon as anyone has a score on the live board: the test would depend on production data.
Q6
A debug spec named zz-debug.spec.ts reports "No tests found". Why?
Did you have it?
Every project's testMatch only matches ui|a11y|auth|api-security|http spec names; the file isn't matched by any project. Name it so a project matches (e.g. debug-ui.spec.ts).

  1. How does the quiz test know the right answer when the order is random?
