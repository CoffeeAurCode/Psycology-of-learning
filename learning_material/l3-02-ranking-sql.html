L3.02

Under the hood: ranking maths and SQL internals

Recipe card65 min
You need
L2.03 (start_test, submit_test, get_leaderboard, get_my_stats), L3.01 (definer functions)
You'll produce
Frame-by-frame traces of distinct on and rank() on real rows, the probability maths of 100-from-130 sampling and of guessing, the cost of every function measured on 10,000 attempts, and the concurrency story of for update

In two sentences: The leaderboard is two SQL ideas stacked: distinct on keeps each player's best attempt, and the window function rank() numbers those bests so that equal results share a place. This lesson runs both on real rows, derives what random 100-of-130 tests mean for a student, measures what each function costs as the class grows, and walks through the edges: ties, concurrent submits, missing questions and integer limits.

By the end, without notes, you can

  1. Trace distinct on + rank() on any set of attempts and predict the board, including ties.
  2. Explain the difference between rank, dense_rank and row_number, and why the board uses rank.
  3. Compute, for random 100-question tests drawn from 130: the chance a question appears, the expected overlap of two tests, and how many tests it takes to see every question.
  4. Read the query plan of get_leaderboard, state its complexity, and fix get_my_stats's four-fold cost.
  5. Explain what select … for update does when two submissions of the same attempt race.

2

The problem this solves

A leaderboard looks like order by score desc limit 10. The naive query has three problems:

  • A student with 12 attempts takes 12 rows. The board should show each person once, at their best.
  • "Best" needs a tie-break. Two attempts with score 95: the faster one is better. Same score and same time: the earlier one.
  • Places must be honest. Two people with identical results are both "1st"; the next person is "3rd", not "2nd".
3

Concepts

3.1 distinct on: first row per group, in your order

  1. Definition. select distinct on (k) … order by k, x, y sorts the rows by k, x, y, then keeps only the first row of each run of equal k.
  2. Why here. "Each player's best attempt" is "the first row per user_id when sorted best-first".
  3. How it works. Postgres sorts (or reads an index in order), then a Unique step compares each row's k with the previous row's and skips repeats. The rule that the order by must start with k is what makes "equal k values are adjacent" true.
  4. Standalone example.
    SQL5 lines
    select distinct on (team) team, player, goalsfrom (values ('A','Asha',3), ('A','Bo',5), ('B','Cy',2)) t(team, player, goals)order by team, goals desc;-- A | Bo | 5-- B | Cy | 2
  5. What breaks without the tie-breakers. With only order by user_id, score desc, two attempts with the same score are in unspecified order, so the board could show the slower attempt's time, and could even change between calls.
  6. Portable alternative. row_number() over (partition by user_id order by score desc, duration_ms, submitted_at) = 1 does the same thing in any SQL database. distinct on is a Postgres extension; it's shorter and usually as fast.

3.2 The rank family

All three are window functions: they compute a value per row from an ordered window of rows, without collapsing them like group by does.

Function Equal rows get The next distinct row gets Sequence for results 95·20m, 95·20m, 95·21m, 95·21m, 88·17m
rank() the same number 1 + the number of rows strictly ahead 1, 1, 3, 3, 5
dense_rank() the same number previous + 1 1, 1, 2, 2, 3
row_number() different numbers (arbitrary among ties) previous + 1 1, 2, 3, 4, 5

(These are the measured outputs from PGlite for exactly those five rows.) The formula behind rank():

rank(r)=1+​{s:s is strictly better than r}​
  • Why it's honest: your place is "how many people beat you, plus one". Ties don't push anyone up or down.

The board uses rank() because it matches how competitions report ties ("joint first, then third"), and the podium colours by rank (L2.09c), so two co-winners both get gold.

3.3 generate_subscripts and array indexes

Postgres arrays are 1-based: question_ids[1] is the first question. generate_subscripts(arr, 1) returns the valid indexes of dimension 1 (1 … 100). Joining on q.id = a.question_ids[i] gives one row per position, so p_answers[i] and q.answer line up position by position. array_agg(q.answer order by i) rebuilds the correct-answer array in the test's order. Without order by i, the aggregate's order is unspecified, and the results screen would mark the wrong options as correct.

JavaScript arrays are 0-based. The data crosses the boundary as JSON arrays, which have no index base, so r.correct[0] in the browser is correct[1] in SQL. No conversion is needed as long as nobody indexes manually across the boundary.

3.4 select … for update: a row lock

  1. Definition. for update locks the selected rows until the end of the transaction. Another transaction that tries to lock or update the same row waits.
  2. Why here. A double-tap or a retry can send two submit_test calls for the same attempt at the same moment.
  3. How it works. Each PostgREST request is one transaction. The first call locks the attempt row, grades and updates it, and commits. The second call was waiting on the lock; when it gets the row, it re-reads the committed version, sees submitted_at set, and raises "already submitted".

Takeaway: FOR UPDATE makes the second submit wait for the first to commit, so it sees submitted_at already set and refuses, instead of grading the same attempt twice. 4. Without it. Both calls read submitted_at is null, both grade, both update. The second overwrites the first's duration_ms with a slightly larger value, and the client may get two different results. Not a security hole, but a correctness one.

4

The math

4.1 What a random 100-of-130 test means

start_test draws 100 distinct questions uniformly at random from N=130 (order by random() limit 100). Let T=100.

Chance a given question is in a test. Each question is equally likely to be any of the N positions in a random ordering, and the test takes the first T:

P(q∈test)=NT​=130100​≈0.769

Expected overlap of two independent tests. By linearity of expectation, summing that chance over the 100 questions of the first test:

E[overlap]=T⋅NT​=1301002​≈76.9 questions
  • Meaning: retaking the test repeats about 77 questions and swaps in about 23 new ones.

How many tests until you've seen every question? A question is missed by one test with probability NN−T​=13030​, so it's missed by all k independent tests with probability (133​)k. The expected number never seen:

E[unseen after k]=130⋅(133​)k

The exact probability of having seen all 130 needs inclusion–exclusion over the questions missed (computed for this lesson):

Tests k 1 2 3 4 5 6 7
Expected unseen 30.0 6.92 1.60 0.37 0.085 0.020 0.005
P(all 130 seen) 0 0.0001 0.180 0.687 0.918 0.981 0.996
  • Meaning for a student: the flashcards cover all 130; the ranked test alone would need about 5–6 attempts to show you everything with > 90% confidence. That's one reason the app has both.

4.2 What does guessing score?

The data has 120 four-option questions and 10 two-option (true/false-style) questions. A test contains on average 100⋅13010​≈7.69 two-option questions. Guessing uniformly:

E[score]=7.69⋅21​+92.31⋅41​≈26.9

Treating the questions as independent Bernoulli trials, the variance is ∑p(1−p)=7.69⋅0.25+92.31⋅0.1875≈19.2, so the standard deviation is about 4.4. A pure guesser lands between roughly 18 and 36 about 95% of the time (±2σ). Anything well above 40 means real knowledge, and that is what the mood ladder of L2.09c ("Time for another cup and a review" below 50%) is calibrated against.

4.3 Cost of the functions

Let Na​ be the number of submitted attempts and U the number of players.

Step of get_leaderboard Work Why
Find submitted rows bitmap scan of test_attempts_rank_idx the partial index contains exactly the submitted rows
distinct on sort Na​ rows: O(Na​logNa​), then one pass sort key user_id, score desc, … doesn't match either index's order
counts hash aggregate: O(Na​)
rank() sort U bests: O(UlogU)
joins to profiles, counts hash joins: O(U)

Measured in PGlite with 2,000 players and 10,000 attempts (two runs each):

Text2 lines
get_leaderboard(200) ms 27.0 / 24.8get_my_stats ms         84.9 / 84.3

The plan confirms the shape: Bitmap Index Scan on test_attempts_rank_idx → Sort (user_id, score DESC, …) → Unique → Sort (score DESC, duration_ms) → WindowAgg → Limit.

get_my_stats costs about 3.4× the leaderboard because it calls get_leaderboard(100000) four times, once for each of best score, total, duration and rank (L2.03's "honest critique"). The fix computes it once:

SQL12 lines
create or replace function public.get_my_stats()returns json language sql stable security definer set search_path = public as $$  with me as (select * from get_leaderboard(100000) l where l.user_id = auth.uid())  select json_build_object(    'best_score',    (select score from me),    'best_total',    (select total from me),    'best_duration', (select duration_ms from me),    'rank',          (select rank from me),    'attempts',      (select count(*) from test_attempts t where t.user_id = auth.uid() and t.submitted_at is not null),    'players',       (select count(distinct t.user_id) from test_attempts t where t.submitted_at is not null)  );$$;

A CTE referenced several times is computed once in Postgres 12+ (it's materialised when referenced more than once). Measured on the same 10,000 attempts: identical JSON result, 22 ms instead of 75 ms.

When would it matter? At ~25 ms for 10,000 attempts, a class of a few hundred is negligible. Beyond ~100,000 attempts, you'd keep a best_attempts table (one row per user, updated by submit_test) with an index on (score desc, duration_ms), turning the board into an index scan of 200 rows.

order by random() limit 100 reads every question, assigns a random number, and keeps the top 100 with a bounded heap: O(NlogT). For 130 rows it took 1.6 ms. For a million-row bank you'd use tablesample system_rows(…) or random ids instead.

4.4 Two limits worth knowing

  • duration_ms int: the largest int is 231−1=2,147,483,647 ms ≈ 24.9 days. The 3-hour expiry check in submit_test guarantees durations stay far below that (3 h=3×3600×1000=10,800,000 ms).
  • limit least(greatest(coalesce(p_limit, 100), 1), 100000) clamps the caller's limit into [1,100000]. Measured: null → 100, 0 → 1, -5 → 1, 50 → 50, 10,000,000 → 100,000. Without it, p_limit: -1 would be an error and p_limit: null would return everything.

7

Bug journal: edge cases as stories

Incident ticket · #01

Known edge · A question deleted mid-test shifts the answer key

Fixed
  1. Symptom
    (hypothetical, not seen in production). A student finishes a test right after an admin deleted question 507 to fix a typo. Their results screen marks options as correct that don't match the questions above them.
  2. Diagnosis
    submit_test joins positions to questions: join questions q on q.id = a.question_ids[i]. An inner join drops position i if its question no longer exists. Reproduced in PGlite with ids [101, 99999, 102]: the inner join returned [3, 1] (2 answers for 3 questions); a left join returned [3, null, 1]. The score silently counts 99 positions, and array_agg(q.answer order by i) returns 99 answers for 100 questions. The browser zips correct[i] with question_ids[i] by index, so every position after the missing one is shifted by one.
  3. Root cause
    The function assumed every attempt's question still exists. Nothing in the schema enforces it (no foreign key from an array element to questions).
  4. Fix
    Diff4 lines
      from generate_subscripts(a.question_ids, 1) as i  join questions q on q.id = a.question_ids[i];  from generate_subscripts(a.question_ids, 1) as i  left join questions q on q.id = a.question_ids[i];   -- keep every position; a missing key scores 0, answer null
    and never delete from questions; correct a question with update, which seed.sql's insert … on conflict do update already does.
  5. Lesson
    When you aggregate by position, use a join that can't drop positions, and assert lengths: array_length(correct, 1) = a.total.

7.2 Clean run · Concurrency

Double submissions are handled by for update (§3.4), and the live test "cannot submit another user's attempt, twice, or with a wrong answer count" proves the sequential case. The truly simultaneous case isn't tested (PGlite is a single connection), so it rests on Postgres's documented locking behaviour.

Decision Alternatives Why this one Trade-off Choose differently when
distinct on for "best per user" row_number() … = 1; group by + max() Shortest correct form; whole best row in one pass Postgres-only Portability matters → row_number()

Check yourself

Answer each one before you look. Multiple-choice questions mark your pick and let you try again; for open questions, answer aloud, then reveal and grade yourself honestly.

Q1
Ana's attempts: 90 in 30:00, 90 in 25:00, 85 in 10:00. Which one is her leaderboard entry?
Did you have it?
90 in 25:00. Score first (90 > 85), then shorter duration among the 90s.
Q2
Results: 98, 95, 95, 95, 90. What rank does the 90 get under rank() and under dense_rank()?
Did you have it?
rank(): 5 (four results strictly better). dense_rank(): 3 (two distinct better values: 98 and 95).
Q3
You remove t.submitted_at asc from the distinct on order. What can go wrong?
Did you have it?
For a player with two attempts of the same score and duration, which one is kept becomes unspecified, so submitted_at (used for the tie display order) can change between calls. The score and time shown are the same either way, so it's a stability bug, not a wrong-score bug.
Q4
A student takes 3 ranked tests. Roughly how many of the 130 questions have they still never seen there?
Did you have it?
About 130⋅(133​)3≈1.6. The chance they've seen all 130 is only about 18%.
Q5
Predict: two submit_test calls for the same attempt arrive 1 ms apart. What does each caller receive?
Did you have it?
The first gets its result. The second waits on the row lock, then reads the committed row, sees submitted_at set, and gets "This test was already submitted".
Q6
Why is array_agg(q.answer order by i) needed when the join already iterates i in order?
Did you have it?
SQL doesn't guarantee that a join produces rows in any order; a hash join can emit them shuffled. Only an explicit order by inside the aggregate guarantees the array follows the test's question order.

Flashcards

See all 12 cards as a listfor a quick scan
  1. What does distinct on (k) keep?
    The first row of each group of equal k, in the query's order by, which must start with k.
  2. rank vs dense_rank vs row_number on 1st, 1st, next?
    1, 1, 3 · 1, 1, 2 · 1, 2, 3.
  3. Formula for rank()?
    1 + the number of rows strictly better.
  4. Why order by i inside array_agg?
    Joins don't guarantee order; the correct-answer array must follow the test's question order.
  5. What does for update do in submit_test?
    Locks the attempt row so a concurrent second submit waits, then sees it already submitted.
  6. P(a question is in a 100-of-130 test)?
    NT​=130100​≈0.77.
  7. Expected overlap of two tests?
    100²/130 ≈ 77 questions.
  8. Tests needed to see all 130 with > 90% chance?
    5 (P ≈ 0.918).
  9. Expected score from pure guessing?
    ≈ 27 ± 4.4 (120 four-option and 10 two-option questions).
  10. Why is get_my_stats ~3–4× the leaderboard's cost?
    It calls get_leaderboard four times; a single CTE fixes it.
  11. Complexity of the leaderboard?
    O(Nₐ log Nₐ) for the per-user sort, plus O(U log U) for ranking.
  12. Danger of an inner join from positions to questions?
    A missing question drops a position, shifting the correct-answer array.

Glossary

Bitmap index scan
collects matching row locations from an index, then fetches them.
CTE
a with subquery.
Inclusion–exclusion
counting the probability of a union by alternately adding and subtracting intersections.
Linearity of expectation
the expected value of a sum is the sum of expected values, even for dependent variables.
Partial index
an index over only the rows matching a where.
Query plan
the steps Postgres chooses to execute a query (explain).
Row lock
a lock on one row held until the transaction ends.
Uniform random sample
every subset of the given size is equally likely.
Window function
computes a value per row over an ordered set of rows, without grouping them.
