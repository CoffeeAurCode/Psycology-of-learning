L3.06

Under the hood: OAuth, PKCE, and why sign-up timed out

Recipe card70 min
You need
L2.07c (the six hops, the dashboards), L3.01 (the security model: JWTs, auth.uid(), threat thinking), L1.02 (HTTP status codes, redirects)
You'll produce
A diagnosis method for any 5xx; a PKCE challenge computed by hand and checked with Node; a threat list for the sign-in flow; the session's 504 as a full incident report

In two sentences: "What is HTTP 504?" has a one-line answer, but finding which server timed out, and why, took a probe of every hop between a phone and a mail server. This lesson goes under the sign-in from both directions: the network plumbing that produced the 504 (gateways, SMTP ports, TCP timeouts, rate limits) and the cryptography that makes Google sign-in safe in a browser (the code flow, state, PKCE's hash, redirect allow-lists, the Public Suffix List).

By the end, without notes, you can

  1. From a status code alone, say which hop produced it (500, 502, 503, 504, 429) and what that means for the fix.
  2. Explain why connecting to a website's port 465 times out instead of being refused, and which ports and TLS modes email submission uses.
  3. Derive the S256 code challenge for a given verifier, explain why it is 43 characters long, compute the verifier's entropy (448 bits), and name the attack PKCE stops.
  4. Name the other guards of the authorisation code flow (state, exact redirect URI, client secret on the server, redirect allow-list) and what each one stops.
  5. Predict the outcome of five edge cases: cancelled consent, an in-app browser, a different browser finishing the flow, two tabs, and an abandoned flow.

The problem this solves

The user's first message was "what http 504", and the second was "somebody got it when they tried to signup..so can you check". Sign-up was an email-code request, so one click crossed four machines:

To answer that you need three things this lesson teaches: what each 5xx code means about where it came from (§3.1), how mail servers are reached and what a dead port looks like (§3.2), and, once Google sign-in replaced email, how the new flow stays safe (§3.3–§4).

3

Concepts

3.1 Status codes that point at a hop

  1. Definition. A gateway (or reverse proxy) is a server that receives your request and forwards it to another server, the upstream. Supabase puts one in front of every project.
  2. Why here. The 504 named the gateway's problem, not GoTrue's or the browser's.
  3. How it works.
Code Name Written by Means What you do
500 Internal Server Error the app server itself Its own code crashed Read its logs
502 Bad Gateway a gateway The upstream answered with garbage, or the connection broke Is the upstream crashing or restarting?
503 Service Unavailable a gateway or the server Nobody available to serve (overloaded, paused, deploying) Wait; check status pages; is the project paused?
504 Gateway Timeout a gateway The upstream accepted the request but didn't answer in time Find what the upstream was waiting on
429 Too Many Requests the server You hit a rate limit (not an error in the server) Wait, or raise the limit
  1. Minimal example. curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" https://example.com/ prints the status and how long the whole request took. A 504 typically arrives after a suspiciously round, long time; a 503 often comes back fast.
  2. In this incident. The first probes ruled out "paused" and "down" in under a second each:
    Text3 lines
    == auth/v1/health        HTTP 200 in 0.389026s   {"version":"v2.197.0","name":"GoTrue",…}== auth/v1/settings      HTTP 200 in 0.447659s== rest/v1/profiles…     HTTP 200 in 0.764510s   []
    GoTrue was alive and fast. So the slow thing was something GoTrue itself waited on during sign-up. The only outside dependency of a sign-up is the email.
  3. Without this model: you'd restart things, or blame the user's network.
  4. Try it (2 min). Run the three curls from §7 against the project. Then add -w "%{time_connect} %{time_starttransfer}\n": connect time is the network, start-transfer minus connect is the server thinking.

3.2 Email, SMTP ports, and what a dead port looks like

SMTP (Simple Mail Transfer Protocol) is how one program hands an email to a mail server. A sign-up email from GoTrue goes like this:

Port Use TLS
25 Server-to-server relay optional STARTTLS; often blocked for clients
465 Message submission (apps → their provider) implicit TLS from the first byte (RFC 8314)
587 Message submission starts plain, upgrades with STARTTLS
2525 Unofficial alternative some providers offer like 587

Refused vs timed out. A TCP connection starts with a SYN packet.

  • If the machine is reachable but nothing listens on that port, it answers with a reset (RST): refused, almost instantly.
  • If a firewall silently drops the SYN, nothing comes back at all. The client retries until its own timeout: timed out.

The session measured both:

Text10 lines
# our website on the SMTP ports (curl --connect-timeout 10)== port 465   * Connection timed out after 10011 milliseconds== port 587   * Connection timed out after 10006 milliseconds # a machine with nothing on 465 (localhost) for contrast* connect to 127.0.0.1 port 465 from 0.0.0.0 port 59216 failed: Connection refused* Failed to connect to 127.0.0.1 port 465 after 2027 ms: Could not connect to server # the same website on HTTPS443: HTTP 200, connect 0.105924s
  • Vercel's edge (216.198.79.131, 64.29.17.131) answers web ports in about 0.1 s and drops everything else. Dropping is a normal firewall choice: it gives scanners nothing to learn.
  • (The 2 s on localhost is Windows retrying a refused connection a few times before reporting it; Linux or macOS report it in milliseconds.)
  • So GoTrue's connection to "the mail server" didn't fail fast. It hung, and while it hung, the gateway's clock ran out: 504.

Why the sender address couldn't work either. The settings used noreply@psychology-of-learning-nptel.vercel.app. Receiving mail servers check that the sending domain authorises the sender, using DNS records (SPF, DKIM, DMARC). Only whoever controls a domain's DNS can publish those, and vercel.app belongs to Vercel. Real options send from an address you control: your Gmail through Gmail's SMTP, or a single verified address on Brevo, or a domain you own.

3.3 The authorisation code flow, layer by layer

Google sign-in through Supabase is two OAuth flows nested inside each other:

Vocabulary from the standard (RFC 6749), mapped to us:

OAuth term Inner flow Outer flow
Resource owner the student the student
Client Supabase Auth our React app
Authorisation server Google Supabase Auth
Client type confidential (has a secret) public (can't keep one)
Proof at the exchange client secret PKCE verifier

The guards, and what each stops:

Guard Where Stops
Exact redirect_uri match Google checks it against the client's registered list Google sending codes to an attacker's server
state (one-time random value) Supabase creates it at hop 2, checks it at hop 3 Forged callbacks: an attacker making your browser complete their sign-in ("login CSRF")
Client secret on the back channel Hop 4, server to server Anyone who saw Google's code in a URL redeeming it
Redirect allow-list (redirect_to) Supabase, before hop 5 Supabase handing our code to an arbitrary site (§3.4)
PKCE verifier Hop 6 Anyone who saw our code redeeming it (§4)
Short lifetimes and single use Both servers Replaying an old code

The front channel is everything carried in browser redirects (visible in the address bar, history, extensions, logs). The back channel is server-to-server (hop 4, and our hop 6 POST). The design rule: codes may travel the front channel; secrets and tokens only the back channel. The implicit flow broke that rule by putting the access token in the URL fragment, which is why it's discouraged (RFC 9700).

3.4 Redirect allow-lists and "open redirects"

An open redirect is a link on a trusted site that bounces visitors to any URL in a parameter. Attackers love them, because https://trusted.site/…?to=https://evil.site looks trusted.

  • Supabase's redirect_to is checked against the Redirect URLs allow-list. Without that check, a crafted link starting at our real Supabase URL could finish on an attacker's page, carrying a fresh sign-in code (PKCE would still stop the exchange, but the allow-list means it never gets that far: defence in depth).
  • Our own ?next is used as nav(next, { replace: true }), an in-app React Router navigation, after the student is signed in. It's only ever set by our own links (/me?next=/test). Defence in depth says: validate it anyway. A safe rule is "must start with one / and not //" (//evil.site is a protocol-relative URL: same scheme, different host). That's the hard practice exercise in §11.

3.5 The Public Suffix List and "top private domain"

  1. Definition. The Public Suffix List (PSL, publicsuffix.org) is a shared list of domain endings under which unrelated people can register names: com, co.uk, and also hosting domains like vercel.app, github.io, netlify.app, supabase.co.
  2. Why it exists. Browsers use it so a.vercel.app can't set a cookie for all of vercel.app (which would reach b.vercel.app, someone else's site). Google uses it to decide which domains one developer may claim.
  3. How it works. The list has two sections: ICANN domains (com, in, co.uk) and private domains, added by companies that hand out subdomains. A host's public suffix is the longest list entry it ends with; its top private domain is that suffix plus one more label:

3.6 Edge cases: predict, then reveal

Predict each outcome before opening it.

E1 · The student taps Cancel on Google's screen.

Outcomereveal
Google redirects to Supabase's callback with an error; Supabase redirects to our redirect_to with error=access_denied and an error_description. SignIn shows "Google sign-in didn't finish", removes the three error keys, keeps next. Covered by a UI test.

E2 · The link is opened inside WhatsApp or Instagram, and the student signs in from that in-app browser.

Outcomereveal
Google's OAuth policy blocks sign-in from embedded webviews ("disallowed_useragent", Error 403), because the host app could read what's typed. The fix is human: open the link in Chrome or Safari. It's why the advice to the friend in L2.07c said "in Chrome, not from inside WhatsApp or Instagram".

E3 · The flow starts in one browser and finishes in another (for example, the phone hands Supabase's final redirect to a different browser app).

Outcomereveal
The second browser has no verifier in its localStorage, so the /token?grant_type=pkce exchange fails and the student stays signed out. Meanwhile Supabase already created the user at hop 6. On the day, 2 of the first 8 Google users had a user row but no last_sign_in_at: consistent with this or with a closed tab, but not proven to be either.

E4 · The student taps the button in two tabs, then finishes in the first tab.

Outcomereveal
Each start stores a verifier. In supabase-js 2.117.3, unless an experimental option adds a flow id to the redirect, the exchange reads the fixed key …-code-verifier, which "mirrors the most recently started flow" (a comment in storePKCEVerifier). The first tab's code is presented with the second tab's verifier: the hashes don't match, the exchange fails, and that tab stays signed out. Trying again works. The busy flag stops double taps in one tab, not across tabs.

E5 · Email sign-in is off. Do the tests' admin-minted codes still sign users in?

Outcomereveal
Yes. On the day, after the user turned Email off, api-security.spec.ts (which signs in two throwaway users with generateLink + verifyOtp) still passed 13/13, while a public POST /auth/v1/otp returned 422 email_provider_disabled. Minting a code needs the secret key, so this is a test-only path, not a back door.

The math: PKCE, derived with real numbers

Symbols.

  • v: the code verifier, a random string (RFC 7636 allows 43–128 characters from A–Z a–z 0–9 - . _ ~).
  • SHA256: a hash function mapping any input to 256 bits (32 bytes). Easy to compute forwards; infeasible to invert or to find a second input with the same output.
  • BASE64URL: base64 with +→-, /→_, and no = padding, so the result is safe in a URL.
  • c: the code challenge.

The definition (method S256).

c=BASE64URL(SHA256(ASCII(v)))

Why this shape: the hash means the challenge reveals nothing usable about v (step 1 travels the front channel, so assume attackers see c); base64url makes 32 raw bytes printable in a query string.

The check at the exchange. The server stored c at hop 1. At hop 6 the client sends v′. The server accepts only if

BASE64URL(SHA256(v′))=c

Why it works: the honest client has v (it never left the tab), so equality holds. An attacker who intercepted the code has seen at most c, and producing a v′ that hashes to c means inverting SHA-256.

Worked example. A made-up verifier, so you can reproduce the numbers (v = a3f1 repeated 28 times, 112 characters, the same length supabase-js uses):

JavaScript6 lines
// pkce.mjs: run with `node pkce.mjs`import { createHash } from "node:crypto";const verifier = "a3f1".repeat(28);console.log(createHash("sha256").update(verifier).digest("hex"));console.log(createHash("sha256").update(verifier).digest("base64"));console.log(createHash("sha256").update(verifier).digest("base64url"));
Text3 lines
6d4b01bcf6ad888a01048cddeb1464a5afc22b49845bdc6943a19431c19ae42cbUsBvPatiIoBBIzd6xRkpa/CK0mEW9xpQ6GUMcGa5Cw=bUsBvPatiIoBBIzd6xRkpa_CK0mEW9xpQ6GUMcGa5Cw

Line by line:

  1. The hash is 64 hex digits = 32 bytes = 256 bits.
  2. Plain base64 contains a / (unsafe in a URL path) and ends with = padding.
  3. Base64url swapped /→_ and dropped the =. That 43-character string is c, sent as code_challenge=bUsBvPatiIoBBIzd6xRkpa_CK0mEW9xpQ6GUMcGa5Cw&code_challenge_method=s256.

Why exactly 43 characters. Base64 writes 6 bits per character:

⌈6 bits/char256 bits​⌉=⌈42.67⌉=43

Check with padding: base64 encodes 3 bytes as 4 characters. 32=10×3+2, so 10 full groups give 40 characters, and the last 2 bytes give 3 characters plus one =: 44 with padding, 43 without.

How strong is supabase-js's verifier? From its source (generatePKCEVerifier): it fills a Uint32Array(56) from crypto.getRandomValues, then maps each number through dec2hex, which keeps the last two hex digits (('0' + dec.toString(16)).substr(-2)), i.e. the low byte. So:

56 values×8 random bits=448 bits of entropy,56×2=112 characters

Compare: RFC 7636 recommends 32 random bytes (256 bits). A guesser trying 1012 verifiers per second would need about 2448/1012≈7×10122 seconds. The universe is about 4×1017 seconds old.

What about plain? If a browser lacks WebCrypto, supabase-js falls back to c=v (method plain) and logs a warning. Then anyone who sees the hop-1 URL learns the verifier, and PKCE protects nothing. Every modern browser has WebCrypto on HTTPS pages; the fallback exists for unusual environments.

The attack PKCE stops (authorisation code interception). RFC 7636 was written for phones, where a malicious app could register the same custom URL scheme as a real app and receive its codes. In browsers the leak paths are a malicious extension reading URLs, a proxy or server log recording query strings, or browser history on a shared computer. In all of them the attacker holds the code but not the verifier, and the exchange fails.

Reading the real code: inside supabase-js 2.117.3

Level 3 reads the library that does the work between our lines. These excerpts are from node_modules/@supabase/auth-js/dist/module/ (comments ours).

Making the verifier and challenge (lib/helpers.js):

JavaScript16 lines
export function generatePKCEVerifier() {    const verifierLength = 56;    const array = new Uint32Array(verifierLength);    // (fallback using Math.random when there is no crypto: omitted)    crypto.getRandomValues(array);                      // cryptographically secure randomness    return Array.from(array, dec2hex).join('');         // each → its low byte as 2 hex chars → 112 chars}export async function generatePKCEChallenge(verifier) {    const hasCryptoSupport = typeof crypto !== 'undefined' && typeof crypto.subtle !== 'undefined' && typeof TextEncoder !== 'undefined';    if (!hasCryptoSupport) {        console.warn('WebCrypto API is not supported. Code challenge method will default to use plain instead of sha256.');        return verifier;                                // "plain": challenge = verifier    }    const hashed = await sha256(verifier);              // binary string of the 32-byte digest    return btoa(hashed).replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');   // base64 → base64url}
  • crypto.getRandomValues draws from the operating system's secure random source; Math.random would be predictable.
  • The three replace calls are the whole definition of base64url: the same three changes you saw in §4's output.

Choosing the method and storing the verifier (lib/helpers.js):

JavaScript12 lines
export async function getCodeChallengeAndMethod(storage, storageKey, isPasswordRecovery = false, onEvictFlow) {    const codeVerifier = generatePKCEVerifier();    let storedCodeVerifier = codeVerifier;    if (isPasswordRecovery) {        storedCodeVerifier += '/recovery';             // marks password-recovery flows (not used by us)    }    const flowId = generatePKCEFlowId();    await storePKCEVerifier(storage, storageKey, flowId, storedCodeVerifier, onEvictFlow);    const codeChallenge = await generatePKCEChallenge(codeVerifier);    const codeChallengeMethod = codeVerifier === codeChallenge ? 'plain' : 's256';   // equal only in the fallback    return [codeChallenge, codeChallengeMethod, flowId];}
  • Store first, then navigate. If the browser left before the verifier was saved, the flow could never finish.
  • storePKCEVerifier writes a per-flow slot (<storageKey>-flow-<id>-code-verifier), an index of open flows (<storageKey>-flows-code-verifier, at most 5; older slots are evicted) and the fixed key <storageKey>-code-verifier, which mirrors the most recent flow. A test after one click found exactly those three keys, e.g. sb-kehcsupmruaskpgdvzaj-auth-token-code-verifier (L4.09 Practice, easy).

Incident ticket · #01

"what http 504" on sign-up

Fixed
  1. Symptom
    A friend tapped sign-up (email code) and got:
    Text1 line
    HTTP 504 Gateway Timeout
    Later the same path, with the app's new error mapping, showed "Sign-in is having trouble right now. Please try again in a minute."
  2. Diagnosis
    The real path, including the wrong turn:

Underneath: the dashboard accepts any hostname without testing it.

Incident ticket · #02

Known failure mode · Google blocks embedded browsers

Fixed
  1. Symptom
    Students who open the link from a chat app see Google's "Error 403: disallowed_useragent" when signing in.
  2. Diagnosis
    It happens only inside in-app browsers; the same student in Chrome is fine.
  3. Root cause
    Google's OAuth policies forbid sign-in from embedded webviews, where the host app could read the password field.
  4. Fix
    Nothing in code can override it. Tell students to open the site in Chrome or Safari ("⋮ → Open in browser").
  5. Lesson
    OAuth moves trust to the provider, and with it some of your UX. Put "open in your browser" in the message you send with the link.

Check yourself

Q1
Sign-up returns 503 within 0.2 s. What do you check first?
Did you have it?
Whether the project is paused or being restarted (a fast 503 means "nobody to serve you"), and the provider's status page. A 504 would instead make you look at what the server waits on.
Q2
curl smtps://mail.example.com:465 prints Connection refused immediately. Compared with timed out, what do you learn?
Did you have it?
The machine is reachable and actively rejects the port: nothing listens there. A timeout means packets are dropped (firewall) or the host is unreachable. Either way it's not a mail server on that port, but "refused" fails fast, so it would have produced an immediate error instead of a 504.
Q3
Predict: you change one character of the verifier in localStorage before the app comes back from Google. What happens?
Did you have it?
The exchange sends the changed verifier; its SHA-256 differs completely from the stored challenge (the avalanche property), so Supabase rejects it and the student stays signed out.
Q4
Why does supabase-js send code_challenge_method=s256, and when would it send plain?
Did you have it?
s256 when WebCrypto is available (challenge ≠ verifier). plain only in the no-WebCrypto fallback, where challenge = verifier, which gives no protection if the first URL is seen.
Q5
A teammate proposes adding vercel.app to the authorised domains "to cover preview deployments too". What do you say?
Did you have it?
Google will refuse it: vercel.app is a public suffix. Authorise each hostname you own. For previews, the Supabase redirect allow-list (not Google's) is what needs their URLs, because Google only ever redirects to Supabase.
Q6
Which guard stops an attacker who reads Google's code from a proxy log, and which stops one who reads Supabase's code?
Did you have it?
Google's code needs the client secret at hop 4 (only Supabase has it). Supabase's code needs the PKCE verifier at hop 6 (only the student's tab has it).

Flashcards

See all 14 cards as a listfor a quick scan
  1. Who writes a 504, and about whom?
    A gateway or proxy, about its upstream, which accepted the request but didn't answer in time.
  2. 502 vs 504?
    502: the upstream answered badly or the connection broke. 504: the upstream didn't answer in time.
  3. Why did SMTP to the website time out rather than fail fast?
    Vercel's edge drops packets to non-web ports; no reset comes back, so the client waits until its timeout.
  4. Ports for email submission and their TLS modes?
    465 implicit TLS; 587 STARTTLS. (25 is server-to-server relay.)
  5. Why can't you send as noreply@…vercel.app?
    You don't control vercel.app's DNS, so you can't publish SPF/DKIM/DMARC for it; receivers reject or junk it.
  6. The PKCE S256 formula?
    c=BASE64URL(SHA256(ASCII(v)))
  7. Why is an S256 challenge 43 characters?
    ⌈256/6⌉=⌈42.67⌉=43 (6 bits per base64 character; 44 with one =, which base64url drops).
  8. Entropy of supabase-js's verifier?
    56 random bytes (low byte of each Uint32): 56×8=448 bits, written as 112 hex characters.
  9. What attack does PKCE stop?
    Authorisation code interception: a stolen code can't be exchanged without the verifier.
  10. What does state stop?
    Forged callbacks (login CSRF): completing a sign-in your browser never started.
  11. Public vs confidential client?
    A public client (browser app) can't keep a secret; a confidential client (a server like Supabase Auth) can.
  12. What is a top private domain?
    A public suffix plus one label, e.g. psychology-of-learning-nptel.vercel.app.
  13. Flow started in Chrome, finished in another browser: result?
    No verifier there → exchange fails → signed out, though Supabase may already have created the user.
  14. Why does Google refuse sign-in inside WhatsApp's browser?
    Embedded webviews are blocked by Google's OAuth policy (disallowed_useragent), because the host app could read input.

Glossary

Avalanche property
a tiny input change flips about half of a hash's output bits.
Back channel
server-to-server requests, invisible to the browser.
Base64url
base64 with - and _ instead of + and /, without padding.
Confidential client
an OAuth client that can keep a secret (a server).
Entropy
unpredictability measured in bits; n bits means 2n equally likely values.
Front channel
data carried in browser redirects and URLs.
Gateway / reverse proxy
a server that forwards requests to an upstream.
Implicit TLS
encryption from the first byte of the connection (port 465).
Login CSRF
tricking a browser into finishing an attacker's sign-in.
Open redirect
a trusted URL that forwards to any URL given in a parameter.
Protocol-relative URL
//host/path, which keeps the current scheme.
Public client
an OAuth client that cannot keep a secret (a browser or mobile app).
Public Suffix List
the shared list of domains under which unrelated parties register names.
RST / SYN
TCP's reset and connection-request packets.
STARTTLS
upgrading a plain connection to TLS (port 587).
Upstream
the server a gateway forwards to.
