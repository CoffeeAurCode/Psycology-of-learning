In two sentences: The flashcard deck is the heart of the app: swipe right if you knew it, left to see it again, tap to flip. It is also where the browser fought back hardest, with four real bugs across Chrome, Safari and touch screens, each told here as an incident ticket.

By the end, without notes, you can

  1. Build the deck from a progress snapshot, and explain why marking a card mustn't rebuild it.
  2. Write SwipeCard with motion values: drag → rotation and stamp opacity via useTransform, and a swipe decision by offset or velocity.
  3. Make the card fly out in the swipe's direction using AnimatePresence custom + exit variants.
  4. Build a 3D flip that is correct in Safari, by driving face visibility from the angle instead of relying on backface-visibility.
  5. Diagnose from symptoms: "swipe goes back a page", "swipe works with a mouse but not with a finger", "iPhone shows the answer mirrored", "Backspace leaves the page in Safari".

2

The problem this solves

Reading a question and its answer is passive. Deciding "did I know it?" is retrieval practice, and sorting cards into known/again focuses future time on weak cards. On a phone, the fastest way to decide is a flick of the thumb.

3

Concepts new in this lesson

3.1 Motion values and useTransform

Definition. A motion value (useMotionValue(0)) is a number that animates outside React's render cycle. Updating it moves the element without re-rendering the component, which is essential for 60 fps dragging.

useTransform(x, [a, b], [c, d]) derives a new motion value by linear interpolation, clamped to the range:

f(x)=c+b−aclamp(x,a,b)−a​(d−c)

Our card uses three of these.

Derived value Input range Output range At x = +75 px At x = +110 px
rotate −220 … 220 −14° … 14° 4.8° 7°
goodOpacity ("GOT IT" stamp) 30 … 120 0 … 1 0.5 0.89
badOpacity ("AGAIN" stamp) −120 … −30 1 … 0 0 0

Check one row: rotate(110)=−14+440110+220​⋅28=−14+0.75⋅28=7°.

useTransform(v, fn) (a function form) maps through any function. We use it for the flip's face visibility.

3.2 Deciding a swipe: offset OR velocity

When the finger lifts, Motion's PanInfo tells you offset (total distance dragged) and velocity (px/s at release). Two ways to mean "swipe":

  • A long drag: |offset.x| > 110 px, deliberate and slow.
  • A flick: |velocity.x| > 650 px/s, short but fast.

Using only distance makes flicks feel ignored; using only speed makes careful drags fail. Otherwise the card springs back (dragSnapToOrigin).

3.3 Directional exits with custom

When current changes, the old SwipeCard leaves. It's an exiting child, so it can't get new props. <AnimatePresence custom={dir}> hands dir (+1 right, −1 left, 0 undo) to the exiting child's variant function: exit: (d) => d === 0 ? fade : { x: d*520, rotate: d*24 }. Swipe right, it flies right; undo, it fades.

3.4 A 3D flip that works in every browser

The classic recipe:

  • a wrapper with transform-style: preserve-3d;
  • two faces;
  • the back face at rotateY(180deg);
  • both faces with backface-visibility: hidden;
  • rotate the wrapper 0 → 180°.

Safari (WebKit) didn't hide the back face in our layout. On iPhones the answer showed through, mirrored, before you flipped (incident 3). The robust approach is to compute visibility yourself from the angle:

rotateY front opacity back opacity pointer events
0° … 89.9° 1 0 front
90° … 180° 0 1 back

At exactly 90° the card is edge-on (invisible anyway), so swapping there is seamless. The angle is a spring (useSpring); its slight overshoot past 180° stays above 90°, so faces never flicker (L3.03 has the spring maths).

Incident ticket · #01

A swipe made the browser go back a page

Fixed
  1. Symptom
    An automated touch-swipe test on the Study page logged navigations: NAV …/study, NAV about:blank. After the first swipe the page was about:blank, the browser's previous page in that test.
  2. Diagnosis
    No app code navigates to about:blank. Chrome on touch devices has overscroll history navigation: a horizontal swipe that the page doesn't consume goes back or forward. The first swipe was treated as "swipe back".
  3. Root cause
    The browser's default gesture competed with the app's.
  4. Fix
    (in styles.css):
    Diff7 lines
    html {  overscroll-behavior-x: none;     /* no swipe-to-go-back while swiping cards */  -webkit-text-size-adjust: 100%;}body {  overscroll-behavior-y: none;  overscroll-behavior: none;
  5. Lesson
    Any horizontal-swipe UI must disable horizontal overscroll navigation. The touch test asserts toHaveURL(/\/study/) after swiping.
Incident ticket · #02

Swipes worked with a mouse but not with a finger

Fixed
  1. Symptom
    With the mouse: 3 / 130 ✓ 1 · ↻ 1 (both swipes registered). With CDP touch: 1 / 130 ✓ 0 · ↻ 0 (nothing), yet tapping to flip worked with touch.
  2. Diagnosis
    We moved the touch point: starting at bx.y + 30 (the card's header) → both swipes registered. Starting in the middle (over the options list) → nothing. The middle is .fc-scroll, a scroll container (overflow-y: auto). The browser saw a touch begin inside a scroller and claimed the gesture for scrolling, sending pointercancel to Motion.
  3. Root cause
    Default touch-action on the scroll area let the browser own all pans that began there, including horizontal ones.
  4. Fix
    :
    Diff5 lines
    .fc-scroll {  flex: 1;  overflow-y: auto;  touch-action: pan-y;            /* browser may scroll vertically; horizontal belongs to the swipe */  overscroll-behavior: contain;   /* scrolling the card doesn't scroll the page behind */
  5. Lesson
    Test gestures with real touch input at the spots users actually touch. Mouse-driven tests can't show touch-action conflicts. Every nested scroller inside a draggable needs an explicit touch-action.
Incident ticket · #03

iPhones showed the answer before the flip, mirrored

Fixed
  1. Symptom
    All the functional tests were green. But phone-size screenshots in WebKit (Safari's engine), iPhone SE and iPhone 13, showed the card's back face, text mirrored ("ɘɈomɘɿ .C"), on first render. Chrome and Firefox were correct.
  2. Diagnosis
    The mirroring is the giveaway: we were seeing the back face through the front, rotated 180°. backface-visibility: hidden wasn't taking effect in WebKit for this nesting (draggable parent with transforms, preserve-3d wrapper, faces with overflow: hidden, masked scroll content). The tests had passed because they checked the wrapper's rotation, not what was painted.
  3. Root cause
    The design depended on a 3D rendering detail that browsers implement inconsistently in complex stacking situations.
  4. Fix
    : drive visibility from the angle (§3.4).
    Diff8 lines
     <motion.div className="fc-inner" animate={{ rotateY: flipped ? 180 : 0 }} transition={{ type: "spring", stiffness: 260, damping: 26 }}>   <div className="fc-face">…front…</div>   <div className="fc-face fc-back">…back…</div> const rotateY = useSpring(flipped ? 180 : 0, { stiffness: 260, damping: 26 }); const frontOpacity = useTransform(rotateY, (v) => (v < 90 ? 1 : 0));   // and back/pointer-events <motion.div className="fc-inner" style={{ rotateY }}>   <motion.div className="fc-face fc-front" style={{ opacity: frontOpacity, pointerEvents: frontEvents }} aria-hidden={flipped}>…   <motion.div className="fc-face fc-back"  style={{ opacity: backOpacity,  pointerEvents: backEvents }}  aria-hidden={!flipped}>…
    Verified with before/after-flip screenshots on iPhone SE (WebKit), Pixel 7 (Chromium), desktop Safari and Firefox.
  5. Lesson
    Look at screenshots from every engine; green assertions on internal state aren't proof of what users see. For 3D tricks, don't rely on backface-visibility alone.

Backspace (undo) left the page in Safari

Fixed

Flashcards

See all 9 cards as a listfor a quick scan
  1. Why is the deck a snapshot?
    So marking a card (with "hide mastered" on) can't remove it or shift indexes mid-session.
  2. Swipe decision rule?
    |offset.x| > 110 px or |velocity.x| > 650 px/s, in that direction; otherwise spring back.
  3. How does the exiting card know which way to fly?
    AnimatePresence custom={dir} feeds the exit variant function.
  4. Why angle-driven face opacity?
    WebKit showed the back face mirrored through the front; backface-visibility wasn't reliable in this layout.
  5. Fix for "swipe goes back a page"?
    html { overscroll-behavior-x: none }.
  6. Fix for "touch swipe ignored over the options"?
    touch-action: pan-y (+ overscroll-behavior: contain) on .fc-scroll.
  7. Why does tapping flip but dragging not?
    Motion's onTap is cancelled once the pointer moves past a small threshold.
  8. What does undo do to the mark?
    Nothing; it moves back one card. The next decision overwrites the mark.
  9. Why preventDefault on Backspace?
    Safari otherwise navigates back.
