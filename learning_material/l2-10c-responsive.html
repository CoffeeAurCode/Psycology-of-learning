Recipe card75 min

You'll produce
All 674 lines of src/responsive.css, a measured derivation of the deck height, and the Level 2 checkpoint

In two sentences: styles.css describes the app on a typical phone; responsive.css loads after it and only overrides what must change on other screens: tighter spacing on 320 px Androids, a shorter card on short phones, a slim bar in landscape, a wider column on tablets, and a full side rail on laptops. Every number in it was measured on one of 11 device profiles, and two of its rules exist because the tests or a screenshot sweep caught content hiding under the tab bar or a heading running into the mug.

2

The problem this solves

The user asked for "every screen size, even iPhones and all kinds of Androids". A phone-first stylesheet looks right on a 390 × 844 iPhone and wrong almost everywhere else:

  • on a 320 px Android, the four card buttons and five tab labels don't fit;
  • on an iPhone SE, the card pushes its own buttons under the tab bar;
  • in landscape there's no vertical room at all;
  • on a laptop, a 560 px column floats in a sea of empty space with a phone tab bar at the bottom.

The idea: one override file, organised by device situation rather than by component, each block small and named for who it serves.

3

Concepts

3.1 Media queries add no specificity, so order is the tie-breaker

@media (max-width: 360px) { .deck-controls { … } } has the same specificity as .deck-controls { … }: one class. When several matching rules set the same property, the last one in the file wins. So:

  • responsive.css is imported after styles.css in main.tsx; every override wins over the base.
  • Inside responsive.css, a more specific situation must come later: the ≤ 620 px-tall block (lines 633–674) sits after the ≤ 760 px-tall block (219–251), so on an iPhone SE 1st gen, which matches both, the smaller deck formula wins.

3.2 Query by situation, not by device name

There is no "iPhone" media query. The file targets the situations that change layout:

  • Width (max-width, min-width): how many things fit side by side.
  • Height (max-height): whether the card and its buttons fit above the tab bar.
  • Orientation: landscape phones have a height problem, not a width problem.
  • Input (hover: hover and pointer: fine): whether there's a mouse. Hover effects on touch screens "stick" after a tap, so they are only added where hovering exists.
  • Feature support (@supports): whether the browser understands color-mix() or dvh.

3.3 Feature queries: @supports not (…)

@supports not (height: 100dvh) { … } applies its rules only in browsers that don't understand 100dvh (Safari before 15.4, old Android WebViews). This is the opposite of the "write it twice" fallback from L2.10a. That trick works for one property in one rule; @supports is needed when the fallback must change several rules at once, or replace a whole clamp() expression.

3.4 Where the deck-height constant comes from

The deck's height is "the viewport minus everything that isn't the deck". Write the visible viewport height as H, the height of everything above the deck as A, everything below it down to the screen edge (including the tab bar and a clearance gap) as B:

deck=H−(A+B)
  • Why: the page must fit in exactly one screen on the Study tab, so the deck gets whatever the fixed chrome leaves.

Measured with Playwright's Pixel 7 profile (412 × 839) on /study:

Box top → bottom (px)
Top bar 0 → 63
Page head ("Flashcards · Week …") 71 → 98
Week chips 110 → 156
Mode switch (.seg) 168 → 218
Deck 232 → 631
Deck foot ("12 / 130 · Hide mastered") 639 → 659
Controls (Undo · Again · Got it · Flip) 688 → 744
Tab bar 759 → 827

So A=232 (the deck's top) and B=839−631=208:

A+B=232+208=440

That 440 is the constant in calc(100dvh - 440px). The bottom part breaks down as:

B=deck margin8​​+foot20​​+foot margin + gap29​​+controls56​​+clearance15​​+tab bar68​​+gap under it12​​=208

The 15 px clearance above the tab bar is the only free choice; the rest is measured.

The same derivation on the other two formulas (measured, emulated insets are 0):

Rule Device profile H A (deck top) B (H − deck bottom) A+B Constant in CSS
Short phones (≤ 760 tall) iPhone 13 in Safari, 390 × 664 664 214 664−454=210 424 100dvh - 424px
Very short (≤ 620 tall) iPhone SE 1st gen, 320 × 568 568 161 568−395=173 334 100dvh - 334px

The very-short constant is 90 px smaller because that block removes chrome: it hides the page head (the selected chip already names the deck), tightens the top bar by 8 px, and shrinks the seg and the controls. Lesson: a "magic number" in a calc() should be a measured sum. When you add a row of UI above the deck, the constant must grow by that row's height, or the buttons slide under the tab bar again.

4.2 Hover devices only (lines 18–71)

  • @media (hover: hover) and (pointer: fine): the primary input can hover and is precise (a mouse or trackpad). A touchscreen laptop with a mouse attached qualifies; a phone doesn't.
  • kbd styles keyboard keys: a 2 px bottom border gives the "physical key" look.

  • Hover borders: options (not disabled, not selected), chips (not on), plain buttons (not primary/red/again/got/disabled), round and icon buttons, grid buttons, inactive tabs. The long :not() chains exclude every state that already has its own colours, so hover never fights a state.
  • filter: brightness(1.08) on primary and red buttons lightens any colour by 8% without a new token.

4.3 Small phones, ≤ 360 px wide (lines 73–217)

Who: 320 px Androids (Galaxy S9+ profile), Moto E, iPhone SE 1st gen, and the Galaxy Fold. Every rule here buys horizontal room:

  • Gutters 16 → 12 px, with the matching full-bleed margins on .topbar and .chips (−12 px). If you change one, change the other, or the top bar's background stops short of the edge.

Incident ticket · #01

Card buttons hidden under the tab bar on short phones

Fixed
  1. Symptom
    In the device screenshot sweep (11 sizes × 5 routes), the iPhone SE's Study screen showed the card, but "Again" and "Got it" were covered by the tab bar. Later, the automated check reported the same thing on the 320 × 568 profile:
    Text4 lines
    ✘ [iphone-se] › ui.spec.ts › no page scrolls sideways and nothing hides under the tab bar    Error: Got it button hidden under the tab bar    Expected: <= 493    Received:    572
    The button's bottom edge was 79 px below the tab bar's top.
  2. Diagnosis
    • The deck formula's floor: clamp(340px, 100dvh - 440px, 540px). On a 568 px viewport the preferred value is 128 px, so the deck is 340 px: far more than the space available. The floor meant for "don't make the card tiny" was making the page too tall.
    • First fix (from the sweep): a short-phone block, max(250px, 100dvh − 400px). It fixed the 667 px-tall SE 2nd gen in the sweep.
    • During testing the constant was re-measured and changed to max(236px, 100dvh − 424px) along with smaller chips and seg buttons, but the 568 px profile still failed: 568 − 424 = 144 → floor 236 px, still too tall.
    • A second, smaller tier was needed for ≤ 620 px-tall screens, removing chrome rather than only shrinking the card. With 100dvh - 318px the gap shrank from 79 px to 12 px (Received: 504.98); re-measuring the real chrome gave 334, and the test passed on every project.
  3. Root cause
    A fixed-pixel subtraction (100dvh − 440px) encodes the height of the surrounding UI on one screen. Its clamp minimum then guarantees overflow on any screen shorter than minimum + constant + clearance (340 + 440 = 780 px). Most phones in a browser are shorter than that.
  4. Fix
    Diff8 lines
    /* ---------- short phones (iPhone SE/8, small Androids): keep card buttons above the tab bar ---------- */@media (max-width: 639px) and (max-height: 760px) {  .deck {    height: max(236px, calc(100vh - 424px));                                      /* old-browser line */    height: max(236px, calc(100dvh - 424px - env(safe-area-inset-bottom)));       /* 424 = measured chrome */  }  …tighter page head, chips, seg, foot, card text…}
    Diff6 lines
    /* ---------- very short phones (iPhone SE 1st gen, small Androids: ≤ 620px tall) ---------- */@media (max-width: 639px) and (max-height: 620px) {  .page-head.compact { display: none; }                                           /* remove chrome, not just shrink */  .deck { height: max(220px, calc(100dvh - 334px - env(safe-area-inset-bottom))); }  .deck-controls .round, .deck-controls .btn { … 44px … }                         /* Apple's minimum target */}
  5. Lesson
    Constants in layout calc()s are measurements: derive them from real boxes (§3.4) and write down what they contain. Test the property you care about ("the button is fully above the bar") on the shortest supported screen, not just the narrowest.

Q1
You add a 40 px "streak" banner above the deck on the Study page. What else must change, on which screens?
Did you have it?
All three deck constants grow by 40 (and its margin): 440 → 480, 424 → 464, 334 → 374, plus the vh fallbacks and the ≥ 640 px and @supports formulas. Otherwise the "Got it" button slides under the tab bar on exactly the phones where it was fixed. Better: hide the banner in the very-short block.
Q2
Why is the very-short block (≤ 620 px tall) placed at the very end of the file rather than next to the short block?
Did you have it?
Media queries add no specificity. The iPhone SE 1st gen matches the ≤ 360, ≤ 760 and ≤ 620 blocks, which all set deck or control sizes. The last one in source order wins, so the most specific situation must come last. (Next to the short block would also beat it, but would lose to the ≤ 360 block's 46 px controls if placed before it.)
Q3
Predict: an iPhone 13 in landscape (750 × 342). What deck height applies, and is that a problem?
Did you have it?
Both the landscape block (330 px) and the ≥ 640 block (clamp(420, …) = 420 px) match; the ≥ 640 block comes later, so the deck is 420 px in a 342 px viewport, taller than the screen. It's usable because the page scrolls, but the landscape block's .deck rule never takes effect on wide landscape phones (its tab-bar changes do; measured: 54 px bar, 0 px labels, 420 px deck). Fix: move the landscape block after the ≥ 640 block, or limit the tablet block's deck rule with (min-height: 521px).
Q4
A browser without dvh support loads the Study page. Without lines 610–621, what happens to the deck?
Did you have it?
The base height: clamp(340px, calc(100dvh − 440px − env(…)), 540px) is invalid there, so the whole declaration is dropped and the deck has no height. Its children are all absolutely positioned, so the deck collapses to 0 px and the cards overlap the controls. The @supports block restores a vh version.
Q5
On a laptop, why must .tabbar set transform: none?
Did you have it?
The phone rule centres the bar with left: 50%; transform: translateX(−50%). The rail sets left: 0, but the transform would still shift it left by half its own width (126 px), half off-screen.
Q6
Why are hover effects inside (hover: hover) and (pointer: fine) instead of applied everywhere?
Did you have it?
On touch screens, :hover sticks after a tap until you tap elsewhere, so a tile you tapped stays lifted and an option keeps a hover border that looks like a selection.

C1. (L2.01) Question 7 of week 12 gets which id, and what does answer: 2 mean?

C2. (L2.02, L2.03) A student calls insert into test_attempts … directly with score = 100. What stops them?

Answerreveal
RLS: there is no insert policy on test_attempts for authenticated, so the insert is denied. Attempts are only created by start_test and only scored by submit_test, both security definer functions that compute the score and the duration on the server.

C3. (L2.05) An effect is written useEffect(() => window.scrollTo({ top: 0 }), [path]). What happened when this shape was used in the build, and why?

Answerreveal
A blank page with destroy is not a function. An arrow function without braces returns its expression, and in that Chrome version scrollTo returned a Promise. React stored it as the effect's cleanup and later tried to call it. Wrap the body in braces so the effect returns undefined.

C4. (L2.07a) Your Supabase project sends 8-digit codes. What did the app originally do with them, and what's the fix?

Answerreveal
It cut input to 6 digits, so every real code was rejected and nobody could sign in. The fix accepts 6–10 digits (OTP_MIN = 6, OTP_MAX = 10, maxLength={OTP_MAX}).

C5. (L2.07b) Local progress was updated at 10:05, the cloud row at 10:02. What does sign-in do?

Answerreveal
"Newest wins": local is newer, so the app keeps local and upserts it to the cloud. If the cloud had been newer, it would replace local.

C6. (L2.08a) On an iPhone, the answer shows mirrored through the front of the card. What is the cause, and what is the robust fix?

Answerreveal
WebKit didn't honour backface-visibility: hidden in this nesting of transforms. Drive each face's opacity (and pointer events) from the rotation angle with useTransform, and keep backface-visibility as a bonus.

C7. (L2.09b) You reload the page in the middle of a ranked test. Why do you return to the same question with the clock still correct?

Answerreveal
The attempt (id, question order, answers, current index, server start time) is saved in localStorage on every change; the clock is computed from the server's started_at, not from a client counter, so reloading can't reset it.

C8. (L2.10a–c) The page wobbles sideways on iPhones during a slide animation. Which two lines fix it, and where?

overflow-x: hidden; overflow-x: clip; on both html and body. clip (unlike hidden) doesn't create a scroll container, so the sticky top bar keeps working.

Flashcards

See all 11 cards as a listfor a quick scan
  1. Do media queries add specificity?
    No. With equal selectors, the later rule in the file wins, so more specific situations go later.
  2. Where does the 440 in 100dvh − 440px come from?
    The measured height of everything above the deck (232) plus everything below it to the screen edge (208) on the base layout.
  3. Why did the 340 px clamp minimum cause the tab-bar bug?
    Any viewport shorter than 340 + 440 = 780 px gets a deck taller than the space left, pushing the buttons under the bar.
  4. Which media feature limits hover effects to mice?
    (hover: hover) and (pointer: fine).
  5. How does the tab bar become a rail?
    Fixed left/top/bottom 0, transform: none, rail width, flex column, no radius, shadow or blur, right border; tabs become rows; labels swap; foot pushed down with margin-top: auto.
  6. Why font-size: 0 for landscape tab labels instead of display: none?
    The text stays in the accessibility tree, so links keep their names.
  7. What does @supports not (height: 100dvh) protect?
    Old Safari drops any declaration containing dvh; without the fallback the deck has no height.
  8. Why stack the hero on 1024–1179 px laptops?
    As one of two grid columns it's only ~600 px wide and the heading runs under the absolutely positioned mug.
  9. How should text-vs-art overlap be measured?
    Text extents (DOM Range rects) against the visible art, not element boxes.
  10. Why does .home-top .hero need !important?
    To beat an inline style margin set in Home.tsx.
  11. What is .shell.no-rail for?
    During a running test the rail isn't rendered, so the shell drops its left margin.

Glossary

Breakpoint
a width or height where the layout changes.
Chrome (UI)
the interface around the main content (bars, headers, controls), not the browser.
Feature query
@supports, rules conditional on browser support.
Interaction media features
hover and pointer, describing the primary input.
Phone-first
base styles for phones, overrides for bigger screens.
Rail
a vertical navigation bar along one edge.
Source order
the position of a rule in the stylesheet, the final tie-breaker in the cascade.
Viewport
the visible area of the page; on phones, the screen minus the browser's bars.
