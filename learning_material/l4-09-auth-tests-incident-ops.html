L4.09

Test it and run it: a sign-in you can't automate, and a live incident

Recipe card75 min
You need
L4.03 (Playwright config, support.ts, the local build server), L4.06 (route interception, throwaway users, signedInClient), L2.07c (the Google flow), L3.06 (the hops, PKCE, the 504)
You'll produce
signInPage in tests/e2e/support.ts; the new sign-in section of auth.spec.ts; two tests in ui.spec.ts; an incident probe kit (five commands and one script); a deploy fingerprint check; a runbook for auth changes

In two sentences: You can't (and mustn't) drive Google's real login page from a test, so the tests check everything on our side of the boundary: that the button hands off correctly, and that a real session produces the right screens. The second half is operations: the exact commands that found the 504, how to prove a deploy is live, and three small debugging mistakes from this session that are worth never repeating.

By the end, without notes, you can

  1. Test a third-party sign-in up to your boundary: intercept /auth/v1/authorize, assert provider, redirect_to and code_challenge, and test the cancelled-consent return.
  2. Write signInPage (inject a real session under sb-<ref>-auth-token, reload) and say exactly what it does and doesn't prove.
  3. Run the incident probe kit (timed status checks, auth settings, the sign-up endpoint, a masked user listing, a port check) and interpret each result.
  4. Verify that production serves a given change by fingerprinting its JavaScript bundle.
  5. Debug safely: redact by allow-list, mask personal data, keep commands from hanging on input, and write the message a user needs.

2

The problem this solves

The old journey test typed a code. With Google, the middle of sign-in happens on accounts.google.com, and automating it is a dead end: Google detects automated browsers, a real account would need a password and 2-step verification stored in CI, and scripting Google's login breaks its terms. Mocking the whole thing would test nothing.

The way out is to draw the boundary and test both edges of it:

3

Concepts

3.1 Testing at your boundary

  1. Definition. A boundary test checks the exact message your code sends to a system you don't own, and your behaviour on every reply it can send back, without running that system.
  2. Why here. Google can't be run in a test, but the URL we send and the replies we handle (a code, or an error) are fully ours.
  3. How. Intercept the outgoing request and assert its contents; then simulate each reply by loading the URL the provider would redirect to.
  4. Minimal example.
    TypeScript1 line
    await page.route("**/pay.example.com/**", (r) => { seen = r.request().url(); return r.fulfill({ body: "ok" }); });
  5. In the project: the hand-off test in §4.3.
  6. Without it: a typo in redirectTo, a lost next, or PKCE switched off would all ship silently, because a real Google login still "works".
  7. Try it: in the hand-off test, change the expected redirect_to to /me?next=/test (unencoded) and watch it fail with the actual value printed.

3.2 Intercepting a navigation

  • page.route(glob, handler) intercepts every request the page makes that matches, including full-page navigations like window.location.assign(...).
  • "**/auth/v1/authorize*": ** matches any scheme, host and path prefix; the trailing * allows the query string.
  • route.fulfill({ status, contentType, body }) answers locally. The browser "arrives" at a tiny page instead of Supabase, so nothing goes on to Google.
  • route.request().url() is the full URL with its query: the thing we want to inspect.
  • page.unroute(glob) removes the interception, so later navigations in the same test go to the network again.

3.3 Injecting a session

supabase-js keeps the whole session as JSON in localStorage under a key derived from the project URL. From its source (supabase-js, index.mjs):

JavaScript1 line
`sb-${baseUrl.hostname.split(".")[0]}-auth-token`

For https://kehcsupmruaskpgdvzaj.supabase.co, hostname.split(".")[0] is kehcsupmruaskpgdvzaj, so the key is sb-kehcsupmruaskpgdvzaj-auth-token. Put a valid session there, reload, and the client starts up signed in, exactly as it would after a real Google sign-in finished.

  • Why reload? The client reads storage once, at start-up (getSession in AuthProvider). Writing storage on a running page changes nothing until the next start.
  • What it proves: every screen and request after sign-in (name step, ?next redirect, ranked test, leaderboard, rename, sync, sign-out) with a real JWT against the real database and RLS.
  • What it doesn't prove: the Google redirect chain and the PKCE exchange. Those are covered by the hand-off test (our half), supabase-js's own tests (the exchange), and a manual sign-in after each auth deploy (the live wiring).
  • Alternative: Playwright's storageState saves a whole browser state to a file and loads it into new contexts. Our version builds a fresh session per test user instead, because each test file creates and deletes its own users (L4.06).

3.4 Probing production safely

Live debugging means running commands against real systems with real keys and real people's data. Three habits:

  • Allow-list what you print. Print only values you know are public (the project URL), or only key names. A deny-list ("hide anything called KEY or SECRET") misses the name you didn't think of (§7, Incident 3).
  • Mask personal data. Show pr***@gmail.com, not the address. Count rows instead of listing them when counts answer the question.
  • Never let a command wait for input. In scripts and automation, give every command a time limit (timeout 60 …) and closed input (< /dev/null) (§7, Incident 2).

6.2 The incident probe kit

These five probes found the 504. Keep them; they work for any Supabase project. U and K as in L2.07c §4.

Probe 1 · Is each layer up, and how fast?

Terminal3 lines
for p in auth/v1/health auth/v1/settings "rest/v1/profiles?select=id&limit=1"; do  curl -s -o /dev/null -w "$p  HTTP %{http_code} in %{time_total}s\n" -H "apikey: $K" "$U/$p"done

All 200 in under a second means the project isn't paused or down; look further along the request.

Probe 2 · What is auth configured to do?

Terminal1 line
curl -s -H "apikey: $K" "$U/auth/v1/settings" | grep -o '"google":[a-z]*\|"email":[a-z]*\|"disable_signup":[a-z]*\|"mailer_autoconfirm":[a-z]*'

settings is public by design (the client uses it to know which providers exist).

Probe 3 · Call the failing endpoint yourself, with a throwaway address.

Terminal2 lines
curl -s -m 70 -w "  [HTTP %{http_code} in %{time_total}s]\n" -X POST -H "apikey: $K" -H "Content-Type: application/json" \  -d '{"email":"e2e-bot-probe@example.com","create_user":true}' "$U/auth/v1/otp"

-m 70 caps it at 70 seconds so a hang can't freeze your terminal. On the day: 429 over_email_send_rate_limit in 0.29 s; after the fix: 422 email_provider_disabled. Use an @example.com address: that domain is reserved and never receives mail, so a working mailer can't spam a real person.

6.4 Runbook: after any change to sign-in

6.5 The message a user needs

When the friend saw "Access blocked", the useful answer wasn't a diagnosis; it was steps:

Hi! Please try signing in again:

  1. Open https://psychology-of-learning-nptel.vercel.app in Chrome (not from inside WhatsApp or Instagram).
  2. Tap Me → Continue with Google and pick your account.
  3. If you still see "Access blocked", tap the blue "error details" link on that page and send me a screenshot of it.
  4. If you have another Google account, try that one too.

It worked on the retry. Each step either fixes a known cause (in-app browser), collects the missing evidence (error details), or gives a way around (another account).

Incident ticket · #02

A probe command that hung for two minutes

Fixed
  1. Symptom
    A one-liner meant to write and run the user-listing script hit the 120-second tool limit and was moved to the background. Running the script next gave:
    Text2 lines
    Error: Cannot find module 'C:\Users\BIT\AppData\Local\Temp\claude\…\scratchpad\users.mjs'code: 'MODULE_NOT_FOUND'
  2. Diagnosis
    The command began with a leftover fragment: cat > "$TEMP/claude/users.mjs" 2>/dev/null || true; …. A cat > with no input file and no heredoc reads standard input, and in that shell stdin was open but silent. So cat waited forever, and the real heredoc that wrote the script never ran: hence "file not found" afterwards.
  3. Root cause
    A command that reads stdin, in a context where nobody would ever type.
  4. Fix
    Stop the hung job; write the file with an editor tool; run the script with closed input and a deadline:
    Diff2 lines
     cat > "$TEMP/claude/users.mjs" 2>/dev/null || true; S=…; cat > "$S/users.mjs" <<'EOF' … EOF; node "$S/users.mjs" timeout 60 node "$S/users.mjs" < /dev/null
  5. Lesson
    In scripts and automation, every command gets < /dev/null (or a heredoc) and a timeout. A hang tells you nothing; a timeout tells you where.
Incident ticket · #03

The redaction filter that leaked a token

Fixed
  1. Symptom
    To look at .env.local without exposing keys, the output was piped through:
    Terminal1 line
    sed 's/\(KEY=\|key=\|password.*=\|secret.*[:=]\).*/\1<redacted>/I' .env.local
    The anon key came out as <redacted>, but the next line printed in full: VERCEL_OIDC_TOKEN="eyJhbGciOi…" (a token the Vercel CLI writes when you link a project).
  2. Diagnosis
    The pattern listed names to hide. VERCEL_OIDC_TOKEN= contains none of KEY=, key=, password, secret.
  3. Root cause
    Deny-list redaction: it hides only what you predicted. The impact was small (the token is a development credential that expires 12 hours after issue, and it appeared only in the local session log), but the method was wrong.
  4. Fix
    Allow-list: print key names only, or only values you know are public.

Incident ticket · #04

The breakage that was predicted but didn't happen

Predicted
  1. Symptom (expected)
    Before the user turned the Email provider off, the plan said: "the signed-in tests create their throwaway users through Supabase's email login… turning Email off will probably break those tests."
  2. Diagnosis
    After the switch, instead of rewriting the helpers, the cheapest check ran first: npx playwright test tests/e2e/api-security.spec.ts --project=api → 13 passed. A public POST /auth/v1/otp returned 422 email_provider_disabled at the same time.
  3. Root cause
    The prediction conflated two paths. The provider switch closes the public email sign-in. The tests use the admin path (generateLink with the secret key) to mint the code, and verifying that code still issues a session.
  4. Fix
    None needed; otpFor's comment was corrected so the next reader doesn't make the same assumption.
  5. Lesson
    Test a predicted breakage before "fixing" it. It took 13 seconds and saved a rewrite of three helpers.

Q1
Why does signInPage need the page to be on our origin before page.evaluate?
Did you have it?
localStorage is per origin. Writing it on about:blank (or any other origin) stores the session where our app will never look.
Q2
A teammate replaces the expect.poll in the hand-off test with expect(authorize?.searchParams.get("provider")).toBe("google") right after the click. What happens?
Did you have it?
It fails intermittently (or always): the click resolves before the navigation is intercepted, so authorize is often still undefined. Polling waits for the handler.
Q3
Which of these would the hand-off test catch? (a) detectSessionInUrl set back to false; (b) flowType set to "implicit"; (c) encodeURIComponent removed; (d) the Google client secret rotated in Google but not in Supabase.
Did you have it?
(b) no code_challenge; (c) redirect_to becomes /me?next=/test. Not (a): that's on the return path, after our boundary. Not (d): that's the live wiring; only the manual sign-in in the runbook catches it.
Q4
Probe 3 returns 429 over_email_send_rate_limit. Is the mail server working?
Did you have it?
Unknown. The rate limit is checked before any email is attempted, so a 429 says nothing about SMTP. You need probe 5 (the port) and the SMTP settings.
Q5
The bundle fingerprint still shows "Email me a code" ten minutes after a successful deploy. Two causes?
Did you have it?
(1) You fetched a different deployment or alias than the one that was updated (check the domain you're querying). (2) A cache served the old index.html, which points at the old hashed chunk. (The hashed chunk itself can't be stale: a new build gets a new filename.)

Flashcards

See all 12 cards as a listfor a quick scan
  1. Why can't the tests drive Google's login page?
    Bot detection, real credentials and 2-step verification in CI, and Google's terms. Test your side of the boundary instead.
  2. What does the hand-off test assert?
    The authorize request has provider=google, redirect_to = /me?next=%2Ftest, and a PKCE code_challenge; and the error return shows the message and keeps next.
  3. supabase-js's session storage key?
    sb-${hostname.split(".")[0]}-auth-token, e.g. sb-kehcsupmruaskpgdvzaj-auth-token.
  4. Why reload after writing the session to storage?
    The client reads storage only at start-up.
  5. What does session injection not prove?
    The Google redirect chain and the PKCE exchange.
  6. How do you assert an element is absent from the page?
    expect(locator).toHaveCount(0).
  7. Why do admin-minted codes still work with the Email provider off?
    The switch closes public email sign-in; minting via the admin API (secret key) and verifying still issue a session.
  8. The five probes, in order?
    Timed health/settings/REST; settings flags; the failing endpoint with a throwaway address; masked user listing; the dependency's port.
  9. Deny-list vs allow-list redaction?
    Deny-list hides names you predicted (and leaks the rest); allow-list shows only what you know is safe.
  10. Two habits that stop automation from hanging?
    < /dev/null (no stdin) and timeout N (a deadline).
  11. How do you prove a deploy is what users get?
    Fetch the live HTML, find the hashed entry chunk, grep it for a user-visible string unique to the new version.
  12. First move on a flaky test after your change?
    Read where it failed (error-context.md, screenshot, trace) before assuming your change caused it.

Glossary

Allow-list / deny-list
showing only approved items / hiding only forbidden ones.
Boundary test
a test of what your code sends to, and how it handles replies from, a system you don't own.
Bundle fingerprint
a string that identifies one build's JavaScript.
error-context.md
the page snapshot Playwright writes for a failed test.
Flaky test
a test that fails and passes on the same code.
Heredoc
shell syntax (<<'EOF' … EOF) that feeds literal text to a command's stdin.
OIDC token
a short-lived signed identity token (here, Vercel's for local development).
Route interception
answering a page's network request from the test instead of the network.
Session injection
placing a valid session in storage so the app starts signed in.
storageState
Playwright's saved cookies and storage for reuse across tests.
stdin
a program's standard input stream.
