Google sign-in, line by line (and why email codes went away)

Recipe card75 min
You need
L2.07a (AuthProvider, the three account screens, ?next), L2.04 (supabase.ts, friendlyError), L1.04 §5 (sessions and JWTs)
You'll produce
The Google Cloud and Supabase settings for Google sign-in; src/lib/supabase.ts (client options + one new error rule); SignIn and GoogleLogo in src/pages/Account.tsx (lines 67–122 and 286–295); the sign-in link on the Test page

In two sentences: A friend tried to sign up and got an HTTP 504. The email codes from L2.07a depended on an email server that was set up wrong, so the app switched to "Continue with Google", where Google proves who you are and Supabase turns that proof into the same kind of session the rest of the app already used. This lesson builds that switch from the dashboards down to the last line, and removes everything that only existed for email codes.

What changed in the series. Before this session, the app signed people in with emailed 8-digit codes (L2.07a). Since this session it is Google-only, and the Email provider is switched off in Supabase. L2.07a still teaches AuthProvider (unchanged) and stays worth reading for its bugs, but its SignIn code is history. This lesson is the current SignIn.

By the end, without notes, you can

  1. Configure Google sign-in end to end from memory: the Google Cloud OAuth client (branding, authorised domains, audience, redirect URI) and the Supabase settings (Google provider, Site URL, redirect allow-list, Email off), in the right order with the right values.
  2. Write SignIn: signInWithOAuth with a redirectTo that keeps ?next, a busy state, and clean handling of ?error=… returns.
  3. Explain what detectSessionInUrl: true and flowType: "pkce" do, and the symptom you'd see without each.
  4. Trace one sign-in through the six hops of the redirect chain, naming each URL and who handles it.
  5. Diagnose "Invalid domain: must be a top private domain" and "Access blocked: Authorisation error · Error 400: invalid_request".

2

The problem this solves

The session started with three words from the user: "what http 504". A friend had tried to sign up and got a 504 Gateway Timeout. L3.06 tells the full diagnosis. The short version:

  • Sign-up with an email code means Supabase must send an email before it answers.
  • The project's custom SMTP settings (SMTP = the protocol mail servers use to hand over email) pointed at the app's own website, psychology-of-learning-nptel.vercel.app, on port 465. A website host doesn't run a mail server, so every connection attempt hung until a gateway in front of Supabase gave up: 504.
  • While investigating, a probe request came back 429 over_email_send_rate_limit: the hourly email quota was used up as well. The project had 0 users.

Two fixes were on the table: set up a real email service (Brevo, Gmail SMTP), or stop sending email at all. Email delivery is an ongoing job: quotas, spam folders, sender verification, one more dashboard to keep right. Google sign-in has none of that. The user chose Google, then asked for Google only after the email fallback kept failing (Incident 1 in §8).

3

Concepts

3.1 OAuth sign-in, with Supabase as the broker

  1. Definition. OAuth sign-in ("Sign in with Google") lets a trusted provider confirm who someone is, so your app never handles a password.
  2. Why here. It removes the email server from the sign-in path, which was the thing that broke.
  3. How it works. Think of a club. Google is the government office that issues ID cards. Supabase is the bouncer: it checks your ID card once, then puts its own wristband on you (a Supabase session with a JWT). Inside the club (our app and its database), staff only look at wristbands. They never see the ID card.
    • The app talks only to Supabase. It never receives a Google token or a password.
    • Supabase talks to Google with a client ID (public) and a client secret (private, stored only in the Supabase dashboard).
    • The result is a normal Supabase session, so auth.uid(), RLS and every policy from L2.02 work unchanged.
  4. Minimal example (outside the project, any supabase-js v2 client):
    TypeScript1 line
    await supabase.auth.signInWithOAuth({ provider: "google" }); // browser leaves for Google
  5. In this project: Account.tsx line 88, with a redirectTo (§5.2).
  6. Without it: you're back to sending email, or storing passwords.
  7. Try it (2 min): open the live site in a private window, tap Me → Continue with Google, and watch the address bar change domains: our site → kehcsupmruaskpgdvzaj.supabase.co → accounts.google.com → Supabase again → our site.

3.2 The redirect chain: six hops

Every sign-in is a relay race of browser redirects. Learn the hops; they're how you debug every OAuth problem.

The hop-3 response is real. This is what curl showed during the session (Location header of the 302, one parameter per line):

Text6 lines
https://accounts.google.com/o/oauth2/v2/auth?client_id=182547289278-qo0utv8esu3gg4ag1epvfvas7ufa4ks6.apps.googleusercontent.comredirect_to=https%3A%2F%2Fpsychology-of-learning-nptel.vercel.app%2Fmeredirect_uri=https%3A%2F%2Fkehcsupmruaskpgdvzaj.supabase.co%2Fauth%2Fv1%2Fcallbackresponse_type=codescope=email+profilestate=c77e7cb5-9457-4abd-bf41-99e49b5f21fa
  • L1client_id is public by design; it names our OAuth client in Google Cloud.
  • L3redirect_uri must match, character for character, one of the "Authorised redirect URIs" in Google Cloud. Ours is Supabase's callback, not our website.
  • scope=email profile asks for the email address and the basic profile (name, photo). Nothing else.
  • L6state is a one-time random value Supabase checks when Google comes back, so a forged callback is rejected (L3.06 §3.3).

3.3 PKCE in one paragraph

PKCE (Proof Key for Code Exchange, said "pixie") protects hop 7→8. Before leaving, the app invents a long random secret, the code verifier, keeps it in localStorage, and sends only its hash (the code challenge) to Supabase. When the app later trades Supabase's code for a session, it must present the verifier itself; Supabase hashes it and compares. Anyone who steals the code from the URL (a browser extension, a log, a shoulder) still can't use it without the verifier. The maths, real numbers and attack are in L3.06 §3.4.

3.4 detectSessionInUrl: finishing the sign-in on page load

  • What: a supabase-js option. When true, the client looks at the URL as it starts up. If it sees ?code=… (PKCE) it exchanges the code for a session, then deletes code from the address bar with history.replaceState.
  • Why it was false: in session 1, codes were typed into a box, never delivered in the URL, so there was nothing to detect.
  • What breaks with false: Google sign-in "does nothing". The student returns to /me?next=%2Ftest&code=…, the code sits there unused, and they still see "Continue with Google".
  • Where it runs: inside createClient, before React renders anything. That's why no app code handles ?code at all; AuthProvider's getSession() waits for that start-up work and then returns the new session.

3.5 Redirect allow-lists: Site URL and Redirect URLs

Supabase refuses to send people (and their codes) to arbitrary websites. In Authentication → URL Configuration:

  • Site URL is the default destination, used when no redirect_to is given or when the given one isn't allowed.
  • Redirect URLs is the allow-list. https://psychology-of-learning-nptel.vercel.app/** allows any path and query on our site; http://localhost:5173/** allows the dev server.

If redirect_to doesn't match, sign-in still works but the student lands on the Site URL (the home page) instead of where they were going. That's the only visible symptom, which makes it easy to miss.

3.6 When the student says no

If the student cancels on Google's screen, the chain ends with the error in the query string instead of a code, for example /me?next=%2Ftest&error=access_denied&error_description=…. The app must (a) say something human, and (b) clean the URL so a reload doesn't show the error again. That's lines 73–81 of Account.tsx.

Line notes (only what changed this session; the rest is in L2.04):

  • detectSessionInUrl: true (was false): finish the sign-in when the page loads with ?code= (§3.4). Breaks if false: returning from Google leaves you signed out.
  • flowType: "pkce": use the code-plus-verifier flow (§3.3). The alternative, "implicit", puts the access token itself in the URL fragment (#access_token=…), where browser history and extensions can read it. Breaks if removed: nothing visible. auth-js's default is flowType: 'implicit' (in its DEFAULT_OPTIONS), so sign-in would still work, but less safely.
  • const status = …?.status: supabase-js auth errors carry the HTTP status. For any status in its list of server and gateway errors (500–504 and Cloudflare's 520–530), auth-js throws an AuthRetryableFetchError with that status. Its message is whatever the gateway sent: a bare Gateway Timeout, HTTP 504 (HTTP/2 has no reason phrase), or a JSON dump. None of those help a student.
  • if (status && status >= 500): any server-side failure (500, 502, 503, 504) gets one human sentence. It sits after the offline check on purpose: "Failed to fetch" has no status and means your connection; a 5xx means ours. Breaks if removed: students saw raw or empty error text.
  • Deleted line: if (/Token has expired or is invalid|otp/i.test(msg)) return "That code is wrong or has expired…". No codes are typed any more, and the loose /otp/ pattern could have relabelled unrelated errors.

Bug journal

Incident ticket · #01

The email fallback said "Sign-in is having trouble right now"

Fixed
  1. Symptom
    After Google sign-in shipped with email kept behind a "Use email instead" link, the user tried email with their own address and sent a screenshot:
    Text4 lines
    Email   (the user's own Gmail address)Sign-in is having trouble right now. Please try again in a minute.[ Email me a code → ]‹ Back to Google sign-in
  2. Diagnosis
    That sentence is the new status >= 500 rule in friendlyError, so the server had failed (it was the 504 again). Nothing about email had been fixed: the SMTP host still pointed at the website. The fallback was a path we knew was broken, now with a better-worded error.
  3. Root cause
    A fallback that is never exercised is not a fallback. It added a second way to fail, and the friendlier error made the failure look temporary ("try again in a minute") when it was permanent.
  4. Fix
    The user's call: "remove the option to use email, only keep google sign in", then "make sure from every where … only google sign in".
    Diff4 lines
     const [step, setStep] = useState<"start" | "email" | "code">("start"); … the email form, the code form, send(), verify(), onCode() … <button className="btn sm ghost block">✉ Use email instead</button> <button className="btn primary block" disabled={busy} onClick={google}>   {/* the only way in */}
    Plus the server side: Supabase → Providers → Email off. Afterwards a direct API call is refused before any email is attempted:
    Text1 line
    {"code":422,"error_code":"email_provider_disabled","msg":"Email logins are disabled"}
  5. Lesson
    Every path you ship must be one you've seen work end to end. Turning off a method means turning it off where it's enforced (the auth server), not only hiding its button. A test now asserts there is no email field.
Incident ticket · #02

"Access blocked: Authorisation error" for one friend

Fixed
  1. Symptom
    A phone photo of a laptop showed Google's error page in Edge:
    Text4 lines
    Access blocked: Authorisation errorSomething went wrong during this authorisation request. Please try again.If you are a developer of psychology-of-learning, see error details.Error 400: invalid_request
    The address bar read accounts.google.com/signin/oauth/error?authError=Cg9pbnZhbGlkX3JlcXVlc3QkAM&flowName=GeneralOAuthFlow&client_id=182547289278….
  2. Diagnosis
    • Is our setup broken for everyone? The curl -L check (§4) reached Google's normal account chooser, so the client ID and redirect URI were accepted. And the user table showed other people signing in with Google within minutes of this error. So: not broken for everyone.
    • What does authError say? It's base64. Decoded, the bytes are 0a 0f "invalid_request" 24 00: a protobuf field (tag 0a, length 15) holding the same text as the page. No extra detail.
    • What was different about this attempt? Two things were in flux: the authorised domains were incomplete (Incident 3 was being fixed at that moment), and Google warns that OAuth settings "may take 5 minutes to a few hours" to apply. Account restrictions (a Family Link supervised account, or a school or work account under an admin policy) can also block one account while others work.
    • The page's "error details" link shows Google's exact reason. That was the next thing to ask for.
  3. Root cause
    Not confirmed. The friend tried again later and it worked. By then the authorised domains were fixed and some time had passed, so the most likely causes are the incomplete domain list or settings that hadn't applied yet.
  4. Fix
    No code change. Authorised domains completed (Incident 3); the friend was told to retry in Chrome (not inside WhatsApp or Instagram) and, if blocked again, to tap "error details" and share a screenshot.
  5. Lesson
    For "works for some, not others", compare against the people it works for before changing code. Your two best instruments are a curl of your own redirect chain and the auth users table. And when a provider offers "error details", get them before guessing.
Incident ticket · #03

"Invalid domain: must be a top private domain"

Fixed
  1. Symptom
    Following advice to add supabase.co to Google's Authorised domains, the console refused it, and vercel.app too:
    Text2 lines
    Authorized domain 1 *   supabase.coⓘ Invalid domain: must be a top private domain
  2. Diagnosis
    The advice (from the assistant in this session) was wrong. Google wants a domain one organisation controls. supabase.co and vercel.app are shared by thousands of unrelated projects.
  3. Root cause
    Both are on the Public Suffix List (in its "private domains" section, where hosting companies list domains they hand out to customers). For Google, browsers and cookie rules they behave like .com: nobody "owns" them, so they can't be authorised. The top private domain is the public suffix plus one more label: kehcsupmruaskpgdvzaj.supabase.co and psychology-of-learning-nptel.vercel.app. The mechanics are in L3.06 §3.6.
  4. Fix
    Diff4 lines
     Authorized domain 1: supabase.co                                  (rejected) Authorized domain 1: vercel.app                                   (rejected) Authorized domain 1: kehcsupmruaskpgdvzaj.supabase.co             (our Supabase project) Authorized domain 2: psychology-of-learning-nptel.vercel.app      (our site)
  5. Lesson
    On shared hosting you own a subdomain, not the domain. Check suspicious "parent" domains against publicsuffix.org before adding them anywhere that asks for a domain you control.
Incident ticket · #04

A scripted edit that silently did nothing (CRLF)

Fixed
  1. Symptom
    A small Node script spliced the new SignIn into Account.tsx and also removed the OTP constants with a regex. The splice worked, but a grep right after showed the constants were still there:
    Text2 lines
    12:// Supabase "Email OTP length" (Auth → Providers → Email). This project uses 8.14:const OTP_LENGTH = Number(import.meta.env.VITE_OTP_LENGTH ?? 8);
  2. Diagnosis
    The pattern ended in const OTP_MAX = 10;\n. file src/pages/Account.tsx reported with CRLF line terminators: every line ends \r\n, so 10;\n never matched. String.replace with a non-matching regex returns the string unchanged, with no error.
  3. Root cause
    Windows line endings (\r\n) versus a pattern written for Unix endings (\n), plus an API that fails silently.
  4. Fix
    The block was removed with an exact-match edit instead. In a regex, write \r?\n for "end of line" on files of either style.
  5. Lesson
    After any scripted edit, assert the change: grep for what should be gone, and run the build. Know your files' line endings (file name, or VS Code's status bar "CRLF/LF").

Check yourself

Answer each one before you look. Multiple-choice questions mark your pick and let you try again; for open questions, answer aloud, then reveal and grade yourself honestly.

Q1
A student returns from Google to /me?next=%2Ftest&code=8d3… and still sees "Continue with Google". Most likely cause?
b. The code arrived but nothing exchanged it. (a) would fail at Supabase's callback, before any redirect to our site with a code. (c) affects where you land, not whether you're signed in. (d) returns ?error=…, not ?code=.
Q2
Which URL goes in Google Cloud's "Authorised redirect URIs"?
b. Google only ever redirects to Supabase. Our site is Supabase's redirect target, configured in Supabase's allow-list, not Google's. Adding (a) to Google does no harm but no good either; (c) is Google itself.
Q3
Why does google() not call setBusy(false) after a successful signInWithOAuth?
Did you have it?
Success means the browser is already navigating to Supabase. Re-enabling the button would allow a second tap mid-navigation (a second flow, a new verifier). The "Opening Google…" label also reassures students on slow connections.
Q4
You remove encodeURIComponent and next is /test. What does redirect_to look like, and does it still work?
Did you have it?
…/me?next=/test. It still works for this value (a slash is legal in a query), but the UI test that expects /me?next=%2Ftest fails, and any future next containing & or # would break the URL. Encoding is the correct general rule.
Q5
Signed in fine, but every student lands on the home page instead of the test. What's wrong?
Did you have it?
The redirect_to URL isn't in Supabase's Redirect URLs allow-list, so Supabase used the Site URL. Add https://psychology-of-learning-nptel.vercel.app/**.
Q6
Why show "Google sign-in didn't finish" instead of the error_description from the URL?
Did you have it?
Anyone can craft a link with any error_description. React would escape it (no script runs), but the page would still display a stranger's words, which is a phishing aid. A fixed message can't be abused.

Flashcards

See all 13 cards as a listfor a quick scan
  1. What finally caused the 504 on sign-up?
    Custom SMTP pointed at the website (psychology-of-learning-nptel.vercel.app:465), which has no mail server, so sending the code email hung until the gateway timed out.
  2. In "Sign in with Google" through Supabase, who receives Google's authorisation code?
    Supabase (at /auth/v1/callback). The app only ever receives Supabase's own code.
  3. What does detectSessionInUrl: true do?
    On start-up, supabase-js exchanges a ?code= in the URL for a session and removes it from the address bar.
  4. What does the PKCE verifier prove?
    That whoever exchanges the code is the same browser that started the sign-in; only that tab has the verifier.
  5. Which URL is the Google client's authorised redirect URI?
    https://kehcsupmruaskpgdvzaj.supabase.co/auth/v1/callback.
  6. What happens when redirect_to isn't in Supabase's allow-list?
    Sign-in works, but the user lands on the Site URL instead.
  7. Why can't you authorise vercel.app in Google Cloud?
    It's a public suffix; only a top private domain (suffix + one label) like psychology-of-learning-nptel.vercel.app can be authorised.
  8. Why is ?next passed through encodeURIComponent?
    It's a URL inside another URL's query; encoding keeps characters like /, &, # from breaking the outer URL.
  9. Why does the error cleanup use replace: true?
    So Back doesn't return to the error URL and show the message again.
  10. Why a fixed error message, not error_description?
    URL text is attacker-controlled; displaying it would let anyone put words on your page.
  11. Where does the Google client secret live?
    Only in the Supabase dashboard (Providers → Google). Never in the repo or a VITE_ variable.
  12. How do you turn email sign-in off where it's enforced?
    Supabase → Sign In / Providers → Email off; the API then answers 422 email_provider_disabled.
  13. What's the first diagnostic for "Access blocked" on one account?
    Check whether others can sign in (users table, your own curl of the chain), then get Google's "error details" for that account.

Glossary

Authorisation code
a short-lived, one-use value returned in a redirect, traded for tokens.
Authorised domain
a domain Google lets your OAuth client and consent screen use.
Client ID / client secret
the public name and the private password of an OAuth client.
Code challenge
the hash of the code verifier, sent at the start.
Code verifier
the random secret kept in the browser and revealed only at the exchange.
Consent screen
Google's page that tells users which app wants which data.
Identity provider (IdP)
the service that proves who someone is (Google here).
OAuth 2.0
the standard for delegated authorisation that "Sign in with…" builds on.
PKCE
Proof Key for Code Exchange, binding a code to the browser that started the flow.
Public suffix
a domain under which unrelated parties register names (com, vercel.app).
Redirect URI
where a provider may send the browser back to.
Scope
what the app asks the provider for (email profile).
SMTP
the protocol for handing email to a mail server.
State parameter
a one-time value that ties a callback to the request that started it.
Top private domain
a public suffix plus one label; the smallest domain one owner controls.
