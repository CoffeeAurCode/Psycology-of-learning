The problem this solves

The browser talks to Postgres directly through Supabase's REST API, using the public key. So every table is reachable by anyone on the internet, and the only thing standing between a stranger and your data is what this file declares.

3

Concepts new in this lesson

3.1 Idempotent DDL: why the script is safe to re-run

DDL (data definition language) means statements like create, alter and drop. The user pastes setup.sql into the Supabase SQL editor, maybe more than once: after fixing a question, after we change a function. So every statement must succeed whether or not its object already exists.

Object Re-runnable form Why this form
Table create table if not exists … Keeps existing data; skips if present
Index create unique index if not exists … Same
RLS switch alter table … enable row level security Already idempotent
Policy drop policy if exists "name" on t; then create policy … Postgres has no create or replace policy. Drop-then-create updates the rule
Function create or replace function … Replaces the body in place

Caveat: create table if not exists will not add a column you add later to an existing table. It skips the whole statement. For schema changes on a live database you would write alter table … add column if not exists …. The PGlite test "setup.sql is safe to run twice" runs the file twice and checks the data survived (L4.02).

3.2 Partial indexes

Definition. An index with a where clause contains only the rows that match.

Why here. The leaderboard only ever considers submitted attempts, and it sorts them by score descending, then duration ascending. An index on exactly that subset, in exactly that order, is smaller and matches the query. Unsubmitted attempts (one per active student, deleted on restart) never bloat it.

3.3 Composite primary keys

primary key (user_id, question_id) means "one row per (user, question) pair". That makes "mark card 101 known" an upsert on that pair: the second mark replaces the first instead of adding a duplicate.

Reading the real code (lines 1–74)

4.1 questions (lines 8–17)

SQL10 lines
-- ---------- Questions (answer key lives here; tests are graded in SQL) ----------create table if not exists public.questions (  id      int primary key,           -- week*100 + question number, e.g. 304 = week 3 Q4  week    int  not null,  prompt  text not null,  options jsonb not null,  answer  int  not null              -- 0-based index into options);alter table public.questions enable row level security;-- No policies on purpose: clients never read this table directly.
  • L2, 9public.: Supabase has several schemas (auth, storage, public…). The REST API exposes public. Writing the schema explicitly avoids surprises.
  • L3id int primary key with no default: ids come from the JSON (100w + n), never generated here.
  • L5prompt: the column is prompt while the JSON field is q. Names differ only because "q" is a poor column name. The seed maps one to the other.
  • L6options jsonb: the array of option strings. jsonb validates that it is JSON.
  • RLS on + no policies = no client can read or write. The grader functions read it as the owner. What breaks if you add for select using (true)? Anyone could download the answer key with one curl, including during a test.

4.2 profiles (lines 19–35)

SQL16 lines
create table if not exists public.profiles (  id           uuid primary key references auth.users on delete cascade,  display_name text not null,  created_at   timestamptz not null default now(),  constraint display_name_len   check (char_length(display_name) between 3 and 20),  constraint display_name_chars check (display_name ~ '^[A-Za-z0-9_. -]+$'));create unique index if not exists profiles_display_name_key on public.profiles (lower(display_name));alter table public.profiles enable row level security; drop policy if exists "profiles: read own"   on public.profiles;drop policy if exists "profiles: insert own" on public.profiles;drop policy if exists "profiles: update own" on public.profiles;create policy "profiles: read own"   on public.profiles for select using (auth.uid() = id);create policy "profiles: insert own" on public.profiles for insert with check (auth.uid() = id);create policy "profiles: update own" on public.profiles for update using (auth.uid() = id) with check (auth.uid() = id);
  • L2id uuid primary key references auth.users on delete cascade: a profile is a user. Deleting a user (our e2e cleanup does this) removes the profile automatically.
  • Named constraints (constraint display_name_len …): the name appears in error messages (violates check constraint "display_name_len"), so you know which rule failed.
  • L5char_length(...) between 3 and 20: matches the app's NAME_RE = /^[A-Za-z0-9_. -]{3,20}$/. The database is the real guard, and the client regex only gives faster feedback. Someone calling the API directly hits the database rule.
  • L6~ '^[A-Za-z0-9_. -]+$': POSIX regex. Inside […], a - at the end is a literal hyphen, . is a literal dot, and the space is allowed. This blocks HTML (<img …>), emoji and quotes. That is defence in depth (several layers each blocking the same attack), even though React already escapes output.
  • L8unique index … (lower(display_name)): an expression index. Uniqueness is enforced on the lowercased value, so Espresso Ana and espresso ANA collide (23505), and the app shows "That name is taken".
  • Policies:
    • read own: you can only select your own profile. But the leaderboard shows other people's names? Yes, through get_leaderboard, a definer function that returns only display_name, never emails or ids beyond what's needed (L2.03).
    • insert own: with check (auth.uid() = id): you may create a profile only with your id.
    • update own: using (you can target only your row) and with check (after the update it must still be yours; you can't change id to someone else's).
    • No delete policy: users can't delete their profile from the client. Account deletion would go through the admin API.

4.3 test_attempts (lines 37–55)

SQL18 lines
create table if not exists public.test_attempts (  id           uuid primary key default gen_random_uuid(),  user_id      uuid not null references auth.users on delete cascade,  question_ids int[] not null,  started_at   timestamptz not null default now(),  submitted_at timestamptz,  answers      int[],  score        int,  total        int not null,  duration_ms  int);create index if not exists test_attempts_user_idx on public.test_attempts (user_id);create index if not exists test_attempts_rank_idx on public.test_attempts (score desc, duration_ms asc) where submitted_at is not null;alter table public.test_attempts enable row level security; drop policy if exists "attempts: read own" on public.test_attempts;create policy "attempts: read own" on public.test_attempts for select using (auth.uid() = user_id);-- No insert/update policies: only start_test()/submit_test() can write, so scores can't be forged.
  • L2default gen_random_uuid(): Postgres generates the attempt id. A random uuid can't be guessed (unlike 1, 2, 3…). Even if it could, submit_test also checks ownership.
  • L4question_ids int[]: the 100 drawn ids, in the order shown. Storing the order matters: answers[i] belongs to question_ids[i].
  • L6–8, 10, 13, 18Nullable submitted_at, answers, score, duration_ms: an attempt is born "open" (null) and filled once on submit. "Open" = submitted_at is null. That predicate appears in the partial index, in start_test (delete open attempts) and in the leaderboard (ignore open ones).
  • L9total int not null: the number of questions actually drawn (100 when ≥ 100 exist). The score is out of this.
  • L12test_attempts_user_idx: speeds up "my attempts" and the delete in start_test.
  • L13test_attempts_rank_idx: the partial index from §3.2.
  • Only a select policy. The comment on line 55 is the security design in one sentence. The PGlite and live tests both try insert and update as a signed-in user and expect failure / zero rows (L4.02, L4.06).

4.4 card_progress (lines 57–74)

SQL17 lines
create table if not exists public.card_progress (  user_id     uuid not null references auth.users on delete cascade,  question_id int  not null,  status      text not null check (status in ('known', 'again')),  updated_at  timestamptz not null default now(),  primary key (user_id, question_id));alter table public.card_progress enable row level security; drop policy if exists "progress: read own"   on public.card_progress;drop policy if exists "progress: insert own" on public.card_progress;drop policy if exists "progress: update own" on public.card_progress;drop policy if exists "progress: delete own" on public.card_progress;create policy "progress: read own"   on public.card_progress for select using (auth.uid() = user_id);create policy "progress: insert own" on public.card_progress for insert with check (auth.uid() = user_id);create policy "progress: update own" on public.card_progress for update using (auth.uid() = user_id) with check (auth.uid() = user_id);create policy "progress: delete own" on public.card_progress for delete using (auth.uid() = user_id);
  • L4status … check (status in ('known','again')): the SQL twin of the TypeScript union Mark = "known" | "again".
  • L5updated_at: the client sends its own timestamp on upsert (the time you swiped). Merge logic compares these to decide "newest wins" across devices (L2.07b).
  • L3, 6question_id has no foreign key to questions. That was a choice, honestly a small one. Without it, progress can be saved even before the seed runs, and old progress survives if a question is renamed. A foreign key would be stricter, and since referential checks run as the table owner, it would work despite the questions table having no policies. Either is defensible; we kept it simple.
  • All four commands have policies, all "own rows only". This is the one table the client fully manages. Reset progress in the app is delete … where user_id = me.

  1. What Postgres does Role = authenticated; grant check on the table passes (Supabase grants table privileges by default)
    Rows so far—
    Does the grant alone allow reading all rows?
    No, RLS is next
  2. What Postgres does Adds the policy as a hidden filter: where auth.uid() = user_id
    Rows so far—
  3. What Postgres does Row (A, 101): A = A true

    Skip; no error is raised

    Rows so far2 rows
    What does B see?
    Only (101, known), its own

Bug journal

Clean run

This half of the schema never broke during the build, because it was tested in PGlite before the user ran it in Supabase. The only database bug of the session lived in the functions (a leaderboard limit too low to look up ranks beyond 1,000 players). See L2.03.

The classic Supabase failure, a table with RLS off, is turned into an incident in L3.01, together with how to detect it.

Decision Alternatives Why this one Trade-off Choose differently when
RLS on every table RLS only on "sensitive" tables Every table is reachable via the API; "not sensitive yet" changes Must write policies Never; always on
No write policies on test_attempts Insert policy with check (auth.uid() = user_id) Clients can't forge score or time All writes need functions Low-stakes data the client may own fully

Check yourself

Answer each one before you look. Multiple-choice questions mark your pick and let you try again; for open questions, answer aloud, then reveal and grade yourself honestly.

Q1
A user runs update profiles set id = '<someone else>' where id = '<me>'. Which clause stops it?
B. using allowed targeting their own row, but with check validates the new row, whose id no longer equals auth.uid(). (The PK would also complain if the other id exists. The policy rejects it either way.)
Q2
You remove the partial index. What breaks?
Did you have it?
Nothing functionally. The leaderboard gets slower as attempts grow, because Postgres sorts the submitted rows itself. Indexes change speed, not results.
Q3
Re-running setup.sql after adding a column badge text inside create table if not exists profiles (…). Does the column appear?
Did you have it?
No. The table exists, so the whole statement is skipped. Use alter table public.profiles add column if not exists badge text;.
Q4
Why does a signed-in user get zero rows, not an error, from questions?
Did you have it?
The table-level grant passes (Supabase grants privileges to authenticated), and RLS then filters every row out because no policy matches. An error (42501) would mean a missing grant.
Q5
The leaderboard shows names, yet profiles is "read own". How?
Did you have it?
get_leaderboard is security definer: it runs as the owner (RLS doesn't restrict the owner here) and returns only the columns we choose.

Flashcards

See all 8 cards as a listfor a quick scan
  1. Why no policies on questions?
    So no client can read or write the answer key; only definer functions use it.
  2. Why only a select policy on test_attempts?
    Writes must go through start_test/submit_test so score and time are computed by the server.
  3. Why drop policy if exists before create policy?
    Postgres has no create or replace policy; this makes the script re-runnable and updates the rule.
  4. What does the partial index cover?
    Only submitted attempts, ordered by score desc, duration asc: the leaderboard's shape.
  5. How are names unique ignoring case?
    A unique expression index on lower(display_name).
  6. What happens to a user's rows when the user is deleted?
    on delete cascade removes their profile, attempts and progress.
  7. RLS-denied delete: error or nothing?
    Nothing: 0 rows affected, no error.
  8. Does create table if not exists add new columns?
    No; use alter table … add column if not exists.

Glossary

Composite key
a primary key made of several columns.
DDL
statements that define schema objects.
Defence in depth
several independent layers each blocking the same attack.
Expression index
an index on a computed value like lower(col).
gen_random_uuid()
built-in random uuid generator.
Open attempt
a started, unsubmitted test (submitted_at is null).
Partial index
an index covering only rows matching a where.

role × object × action table.
