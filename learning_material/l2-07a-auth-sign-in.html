The problem this solves

Five places need to know "who is signed in?": the Me tab's dot, Home's stats, the test intro, progress sync and the account page. Each could ask Supabase separately, but they'd disagree for a moment after sign-in or sign-out. One provider holds the truth, and everyone re-renders together when it changes.

3

Concepts

3.1 How supabase-js tracks auth

  • supabase.auth.getSession() reads the stored session (from localStorage; no network unless the token needs refreshing).
  • supabase.auth.onAuthStateChange(cb) calls cb(event, session) on SIGNED_IN, SIGNED_OUT, TOKEN_REFRESHED and so on. It returns { data: { subscription } }, which you unsubscribe from on cleanup.
  • Inside that callback, the library holds an internal lock. Supabase's documentation warns against await-ing other Supabase calls inside it, because that can deadlock. So we schedule the profile fetch with setTimeout(…, 0), which runs after the callback returns.

3.2 maybeSingle()

.select(...).eq("id", uid).maybeSingle() returns data = the row or null when there are zero rows. .single() would return an error for zero rows. A brand-new user has no profile yet, and that is not an error. It's the "choose a name" state.

3.3 One-time-code inputs on phones

Attribute Effect
inputMode="numeric" Phones show the digit keypad
autoComplete="one-time-code" iOS and Android offer "From Messages/Mail: 12345678" above the keyboard, one tap to fill
maxLength={10} Blocks absurd pastes; our accepted range is 6–10 digits
onChange strips non-digits Pasting "1234 5678" or "Code: 12345678" still works

3.4 Native validation vs app validation

<input type="email"> inside a <form> makes the browser validate on submit, and block submission with its own popup, which looks different in every browser. We want one styled message, so the form sets noValidate and our send() validates itself. type="email" stays for the right keyboard (with @) and autofill.

Bug journal

Incident ticket · #01

Nobody could sign in: 8-digit codes cut to 6

Fixed
  1. Symptom
    In the signed-in journey test, after typing the real code, the screen said "That code is wrong or has expired. Request a new one.", and the code box was empty again. The failure screenshot showed the error under an empty box with six placeholder dots.
  2. Diagnosis
    Was the test's code wrong? We logged the verify response in a debug test:
    Text2 lines
    VERIFY 403 {"code":"otp_expired","message":"Token has expired or is invalid"}CODE 8 value before fill:
    The admin API's code had 8 digits. The app's onCode did v.replace(/\D/g, "").slice(0, OTP_LENGTH) with OTP_LENGTH = 6, so the input kept only the first 6 digits and auto-submitted them. Supabase compared 6 digits against an 8-digit code and correctly refused.
  3. Root cause
    The app assumed Supabase's default OTP length is 6. This project's Auth setting ("Email OTP length") was 8. The assumption was never checked against the real config, and no test had used a real code until the e2e suite. Every real user with the real email would have been rejected.
  4. Fix
    Diff14 lines
     const OTP_LENGTH = 6; // Supabase "Email OTP length" (Auth → Providers → Email). This project uses 8. const OTP_LENGTH = Number(import.meta.env.VITE_OTP_LENGTH ?? 8); const OTP_MIN = 6; const OTP_MAX = 10;… const digits = v.replace(/\D/g, "").slice(0, OTP_LENGTH); const digits = v.replace(/\D/g, "").slice(0, OTP_MAX);       // never truncate a real code… disabled={busy || code.length !== OTP_LENGTH} disabled={busy || code.length < OTP_MIN}                      // any valid length can be verified maxLength={OTP_LENGTH} maxLength={OTP_MAX} We sent a 6-digit code …          (Test intro: "a 6-digit code" → "a sign-in code")
    Plus CSS letter-spacing so 8 digits fit, and a VITE_OTP_LENGTH line in .env.example.
  5. Lesson
    Any value that mirrors a remote configuration (code length, rate limits, token expiry) must be read from config or tolerate the whole legal range, and must be exercised by a test against the real service. Our auth journey test now does that on three browsers.
Incident ticket · #02

The browser's own email check hid the app's message

Fixed
  1. Symptom
    The UI test typed not-an-email and clicked "Email me a code", expecting the app's red "Enter a valid email address." It timed out: getByText('Enter a valid email address.') not found.
  2. Diagnosis
    The failure screenshot showed no red text, and nothing had been sent. The browser had stopped the submit itself: type="email" inside a <form> triggers HTML5 constraint validation, which shows a native tooltip (not in the DOM, so invisible to screenshots and tests).
  3. Root cause
    Two validators. The browser's ran first and won, and it looks and words differently in Chrome, Firefox and Safari.
  4. Fix
    Diff2 lines
     <motion.form key="email" onSubmit={send} …> <motion.form key="email" onSubmit={send} noValidate …>   {/* our validation, one style everywhere */}
  5. Lesson
    Pick one validation layer for the UI. Keep type="email" for the keyboard and autofill, and add noValidate when you show your own messages.

Answer each one before you look. Multiple-choice questions mark your pick and let you try again; for open questions, answer aloud, then reveal and grade yourself honestly.

Q1
A user's Supabase project switches OTP length to 10. Without code changes, can they sign in?
Did you have it?
Yes. Auto-submit (at 8) won't fire, but the input accepts up to 10 digits and the button enables at ≥ 6, so tapping Verify works. Set VITE_OTP_LENGTH=10 to restore auto-submit.
Q2
Why does AuthProvider set ready only after fetchProfile?
Did you have it?
So the first rendered screen already knows whether the user needs a name. Otherwise Account would flash ChooseName for an existing user.
Q3
What would .single() do for a new user's profile query?
Did you have it?
Return an error (zero rows), not null. maybeSingle() treats zero rows as a normal null result.
Q4
Why setTimeout(() => fetchProfile(...), 0) in the auth callback?
Did you have it?
supabase-js holds a lock during the callback; awaiting another Supabase call inside can deadlock. Deferring runs it after the callback returns.
Q5
The verify response is 403 otp_expired for a code you just received. List two causes.
Did you have it?
(1) The code was truncated or altered before sending (our bug). (2) A newer code was requested, which invalidates older ones, or more than an hour passed (expiry setting).

Flashcards

See all 8 cards as a listfor a quick scan
  1. What does ready prevent?
    A flash of the signed-out UI before the stored session and profile are loaded.
  2. Why maybeSingle() for the profile?
    New users have no row; zero rows must be null, not an error.
  3. Why defer work in onAuthStateChange?
    Awaiting Supabase calls inside the callback can deadlock on its internal lock.
  4. What was the "nobody can sign in" root cause?
    The app truncated codes to 6 digits; the project sends 8.
  5. Which OTP lengths does the app accept now?
    6–10; auto-submits at VITE_OTP_LENGTH (default 8).
  6. What does autoComplete="one-time-code" give users?
    One-tap fill of the code from Mail/Messages above the keyboard.
  7. Why noValidate on the email form?
    So the app's own message shows consistently instead of each browser's native popup.
  8. What does ?next=/test do?
    After session + profile exist, Account navigates there with replace: true.

Glossary

Auth state change
an event emitted by supabase-js on sign-in, sign-out or refresh.
Constraint validation
the browser's built-in form checks.
Deadlock
two pieces of code waiting on each other forever.
maybeSingle
query helper returning one row or null.
OTP length
the number of digits in emailed codes (a Supabase Auth setting).
sr-only
visually hidden, still read by screen readers.
