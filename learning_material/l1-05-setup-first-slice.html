Setup and the first working slice (+ Level 1 checkpoint)

Recipe card
Time
75 min (+ 30 min setup practice item in the plan)
You need
A computer with internet; L1.01–L1.04
You'll produce
(1) the finished app running locally; (2) a from-scratch Vite + React + TypeScript project, slice/, that shows the 130 questions as flip cards

In two sentences: First you install the tools and run the real app on your machine. Then you build the smallest end-to-end version of it by hand, with no project generator, so that every config file in Level 2 is already familiar.

The problem this solves

Project generators (npm create vite) produce working code you did not write. When something breaks, you cannot tell which line matters. Building the skeleton by hand once makes it yours. And running the finished app first gives you a target to compare against.

3.2 Clone, install, configure, run

Terminal3 lines
git clone https://github.com/CoffeeAurCode/Psycology-of-learning.gitcd Psycology-of-learningnpm install
  • git clone copies the repo with its history.
  • npm install reads package.json plus package-lock.json (exact resolved versions of every sub-dependency) and fills node_modules/. Expect added ~200 packages.

Create .env.local by copying the template:

Terminal4 lines
cp .env.example .env.local# then edit .env.local:# VITE_SUPABASE_URL=https://YOUR-PROJECT.supabase.co# VITE_SUPABASE_ANON_KEY=sb_publishable_xxx

Without real values, the app still runs. Flashcards, quiz and list work offline, and the test and leaderboard screens show "needs Supabase" banners (L2.04 explains isConfigured).

Terminal1 line
npm run dev       # → VITE v7.x ready … Local: http://localhost:5173/

Open the URL. dev runs the Vite dev server. It serves source files translated on the fly, and hot module replacement (HMR) updates the page when you save.

Terminal2 lines
npm run build     # → tsc -p . && vite build → dist/index.html, dist/assets/*.js|cssnpm run preview   # → serves dist/ at http://localhost:4173

build first type-checks (tsc -p .; any type error stops the build), then bundles to dist/. preview serves dist/ exactly as a static host would. Always try preview before deploying: some bugs only exist in the built version.

3.3 Common failures (learn them now)

Symptom Cause Fix
'vite' is not recognized / command not found: vite npm install not run, or run in another folder Run npm install in the folder that has package.json
Port 5173 is in use (or Vite silently picks 5174) Another dev server is running Close it, or pass --port 5180 --strictPort (strict = fail instead of switching)
error TS2307: Cannot find module './questions.json' Wrong path, or JSON imports not allowed Check the path; Vite + moduleResolution: "bundler" handle JSON
Blank page; console: destroy is not a function An effect returned a value (L2.05) Wrap effect bodies in braces
"/study" becomes C:/Program Files/Git/study when passed to a script in Git Bash MSYS path conversion rewrites arguments that look like paths Prefix the command with MSYS_NO_PATHCONV=1 (L4.03)

4.1 package.json

JSON21 lines
{  "name": "slice",  "private": true,  "type": "module",  "scripts": {    "dev": "vite",    "build": "tsc -p . && vite build",    "preview": "vite preview"  },  "dependencies": {    "react": "19.2.9",    "react-dom": "19.2.9"  },  "devDependencies": {    "@types/react": "19.2.18",    "@types/react-dom": "19.2.7",    "@vitejs/plugin-react": "5.2.0",    "typescript": "5.9.3",    "vite": "7.3.7"  }}

Line notes:

  • "private": true: npm refuses to publish it by accident.
  • "type": "module": .js files (and vite.config.ts) are ES modules, so import works everywhere.
  • Exact versions (no ^): we pinned what we tested, so a new release can't change behaviour silently. The real project pins most packages the same way. (A few test tools added later use ^.)
  • dependencies vs devDependencies: runtime libraries vs build and type tools. Vite bundles both into the output as needed. The split documents intent.

Then:

Terminal1 line
npm install

4.2 tsconfig.json

JSON17 lines
{  "compilerOptions": {    "target": "ES2022",    "lib": ["ES2022", "DOM", "DOM.Iterable"],    "module": "ESNext",    "moduleResolution": "bundler",    "jsx": "react-jsx",    "strict": true,    "skipLibCheck": true,    "isolatedModules": true,    "verbatimModuleSyntax": true,    "noEmit": true,    "resolveJsonModule": true,    "types": ["vite/client"]  },  "include": ["src"]}

Line notes:

  • target/lib: which JS features and browser APIs exist (DOM types like HTMLElement).
  • moduleResolution: "bundler": resolve imports the way Vite does.
  • jsx: "react-jsx": the modern JSX transform, with no import React needed in every file.
  • strict: true: null checks and more. This is what made profile! necessary, and visible, in our code.
  • isolatedModules + verbatimModuleSyntax: each file must be translatable on its own (that is how Vite compiles). Type-only imports must say import type.
  • noEmit: tsc only checks; Vite produces the JS.
  • resolveJsonModule: allows import raw from "./questions.json". (The real project resolves JSON through Vite's bundler resolution too. It doesn't list this flag, but adding it is harmless and makes the slice explicit.)
  • types: ["vite/client"]: types for import.meta.env and asset imports.

4.5 src/main.tsx

TSX10 lines

4.6 src/App.tsx: the slice

TSX53 lines
import { useEffect, useState } from "react";import raw from "./data/questions.json"; type Question = { id: number; week: number; q: string; options: string[]; answer: number };const QUESTIONS = raw as Question[];const LETTERS = "ABCD"; export default function App() {  const [pos, setPos] = useState(0);  const [flipped, setFlipped] = useState(false);  const q = QUESTIONS[pos];   const go = (d: number) => {    setFlipped(false);    setPos((p) => (p + d + QUESTIONS.length) % QUESTIONS.length);   // wrap around both ends  };   useEffect(() => {    const k = (e: KeyboardEvent) => {      if (e.key === " ") { e.preventDefault(); setFlipped((f) => !f); }      if (e.key === "ArrowRight") go(1);      if (e.key === "ArrowLeft") go(-1);    };    window.addEventListener("keydown", k);    return () => window.removeEventListener("keydown", k);  });                                          // no deps: re-bind each render (go is recreated)   return (    <main className="wrap">      <p className="meta">        Week {q.week} · Q{q.id % 100} · {pos + 1} / {QUESTIONS.length}      </p>      <button className={`card ${flipped ? "flipped" : ""}`} onClick={() => setFlipped((f) => !f)}>        {!flipped ? (          <>            <strong>{q.q}</strong>            <ol type="A">{q.options.map((o) => <li key={o}>{o}</li>)}</ol>            <small>Tap to reveal</small>          </>        ) : (          <>            <small>Correct answer</small>            <strong className="ans">{LETTERS[q.answer]}. {q.options[q.answer]}</strong>          </>        )}      </button>      <nav>        <button onClick={() => go(-1)}>← Prev</button>        <button onClick={() => go(1)}>Next →</button>      </nav>    </main>  );}

Line notes:

  • raw as Question[]: JSON imports are typed loosely; we label them. The real app does the same in questions.ts.
  • q.id % 100: ids are week*100 + n, so % 100 gives the number within the week (L2.01).
  • (p + d + len) % len: modulo wraps around. + len keeps it positive when going back from 0. Check: (0 − 1 + 130) % 130 = 129 ✓.
  • The key={o} on options: option texts are unique within a question (a data test enforces this, L4.01).
  • We swap content on flip instead of using a 3D rotation. The real app's 3D flip, and why Safari needed a special approach, comes in L2.08a.

Bug journal: setup

Clean run

Building the slice by hand avoided generator surprises, so nothing broke. The real project's first browser run did break (blank page). That story lives with the code that caused it in L2.05. One setup-adjacent surprise from the session is worth knowing now:

Incident ticket · #01

"The dev server keeps reloading and the app looks frozen."

Fixed
  1. Symptom
    During testing in Chrome, the page kept reloading; timers took 37 seconds to fire a 500 ms timeout; screenshots timed out.
  2. Diagnosis
    The console showed [vite] server connection lost. Polling for restart... about once a minute, followed by reloads. A JS check showed document.visibilityState === "hidden". The test tab was in the background.
  3. Root cause
    Two unrelated things. (a) In this environment the dev server's live-reload WebSocket kept dropping, and Vite's client reloads the page when it reconnects. (b) Browsers throttle timers and pause requestAnimationFrame in hidden tabs, so animations never finished.
  4. Fix
    Test against npm run build && npx vite preview (no reload socket), and in automation use headless browsers, which are never "hidden".
  5. Lesson
    Before calling an app frozen, check document.visibilityState and whether you are on the dev server. Full forensics in L4.07.

Why this design

Decision Alternatives Why this one Trade-off Choose differently when
Vite + React + TS Next.js; plain HTML/JS Fast static build, zero-config deploy, types catch errors early No server rendering (SEO relies on meta tags + fallback HTML) You need per-page SSR or server routes → Next.js
Hand-written config npm create vite Every line understood 10 minutes of typing Never for learning; fine for a throwaway
Pinned exact versions ^ ranges Reproducible builds Manual upgrades A library you want patch fixes from automatically
Content swap (slice) vs 3D flip CSS 3D from day one Works on every browser immediately Less delightful Once you know the Safari pitfall (L2.08a)

Q1
npm run build fails with a TypeScript error but npm run dev works. Why?
B. Vite's dev server only strips types for speed. Our build script runs tsc first, so type errors block deploys. That is a feature.
Q2
Why put the slice folder outside the repo?
Did you have it?
So its node_modules and experiments can't be committed or deployed by accident, and the real project's config stays untouched.
Q3
You go back from card 1 and get undefined errors. Which expression is missing the + len?
Did you have it?
(p + d) % len: in JavaScript -1 % 130 is -1 (remainder keeps the sign), so QUESTIONS[-1] is undefined. Adding len first fixes it.

9

Flashcards

See all 6 cards as a listfor a quick scan
  1. What does npm run build do before bundling, in this project?
    Runs tsc -p . to type-check; any error fails the build.
  2. Why "type": "module" in package.json?
    So JS/TS config files are ES modules and can use import.
  3. Why verbatimModuleSyntax?
    Forces import type for type-only imports so per-file compilation (Vite) never imports a non-existent runtime value.
  4. Where does index.html live in a Vite app?
    The project root; it is the entry point.
  5. Why test with preview before deploying?
    It serves the production build; some bugs exist only after bundling or without the dev server.
  6. How do you wrap an index backwards safely?
    (p + d + len) % len, because JS % keeps the sign.
