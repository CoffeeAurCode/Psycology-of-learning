2

The problem this solves

Students study on their phone on the bus and on a laptop at home. Progress must work offline and signed out (instantly, in the browser), yet follow them once signed in, without one device wiping the other's work. And the leaderboard needs a public name that is safe to show.

3

Concepts

3.1 Optimistic updates

Definition. Update the UI immediately as if the server call succeeded, and send the call in the background.

Why here. A swipe must feel instant. Waiting 200 ms for Supabase before moving to the next card would feel broken. If the upsert fails (offline), the mark is still in localStorage, and the next sign-in merge pushes it up.

3.2 "Last write wins" by timestamp

Each mark carries t, the moment you swiped (milliseconds since 1970). When two copies disagree about the same card, the larger t wins:

merged[id]={remotelocal​if tremote​>tlocal​ or local missingotherwise​

It is simple and good enough for flashcards: the most recent judgment of a card is the one you want. It is wrong for data where both edits matter (two people editing one document). That needs merging, not picking.

3.3 Supabase query builders are lazy

supabase.from("t").upsert(row) builds a request object. It is sent only when awaited or .then()-ed. The builder is a "thenable" (an object with a then method, which await understands). That is why mark() ends with .then(() => {}). Remove it, and nothing is ever saved to the cloud, silently.

Worked trace (step-through frames): the merge with real timestamps

Device B (laptop) signs in. Times are simplified integers (real values are epoch milliseconds).

Local (pol.marks on B): { 101: { s: "known", t: 1000 }, 102: { s: "again", t: 3000 } } Cloud (from phone A): [{ question_id: 101, status: "again", updated_at: t=2000 }, { question_id: 103, status: "known", updated_at: t=500 }]

The known limitation (honest)

A reset on device A deletes the cloud rows. Device B still holds its local marks. The next time B signs in (uid changes), the merge sees an empty cloud and pushes B's marks back up. Resets aren't propagated, because deletions leave no trace to compare against. The fix would be tombstones: store status: "cleared" with a timestamp instead of deleting, so "newest wins" also covers resets. Not built, since resets are rare.

Bug journal

Incident ticket · #01

Signing out crashed the whole app to a blank page

Fixed
  1. Symptom
    The signed-in journey test got through sign-in, a 100-question test, the leaderboard, a rename and progress sync, then failed at the last step:
    Text3 lines
    Error: expect(locator).toBeVisible() failedLocator: getByText('Pull up a chair')Received: <element(s) not found>
    The failure screenshot was an empty cream page. No top bar, no tab bar, nothing.
  2. Diagnosis
    A totally blank page in React 19 means an uncaught render error unmounted the root. What renders at sign-out? Account swaps its keyed child from <Me/> to <SignIn/> inside AnimatePresence mode="wait". AnimatePresence keeps the exiting <Me/> mounted for its fade. While mounted, it re-renders with the latest context. signOut had set profile = null immediately, while session cleared a moment later via onAuthStateChange. So <Me/> rendered with a session and profile === null, and the line const name = profile!.display_name; threw TypeError: Cannot read properties of null. The ! had told TypeScript "never null", and that was wrong for exactly this frame.
  3. Root cause
    A component assumed its parent's condition (profile exists) still held, but exit animations render components after the condition that chose them has become false. On top of that, two pieces of state that should change together (session, profile) changed at different times.
  4. Fix
    (three layers).
    Diff7 lines
    function Me() {  const { session, profile, signOut } = useAuth();  …all hooks…  const name = profile!.display_name;  // can briefly render during the sign-out transition, after the profile is cleared  if (!session || !profile) return null;      // guard AFTER the hooks  const name = profile.display_name;
    Diff5 lines
      signOut: async () => {    await supabase.auth.signOut();    setSession(null);                           // clear both together    setProfile(null);  },
    Plus the app-wide ErrorBoundary (L2.05), so any future render error shows "Oops, something spilled" instead of a blank page. The test now also collects pageerror events and asserts there were none.
  5. Lesson
    Components rendered inside AnimatePresence must survive the state that made them stop being chosen. Never use ! on data that can change during an animation. And update related state atomically.

Check yourself

Answer each one before you look. Multiple-choice questions mark your pick and let you try again; for open questions, answer aloud, then reveal and grade yourself honestly.

Q1
You delete .then(() => {}) from mark. What happens?
B. Supabase query builders execute only when awaited or then-ed. Local state still updates, so D is wrong.
Q2
Why does the merge re-read storage instead of using marks?
Did you have it?
The async function's captured marks may be stale by the time the network returns. Storage is updated on every mark, so it is current.
Q3
Phone (clock correct) marks 101 "known" at 10:00. Laptop (clock 10 minutes fast) marked 101 "again" at real time 09:55, recorded as 10:05. After merging, which wins?
Did you have it?
"again", because 10:05 > 10:00, even though it was really earlier. That is the clock-skew weakness of wall-clock last-write-wins. Using server timestamps (default now() on insert) would fix ordering for cloud writes.
Q4
Why is the Me guard placed after useToast()?
Did you have it?
Rules of hooks: returning before some hooks would change the number of hooks called between renders and make React throw.
Q5
A user resets on the phone, then signs in on the laptop that still has local marks. What does the laptop end up with?
Did you have it?
Its old marks, pushed back to the cloud: the reset didn't propagate. That's the known limitation; tombstones would fix it.

Flashcards

See all 8 cards as a listfor a quick scan
  1. What does "local-first" mean for marks?
    State and localStorage are the primary copy; the cloud is merged in on sign-in and updated in the background.
  2. Merge rule per card?
    Keep whichever copy has the newer timestamp; add missing ones.
  3. Which local entries are pushed after the merge?
    Those the cloud lacks or has with an older timestamp.
  4. Why .then(() => {}) after the upsert?
    Supabase builders are lazy; nothing is sent until awaited or then-ed.
  5. Why did sign-out blank the app?
    The exiting <Me/> re-rendered with profile = null and dereferenced it via profile!; the render error unmounted the root.
  6. Three layers of the sign-out fix?
    A guard in Me after hooks; signOut clears session and profile together; an app-wide ErrorBoundary.
  7. Known limitation of the sync?
    Resets don't propagate to other devices' local copies (no tombstones).
  8. Why minWidth: 0 on the email column?
    Flex items default to min-width auto; 0 lets them shrink so the ellipsis works.
