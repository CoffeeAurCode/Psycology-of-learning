The problem this solves

setup.sql passing in PGlite doesn't mean the live project matches it: someone could have edited a policy in the dashboard, skipped running the latest setup.sql, or changed an auth setting (code length, email templates) that no SQL describes. And the UI tests of L4.04–05 used injected state; nothing yet proves a real person can sign in, take a test and see themselves ranked.

The idea: one spec attacks the live API directly, and one journey uses the live system through the UI, both with throwaway users that are created confirmed and deleted afterwards.

3

Concepts

3.1 What's real and what's faked

Part Real or faked Why
The browser, the built app, the network to Supabase Real It's the system under test
"Send me a code" (POST /auth/v1/otp) Faked with page.route → 200 {} Sending real email would spam example.com, hit rate limits, and need an inbox
The code itself Real, from generateLink It's the code Supabase would have emailed
Verifying the code (/auth/v1/verify) Real Proves the 6–10 digit handling, sessions, and the redirect back to /test
Everything in the database Real RLS, functions and the leaderboard as deployed

3.2 Route interception

page.route(pattern, handler) intercepts the page's requests whose URL matches the glob. The handler can route.fulfill(...) (answer it), route.continue() (let it through, possibly modified) or route.abort(). Here only the OTP-send endpoint is fulfilled; every other request goes to Supabase untouched. A counter proves the app actually made the request exactly once.

3.3 pageerror: fail on crashes nobody asserted

page.on("pageerror", e => …) fires for uncaught exceptions in the page. Many crashes don't break the next assertion immediately (the error boundary shows a "Reload" screen, or a background promise rejects). Collecting them and asserting the list is empty at the end catches them anyway. This is how the "signing out crashed the app" bug would be caught even if the next screen happened to render.

3.4 Serial mode and long timeouts

test.describe.configure({ mode: "serial", timeout: 480_000 }):

  • serial: the tests in the file run in order in one worker, and if one fails the rest are skipped (for the security spec, the signed-in tests share users created in beforeAll).
  • 480 s: a 100-question test through the UI is long on slow WebKit (each question is a slide transition plus an auto-advance). 240 s was measured as not enough on iphone-13.

Incident ticket · #01

One worker's cleanup deleted another worker's user mid-test

Fixed
  1. Symptom
    In a full run, the Firefox journey failed at the very end of its test:
    Text4 lines
    ✘ [desktop-firefox] › auth.spec.ts › sign in, take a ranked test, appear on the leaderboard, manage account  Error: expect(page).toHaveURL(expected) failed  Expected pattern: /\/test\/result/  Received string:  "http://127.0.0.1:4174/test/run"
    The page snapshot showed "Question 100 of 100", 94/100 answered, the clock at 8:02, and "Submit test" focused: the click had happened, but submission didn't go through.
  2. Diagnosis
    The same journey passed alone. In the full run it overlapped with api-security.spec.ts in another worker, whose afterAll called deleteTestUsers(), which deleted every user whose email starts with e2e-bot-. That included the Firefox journey's user, deleted while it was on question 100. Its session then pointed at a user that no longer existed, and submit_test failed.
  3. Root cause
    A cleanup scoped by a shared prefix, run while other workers were using resources with that prefix. Cleanup was correct for a single worker and wrong for four.
  4. Fix
    (in support.ts):
    Diff8 lines
    const created = new Set<string>();export async function createTestUser(tag: string) {  …  created.add(data.user!.id);  return { email, id: data.user!.id };}/** Delete only the users this test file created (other workers may still be using theirs). */export async function deleteMyTestUsers() { … for (const id of created) … }
    and both specs' afterAll switched from deleteTestUsers to deleteMyTestUsers. The prefix sweep moved to global teardown, which runs after all workers.
  5. Lesson
    In parallel test runs, a test may only destroy what it created. Sweeps by pattern belong in global setup or teardown, when nothing else is running.
Incident ticket · #02

An extra "Next" click skipped a question

Fixed
  1. Symptom
    The iPhone 13 journey hit the 8-minute limit, stuck on one line:
    Text3 lines
    Error: locator.click: Test timeout of 480000ms exceeded.  - waiting for getByRole('button', { name: /^Next/ })> 63 |       if (i < 99) await page.getByRole("button", { name: /^Next/ }).click();
  2. Diagnosis
    Eight minutes of waiting for a button isn't slowness; the button wasn't there. The failure screenshot and page snapshot showed the last question, where the runner's bottom bar shows "Submit test" instead of "Next". So the test thought it was on an earlier question than the app. Reading the loop found an extra step: after answering question 94, the loop clicked "Next" (if (i === 93) … Next), but the app auto-advances after an answer. When that click landed after the auto-advance, it moved one question further, the skip loop's "Next" clicks reached question 100 one step early, and the final "Next" waited forever. (Why the other engines passed wasn't fully established; the timing of the click relative to the auto-advance is the likely difference, and slower WebKit runs made the late landing more likely.)
  3. Root cause
    The test duplicated an action the app performs itself (advancing), making the outcome depend on timing.
  4. Fix
    Diff3 lines
        await page.locator(".q-card .opt").nth(pick).click(); // the app auto-advances after an answer    if (i === 93) await page.getByRole("button", { name: /^Next/ }).click();  }
    plus the per-iteration guard already in the loop, await expect(page.getByText(\Question ${i + 1} of 100`)).toBeVisible()`, so any future drift fails within 8 s at the right line instead of after 8 minutes. The file's timeout was also raised from 240 s to 480 s, after a separate run showed WebKit needing more than 4 minutes for 100 questions.
  5. Lesson
    Don't perform actions the app already performs. Assert you're where you think you are at the start of each loop step, so a drift fails fast and close to its cause.

Check yourself

Answer each one before you look. Multiple-choice questions mark your pick and let you try again; for open questions, answer aloud, then reveal and grade yourself honestly.

Q1
Why does the anonymous read test assert error is null and not only that data is empty?
Did you have it?
An empty result can also come from a broken key (401), a missing table, or a network failure. Only "no error and no rows" proves RLS is denying access.
Q2
Which single assertion in the journey is the regression test for the 8-digit bug?
Did you have it?
await expect(page.getByText("You're in!")).toBeVisible() after typing the real code: with a 6-digit cut, the code is rejected and the message never appears. (The wrong-code step with 8 zeros also exercises the 8-digit auto-submit.)
Q3
The journey's leaderboard check uses .lb-row.me, .pod with hasText: name. Why both?
Did you have it?
Depending on who else is on the live board, a score of 90 may land on the podium (rendered as .pod) or in the list (.lb-row.me).
Q4
Predict: someone changes the security spec's afterAll back to deleteTestUsers(). When does it fail, and how?
Did you have it?
Only when it overlaps with a running journey in another worker: that journey's user is deleted mid-test and a later step (often the submit) fails. It's intermittent, which is exactly what makes it dangerous.
Q5
Why is the second user in the journey created through supabase-js instead of the UI?
Did you have it?
It only needs to own a name. Creating it through the UI would add a second sign-in flow and minutes of runtime for no extra coverage.
Q6
What does "the board equals a copy sorted by score desc, then duration asc" not prove?
Did you have it?
That ties are ranked correctly (equal ranks), and that each player appears once at their best. The PGlite test covers those with controlled data.

Flashcards

See all 10 cards as a listfor a quick scan
  1. What does the journey fake, and what is real?
    Only "send code" is faked (no email); the code, verification, session and every database call are real.
  2. How is an email code obtained without email?
    Admin generateLink → properties.email_otp.
  3. Why assert error null on anonymous reads?
    To distinguish RLS denial (no error, no rows) from a broken key or missing table.
  4. Error codes: privilege, check, unique?
    42501, 23514, 23505.
  5. Why does the key check matter?
    Pasting the secret key into VITE_SUPABASE_ANON_KEY would ship it to every browser.
  6. What caused the Firefox journey to fail at submit?
    Another worker's cleanup deleted all e2e-bot- users, including the one in use.
  7. Rule for cleanup in parallel runs?
    Destroy only what you created; sweep by pattern only in global teardown.
  8. What caused the 8-minute wait for "Next"?
    An extra Next click after an auto-advancing answer skipped a question, so the loop reached the last question early.
  9. What does page.on("pageerror") add?
    Fails the journey on uncaught exceptions even if the next assertion happens to pass.
  10. Journey expected numbers?
    94 answered, 6 unanswered, score 90, 10 to review, 50/100 at the reload.

the deployed system diverging from its source files.

code run once after every worker has finished.

running a file's tests in order in one worker.
