L2.01

From PDFs to 130 questions: the data pipeline

Recipe card60 min
You need
L1.05 done; pdftotext (ships with Git for Windows; on macOS brew install poppler)
You'll produce
src/data/questions.json (130 questions), src/data/questions.ts, scripts/gen-seed.mjs, and the generated supabase/seed.sql + setup.sql

In two sentences: All of the app's value sits in 130 question-and-answer pairs taken from 12 PDFs and one web page. This lesson shows how we extracted them, how the data is shaped (ids, 0-based answers, notes), and the script that turns the JSON into SQL so the database and the app can never disagree.

By the end, without notes, you can

  1. Run pdftotext -layout and pick the answer key out of its output, including wrapped and malformed "Ans." lines.
  2. Explain the id scheme week*100 + n and why answers are 0-based indexes.
  3. Write questions.ts (types + derived constants) and gen-seed.mjs from memory, including SQL string escaping.
  4. Explain why questions.json is the single source of truth, and which test proves the SQL matches it.

2

The problem this solves

The exam asks only assignment questions, and those exist only as PDFs (weeks 0–11) and a SWAYAM page (week 12). The app needs them as structured data in two places: the browser (flashcards, quiz, list, test UI) and Postgres (grading). Typing them twice would guarantee drift. So we keep one JSON file and generate the SQL from it.

3

Concepts

3.1 pdftotext -layout: text that keeps its columns

Definition. pdftotext (from the Poppler tools) converts a PDF to plain text. With -layout it keeps the original spacing, so options stay on their own lines.

Why here. The assignment PDFs are text-based, not scans. That makes extraction exact. No OCR (image-to-text guessing) was needed for weeks 0–11.

How we used it.

Terminal1 line
for f in *.pdf; do pdftotext -layout "$f" "txt/${f%.pdf}.txt"; done
  • "$f" is quoted because a filename contains spaces (Assignement 3. Solution.pdf).
  • ${f%.pdf} is Bash for "$f with .pdf removed from the end".
  • Output: one .txt per week, about 4 KB each.

A real chunk of output (week 0):

Text7 lines
1) What is Psychology?    A. Just a social media trend    B. An art of living    C. A subject about human body    D. A study of cognitive processes & behavior          Ans. D= A study of cognitive processes & behavior

What can go wrong. The keys are not perfectly regular, and those irregularities are why we hand-checked every question:

7, Q6 Key says Ans. = humanistic (no letter) Matched the text to option c
10, Q7 The answer text wraps onto a second line The parser joins the next line (L4.01)

3.2 Week 12: questions in images, answers in HTML

There was no week-12 PDF. The user saved the SWAYAM assignment page with its assets. In that HTML:

  • each question was an image (a12q1.png … a12q10.png), and the A/B/C/D labels next to them had no text;
  • below each one was the platform's feedback: Accepted answer is followed by C..

So we read the ten images (their text is short and clear), and took the answers from the HTML by stripping tags and matching the pattern. The accepted answers were C D D B C D D A A B. A unit test re-checks this against the saved page (L4.01).

Side note. The page also showed the user's own submission. Q1 was marked wrong: they had picked multidimensional, but the accepted answer is unidimensional. That is why reading "Accepted answer", not "your answer", matters.

3.3 The id scheme: week * 100 + n

Definition. Question n (1–10) of week w gets id id=100w+n. So week 3 Q4 → 304, week 12 Q1 → 1201, week 0 Q1 → 1.

Why.

  • Stable. Adding question 11 to week 3 gives it 311 and changes no other id. A running counter (1…130) would shift every later id and silently break everyone's saved progress and attempts, which reference ids.
  • Readable. You can debug question_id = 507 in a database row without a lookup.
  • Reversible. w=⌊id/100⌋, n=idmod100, which is the app's numberInWeek.

3.4 Answers as 0-based indexes

answer: 3 means options[3], the fourth option (D). The UI shows letters with "ABCD"[answer]. The database stores the same integer, and submit_test compares integers. Using the letter would add conversions; using the text would break if we fixed a typo in an option.

4

Reading the real code

4.1 The one-off export (history)

The first artifact of the session was a single-file HTML flashcard page. Its script held a DATA array of {w, q, o, a, n?} objects. When we moved to React, this command converted it once, run with node -e from the project root:

JavaScript12 lines
const fs = require("fs");const h = fs.readFileSync("Psychology_of_Learning_Flashcards.html", "utf8");const js = h.split("<script>")[1].split("</script>")[0];const data = eval(js.split("DATA.forEach")[0].replace("const DATA =", "(").trim().replace(/;$/, "") + ")");const cnt = {};const out = data.map((d) => {  cnt[d.w] = (cnt[d.w] || 0) + 1;  const o = { id: d.w * 100 + cnt[d.w], week: d.w, q: d.q, options: d.o, answer: d.a };  if (d.n) o.note = d.n;  return o;});fs.writeFileSync("src/data/questions.json", JSON.stringify(out, null, 1));

Line notes:

  • L3: grab the text between <script> and </script>.
  • L4: keep only the array literal. Replacing const DATA = with ( and closing with ) turns […] into an expression that eval can return. eval runs arbitrary code. That was acceptable here only because we wrote that file ourselves. Never eval downloaded content.
  • L5–9: cnt[d.w] counts questions seen so far in each week, so the 1st of week 3 becomes 301, the 2nd 302 and so on. This is why the duplicated printed "6)" in week 1 doesn't matter.
  • L10: JSON.stringify(out, null, 1) pretty-prints with 1-space indentation, which keeps diffs readable.

It is no longer part of the build. questions.json is now edited directly.

4.2 src/data/questions.ts

TypeScript34 lines
import raw from "./questions.json"; export type Question = {  id: number; // week*100 + number, matches public.questions.id  week: number;  q: string;  options: string[];  answer: number; // 0-based  note?: string;}; export const QUESTIONS: Question[] = raw as Question[];export const BY_ID = new Map(QUESTIONS.map((q) => [q.id, q]));export const WEEKS = [...new Set(QUESTIONS.map((q) => q.week))].sort((a, b) => a - b);export const TEST_SIZE = 100; export const WEEK_TOPICS: Record<number, string> = {  0: "Intro to psychology",  1: "What is learning",  2: "Behaviourism & intelligence",  3: "Memory",  4: "Thinking & Bloom",  5: "Motivation",  6: "Emotional intelligence",  7: "Learning & instruction",  8: "Pedagogy",  9: "E-learning",  10: "Teaching & assessment",  11: "Social cognition",  12: "Sustainability",}; export const LETTERS = "ABCD";export const numberInWeek = (q: Question) => q.id % 100;

Line notes:

  • L1: Vite imports JSON as a plain JS value. TypeScript infers a wide type, so…
  • L12: …we assert Question[]. It is an assertion, not a check. The unit tests do the checking: every question has 2 or 4 options, a valid answer index, and so on.
  • L13L13 BY_ID: a Map from id to question, giving O(1) lookups. The test runner receives question_ids from the server and must find each question quickly (BY_ID.get(id)). Without it, every render would scan 130 items.
  • L14L14 WEEKS: new Set(...) removes duplicates and [...set] turns it back into an array. .sort((a, b) => a - b) sorts numerically. The default sort() compares strings, which would order [0, 1, 10, 11, 12, 2, …]. A real bug avoided.
  • L15L15 TEST_SIZE: shown in the UI text. The server has its own limit 100 (in SQL). They must match. A test checks start_test returns 100 ids.
  • L17L17–31 WEEK_TOPICS: Record<number, string> is an object type with number keys and string values. Shown on week tiles and the Study header.
  • L33L33 LETTERS: "ABCD"[i] turns an index into a letter, because strings are indexable.
  • L34L34 numberInWeek: the reverse of the id scheme.

4.3 scripts/gen-seed.mjs

JavaScript25 lines
// Regenerates supabase/seed.sql and supabase/setup.sql from src/data/questions.json.// Run after editing questions: npm run gen:sqlimport { readFileSync, writeFileSync } from "node:fs"; const questions = JSON.parse(readFileSync(new URL("../src/data/questions.json", import.meta.url), "utf8"));const lit = (s) => "'" + String(s).replace(/'/g, "''") + "'"; const rows = questions.map(  (q) => `  (${q.id}, ${q.week}, ${lit(q.q)}, ${lit(JSON.stringify(q.options))}::jsonb, ${q.answer})`); const sql = `-- Generated by scripts/gen-seed.mjs — ${questions.length} questions. Run after schema.sql.insert into public.questions (id, week, prompt, options, answer) values${rows.join(",\n")}on conflict (id) do update  set week = excluded.week, prompt = excluded.prompt, options = excluded.options, answer = excluded.answer;`; writeFileSync(new URL("../supabase/seed.sql", import.meta.url), sql); // one-shot file: schema + questions, for pasting into the Supabase SQL editorconst schema = readFileSync(new URL("../supabase/schema.sql", import.meta.url), "utf8");const banner = "\n\n-- =====================================================================\n-- Questions\n-- =====================================================================\n";writeFileSync(new URL("../supabase/setup.sql", import.meta.url), schema + banner + sql);console.log(`Wrote supabase/seed.sql and supabase/setup.sql (${questions.length} questions)`);

Line notes:

  • L3 node:fs: the node: prefix says "built-in module", so it can't be confused with an npm package called fs.
  • L5 new URL("../src/…", import.meta.url): resolve the path relative to this script's file, not the current working directory. Running node scripts/gen-seed.mjs from anywhere works. A plain "src/…" would break if run from scripts/.
  • L6 lit() builds a SQL string literal. In SQL, a quote inside a string is written as two quotes: Maslow's → 'Maslow''s'. /'/g is a regex with the global flag, so every quote is replaced, not only the first. Without this, the first apostrophe would end the string and the rest would be parsed as SQL. That is a syntax error at best, and SQL injection at worst.
  • L9 options are stored as JSON text, then cast with ::jsonb (binary JSON), so Postgres validates it.
  • L12–17 one multi-row insert … values (…), (…), … statement. on conflict (id) do update makes the seed idempotent: re-running it updates rows instead of failing on duplicate keys. So you can fix a typo, regenerate and paste again.
  • L22–24 setup.sql = schema.sql + banner + seed, so the user pastes one file into the Supabase SQL editor.
  • package.json has "gen:sql": "node scripts/gen-seed.mjs", so npm run gen:sql runs it.

Running and testing

Terminal11 lines
npm run gen:sql# Wrote supabase/seed.sql and supabase/setup.sql (130 questions) npm run test:unit# ✔ there are 130 questions, 10 per week, weeks 0–12# ✔ ids are unique and follow week*100 + n# ✔ every question has text, 2 or 4 distinct options and a valid answer# ✔ supabase/seed.sql is in sync with questions.json# ✔ week 0 answers match 00.Assignement_Psy.pdf   … (12 PDF checks)# ✔ week 12 answers match the SWAYAM accepted answers# ℹ tests 17  ℹ pass 17  ℹ fail 0

What each proves:

  • Shape tests catch a missing option or a bad index the moment you edit the JSON.
  • "seed.sql is in sync" catches editing the JSON and forgetting npm run gen:sql.
  • PDF checks recompute every answer from the official keys. The week-12 check re-reads "Accepted answer is X" from the saved page.
  • We also proved the tests can fail. We changed one answer on purpose; two tests failed; we restored it. This is a mutation check, taught in L4.01.
7

Bug journal

Incident ticket · #01

Official key letter contradicts its own text (week 6, Q7)

Fixed
  1. Symptom
    Ans. a= all of the given, but option a is "optimism" and "all of the given" is option d.
  2. Diagnosis
    We compared the letter and the text for all 120 PDF answers. Only this one disagreed. Week 7 Q6 had no letter at all (Ans. = humanistic).
  3. Root cause
    A typo in the official answer key.
  4. Fix
    Trust the text: "answer": 3 plus "note": "The answer key prints \"a = all of the given\"; the answer text is \"all of the given\" (option d).". The card's back face shows the note so students aren't confused by the PDF.
  5. Lesson
    When a source contradicts itself, decide which part is authoritative (the text here), record the decision in the data, and make the test compare on the authoritative part. Our PDF test compares texts, never letters.

Test-tooling incident (the PDF tests were silently skipped because pdftotext -v exits non-zero) belongs to the test code and is told in L4.01.

Discussionreveal

Flashcards

See all 8 cards as a listfor a quick scan
  1. What is the id of week 12, question 1?
    1201 (100·12 + 1).
  2. Why not sequential ids?
    Inserting a question would shift later ids and corrupt saved progress and attempts.
  3. How do you escape a quote inside a SQL string?
    Double it: ''.
  4. Why new URL(path, import.meta.url) in a Node script?
    Resolves relative to the script file, independent of the working directory.
  5. Why does the seed use on conflict do update?
    Idempotent: you can re-run it after fixing data.
  6. Which part of a contradictory key did we trust, and how is it recorded?
    The answer text; recorded as answer: 3 plus a note on the question.
  7. What catches "edited JSON, forgot gen:sql"?
    The unit test "supabase/seed.sql is in sync with questions.json".
  8. Why BY_ID?
    O(1) lookup of questions by the ids the server sends.

Glossary

Build artifact
a file produced by a script (here seed.sql), never edited by hand.
Idempotent
safe to run repeatedly with the same result.
jsonb
Postgres's binary JSON type.
Mutation check
deliberately breaking code or data to prove a test fails.
OCR
optical character recognition (not needed here).
Poppler
PDF tools including pdftotext.
Source of truth
the single authoritative copy of data.
SQL injection
user text being executed as SQL because of missing escaping.
