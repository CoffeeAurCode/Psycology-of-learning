L3.01

Under the hood: the security model

Recipe card70 min
You need
L1.04 (RLS, roles, keys, JWT), L2.02 (tables and policies), L2.03 (the four functions)
You'll produce
A threat model for the app, a request-by-request explanation of how Postgres decides what each caller may do, three verified foot-guns, and one real weakness with a proposed fix

In two sentences: The browser is hostile territory: anyone can open DevTools, copy the public key and call the database API directly, so every rule that matters lives in Postgres, as row-level security policies and security definer functions. This lesson follows a request from the browser to the row, attacks the app the way a curious student would, proves which attacks fail and why, and is honest about the one that still works.

Session 2 update

Sign-in is now Google via Supabase (OAuth with PKCE), so §4.2's guessing maths for 8-digit email codes no longer applies to the live app. Everything after sign-in (JWT, auth.uid(), RLS, definer functions) is unchanged. The new sign-in's threat model is in L3.06.

By the end, without notes, you can

  1. Draw the path of an API request from supabase-js to a Postgres row, naming where the role, the user id and each policy are applied.
  2. Predict the result (rows, empty, or which error code) of ten attacks, and explain each from the policies and grants.
  3. Explain three Postgres foot-guns: tables with RLS off, the default EXECUTE grant to PUBLIC, and pg_temp in a definer's search path, and how to detect each.
  4. State what the server can and cannot guarantee about a leaderboard score, and design a fix for the instant-submit weakness.

  1. "attempts: read own" (for select using (auth.uid() = user_id)). With no insert/update policies, clients can't write the table at all; only the definer functions start_test and submit_test can.

2

The problem this solves

The naive app checks permissions in JavaScript: "only show the submit button if the user is signed in", "compute the score in the browser and save it". Both are decorations. The JavaScript runs on the attacker's machine. They can edit it, skip it, or never load it and call the API with curl.

The idea: treat the API as public and put the rules where the attacker can't reach: inside the database, evaluated for every query, using an identity the attacker can't forge (a signed JWT).

3

Concepts: what happens between your code's lines

3.1 One request, from browser to row

Take supabase.from("card_progress").select("*") sent by a signed-in student. Step by step:

Three facts make this safe:

  • The role comes from the JWT, and the JWT is signed by Supabase Auth. Editing the payload ("role": "service_role") breaks the signature; PostgREST rejects it with 401.
  • auth.uid() reads the sub claim from the request settings PostgREST set. The client never sends a user id the server trusts; it sends a token from which the server derives it.
  • RLS is added inside Postgres, after the grant check and before any row leaves. The query the client wrote is SELECT *; the query that runs is effectively SELECT * … WHERE auth.uid() = user_id.

3.2 How RLS combines policies

  1. Definition. A policy is a boolean expression attached to a table, a command (select, insert, update, delete, all) and optionally a role.
  2. The rules Postgres applies:
    • RLS enabled with no policy for a command → that command sees or changes nothing (default deny).
    • USING (expr) filters which existing rows are visible to select, update and delete.
    • WITH CHECK (expr) tests new row values on insert and update. Failing it raises error 42501 "new row violates row-level security policy".
    • Several permissive policies for the same command are ORed.
    • An update needs a row to pass USING (to be targeted) and the new version to pass WITH CHECK.
  3. Consequences you can observe:
    • A blocked select returns [], not an error. That's why the live tests assert data equals [].
    • A blocked update or delete matches zero rows: it succeeds and changes nothing (data: [], error: null).
    • A blocked insert errors with 42501.
Table select insert update delete
questions ✗ (no policy) ✗ ✗ ✗
profiles own row own id only own row, stays own ✗ (no policy; cascades when the auth user is deleted)
test_attempts own rows ✗ ✗ ✗
card_progress own rows own user_id own, stays own own

3.3 security definer: the waiter who can enter the kitchen

A normal (security invoker) function runs with the caller's role, so RLS still applies inside it. A security definer function runs with the role of its owner. In Supabase that's postgres, which owns the tables, and table owners are not subject to RLS (unless a table uses force row level security). So inside submit_test the code can read the questions answer key that the caller can't.

That power is exactly why each definer function must:

  • re-check identity itself: auth.uid() still returns the caller's id inside a definer function, because it reads the request's claims, not the current role;
  • return only safe data: get_leaderboard reads every attempt, but returns names, scores and times, never emails or answer arrays;
  • pin its search path (§3.5);
  • be callable only by the right roles (§3.4).

3.4 Grants come before policies

Before RLS runs, Postgres checks privileges: may this role touch this table or call this function at all?

  • Supabase grants table privileges on public to anon and authenticated by default, and relies on RLS for row-level gating. (The DB tests reproduce this with grant all on all tables in schema public to anon, authenticated.)
  • Postgres grants EXECUTE on every new function to PUBLIC (every role) by default. A definer function you forget to lock down is callable by anon.

So the schema ends with:

SQL8 lines
revoke all on function public.start_test()                from public, anon;revoke all on function public.submit_test(uuid, int[])    from public, anon;revoke all on function public.get_my_stats()              from public, anon;revoke all on function public.get_leaderboard(int)        from public;grant execute on function public.start_test()             to authenticated;grant execute on function public.submit_test(uuid, int[]) to authenticated;grant execute on function public.get_my_stats()           to authenticated;grant execute on function public.get_leaderboard(int)     to anon, authenticated;

An anon call to start_test then fails before the function body runs, with 42501 "permission denied for function start_test". The function's own if uid is null check is a second line of defence.

3.5 The search path inside a definer function

Unqualified names (questions, profiles) are looked up along search_path. If a caller could put a look-alike questions table earlier on the path, the definer function would grade against their table. set search_path = public on the function fixes the path to public for the duration of the call.

There is a subtlety, verified in PGlite for this lesson: the session's temporary schema pg_temp is still searched first for tables, even when it isn't listed. A session that can run raw SQL could create temp table questions (…) and shadow the real one:

Text3 lines
create temp table questions (…);  -- emptyselect start_test();→ ERROR: No questions in the database yet (run seed.sql)

The definer function read the empty temp table. Through Supabase's HTTP API nobody can run create temp table (PostgREST only exposes table endpoints and functions), so this isn't exploitable here. The fully hardened forms are set search_path = public, pg_temp (temp searched last) or set search_path = '' with every name schema-qualified (public.questions). The Postgres docs recommend the first; Supabase's linter recommends the second.

4

The math

4.1 Why a JWT can't be edited

A JWT is base64url(header) . base64url(payload) . signature, where

signature=Signk​(base64url(header)∥.∥base64url(payload))
  • k is a key only Supabase holds (an HMAC secret or a private signing key).
  • Changing one character of the payload changes the signed message, so the old signature no longer verifies.
  • Producing a valid new signature without k means breaking HMAC-SHA256 or ECDSA, which is computationally infeasible (for HMAC-SHA256, on the order of 2256 guesses for the key).

So the client can read its token (the payload is only encoded, not encrypted: paste it into a JWT decoder and you'll see sub, role, exp), but can't change it.

4.2 How safe is an 8-digit email code?

Let d be the number of digits, so there are 10d codes, and an attacker gets k guesses before the code expires or rate limits stop them. With distinct guesses,

P(success)=10dk​
  • Why: each distinct guess eliminates one code; the real code is equally likely to be any of the 10d.
d k=100 k=10,000
6 10−4 (0.01%) 10−2 (1%)
8 (this project) 10−6 10−4 (0.01%)

Supabase rate-limits OTP verification and codes expire, so realistic k is small. Two extra digits make guessing 100× harder for the same budget. (The cost was the 8-digit sign-in bug of L2.07a: the app has to accept whatever length the project sends.)

Reveal A6–A10reveal

  • A9: data: []. A's rows are invisible to B under USING (auth.uid() = user_id), so zero rows are deleted.
  • A10: rows with rank, user_id, display_name, score, total, duration_ms, attempts, submitted_at, and no email. The definer function reads profiles for everyone but returns only the public name. (user_id is a random UUID; it identifies a row but reveals nothing.)

7

Bug journal: four failure modes, all verified

Incident ticket · #01

Known foot-gun · A new table with RLS off is public

Fixed
  1. Symptom
    You add public.announcements for a "news" banner and forget enable row level security. Anyone can now run curl "$URL/rest/v1/announcements?select=*" -H "apikey: <publishable key>" and read every row, including drafts, and write to it. Reproduced in PGlite as role anon:
    Text2 lines
    anon reads: [{"id":1,"body":"secret draft"}]anon reads questions: 0
  2. Diagnosis
    Nothing errors; that's the danger. The only signals are a catalog query, Supabase's Security Advisor ("RLS disabled in public"), or a test that reads every table as anon.
  3. Root cause
    Supabase grants table privileges to anon and authenticated by default. With RLS off, privileges are the only gate, and they say yes.
  4. Fix and detection
    Diff3 lines
    create table public.announcements (id int primary key, body text);alter table public.announcements enable row level security;create policy "announcements: read" on public.announcements for select using (true);  -- public read, no writes
    The query that finds every unprotected table (empty for this project's schema; it listed announcements once the table was added):
    SQL3 lines
    select c.relnamefrom pg_class c join pg_namespace n on n.oid = c.relnamespacewhere n.nspname = 'public' and c.relkind = 'r' and not c.relrowsecurity;
  5. Lesson
    Make "every public table has RLS" a test, not a habit: run this query in the DB test suite and assert it returns no rows. The live test "cannot read the answer key or any private table" only covers the tables it names; the catalog query covers tables nobody has written a test for yet.
Incident ticket · #02

Known foot-gun · Functions are executable by everyone by default

Fixed
  1. Symptom
    A helper function you added to public for internal use is callable by any visitor: rpc("helper") works with only the publishable key. Verified in PGlite: as anon, select public.helper() returned 42.
  2. Diagnosis
    You never granted anything. Postgres did: new functions get EXECUTE for PUBLIC. PostgREST exposes every function in the exposed schema as /rest/v1/rpc/<name>.
  3. Root cause
    Default privileges. For a security definer function this is a full RLS bypass for whatever the function does.
  4. Fix
    Diff2 lines
    create function public.helper() … security definer …;revoke all on function public.helper() from public, anon, authenticated;   -- nobody via the API
    Or put internal helpers in a schema the API doesn't expose (for example private).
  5. Lesson
    Every create function in an exposed schema is followed by its revoke/grant lines. The live test "cannot start, submit or read stats" asserts error code 42501 for each function anon must not call.

7.3 Hardening note · pg_temp is searched first

Verified in §3.5: inside a definer function with set search_path = public, a temp table named questions shadowed the real one. Not exploitable through the API (no raw SQL), so the schema is safe as deployed. If the database is ever reachable by untrusted SQL clients (a reporting tool, a shared Postgres), change each function to set search_path = public, pg_temp or set search_path = '' with schema-qualified names.

Incident ticket · #03

Found while writing this lesson · A script can top the leaderboard

Fixed
  1. Symptom
    A perfect, instant attempt is accepted and ranked first. Reproduced in PGlite with the real setup.sql:
    Text1 line
    instant submit: {"score":100,"total":100,"duration_ms":12,"rank":1}
    The DB test suite's own play() helper does the same thing for every test, in milliseconds, and nothing objects.
  2. Diagnosis
    Each check in §5 holds: the score is computed by the server from the submitted answers, and the time is measured by the server. What the server cannot know is who or what chose the answers. And the answers aren't secret: the flashcards ship all 130 questions with their answers in the JavaScript bundle (src/data/questions.json), by design, because studying them is the point of the app. So a 20-line script with a real session can call start_test, look up all 100 answers locally, and call submit_test within a fraction of a second.
  3. Root cause
    The leaderboard ranks by score, then time, and the system protects the integrity of the measurement (no forged rows, no edited scores, no client clock) but has no notion of a plausible attempt. RLS answers "may this user write this?", not "is this a human taking a test?".
  4. Fix
    (proposed, not applied to the app):
    Diff5 lines
      dur := (extract(epoch from (clock_timestamp() - a.started_at)) * 1000)::int;  -- 100 questions can't be read and answered by a person in under ~2 minutes  if dur < a.total * 1200 then    raise exception 'Too fast to be a real attempt' using errcode = 'P0001';  end if;
    A softer variant stores the attempt but excludes it from get_leaderboard (where t.duration_ms >= t.total * 1200). Either way, the DB test helper must then fake time (for example by back-dating started_at as the test owner). Stronger options, in increasing cost: a per-user cooldown between attempts, CAPTCHA on start_test, or hiding the answer key from the bundle (which would break offline flashcards).
  5. Lesson
    Write down what the server guarantees and what it doesn't. Here: "scores are computed server-side and can't be forged or edited; durations are server-measured; we do not detect automated or assisted answering." Then decide whether the gap matters for this audience (a class leaderboard for a MOOC) before paying for a fix.

Check yourself

Answer each one before you look. Multiple-choice questions mark your pick and let you try again; for open questions, answer aloud, then reveal and grade yourself honestly.

Q1
A student runs supabase.from("test_attempts").update({ score: 100 }).eq("id", myAttemptId) and gets { data: [], error: null }. They conclude the update "worked". What really happened?
Did you have it?
Nothing changed. With RLS on and no update policy, no row passes the (absent) USING clause, so the update targets zero rows and returns no error. Only a failing WITH CHECK or insert raises 42501.
Q2
Predict: inside get_leaderboard (security definer), what does auth.uid() return when anon calls it?
Did you have it?
null. auth.uid() reads the request's JWT claims, not the current role. Definer changes the role to the owner but not the request claims. (That's why get_my_stats can use auth.uid() to find the caller's row.)
Q3
You add create policy "attempts: update own" on test_attempts for update using (auth.uid() = user_id); to let users rename attempts. What did you just break?
Did you have it?
Score integrity. Without a WITH CHECK restricting columns, and since policies are row-level not column-level, a user can now update score and duration_ms on their own rows. Column-level protection needs column privileges (revoke update (score, duration_ms) …) or a definer function instead.
Q4
Someone edits their JWT payload from "role":"authenticated" to "role":"service_role" in DevTools. What happens?
Did you have it?
PostgREST verifies the signature over the header and payload; the edited payload no longer matches, so the request is rejected (401). Without the signing key the student can't produce a valid signature.
Q5
Why can't the instant-submit weakness (7.4) be fixed with another RLS policy?
Did you have it?
RLS decides who may read or write which rows. The scripted submission comes from the legitimate owner, through the legitimate function, with correct data. Detecting "not a human" needs a rule about the attempt itself (a minimum duration, a cooldown, a CAPTCHA), inside submit_test or in front of it.
Q6
Which of these exposes data to anonymous visitors? (a) a table with RLS on and no policies; (b) a table with RLS off; (c) a security definer function granted to anon that returns select * from profiles.
Did you have it?
(b) and (c). (a) is default deny. (b) is open via default grants. (c) bypasses RLS and returns whatever it selects: definer functions must return only what's safe for their callers.

Flashcards

See all 12 cards as a listfor a quick scan
  1. Where do the role and user id of an API request come from?
    The signed JWT. PostgREST verifies it, sets the role, and stores the claims; auth.uid() reads sub.
  2. RLS on, no policy for select: what does a select return?
    An empty result, no error (default deny).
  3. What does a blocked update return?
    Success on zero rows (data: [], no error).
  4. USING vs WITH CHECK?
    USING picks which existing rows are visible/targetable; WITH CHECK validates the new row on insert/update.
  5. Why can a definer function read the answer key?
    It runs as the owner of the tables, and owners aren't subject to RLS.
  6. What must every definer function do itself?
    Check identity (auth.uid()), return only safe columns, pin search_path, and be granted only to the right roles.
  7. Why revoke … from public?
    Postgres grants EXECUTE on new functions to PUBLIC by default.
  8. Error code for "permission denied" / RLS insert violation?
    42501. Check constraint 23514, unique 23505.
  9. How do you find tables with RLS off?
    pg_class where relkind = 'r', schema public, not relrowsecurity; or Supabase's Security Advisor.
  10. What does set search_path = public not prevent?
    Temp-table shadowing: pg_temp is still searched first unless listed last.
  11. P(guess an 8-digit code in k tries)?
    108k​.
  12. What doesn't the server guarantee about a score?
    That a human chose the answers unaided. The key is public study material, so a script can submit a perfect paper instantly.

Glossary

Claims
the fields in a JWT payload (sub, role, exp).
Default deny
with RLS on, nothing is allowed without a policy.
Definer / invoker
whose privileges a function runs with: its owner's, or its caller's.
Grant / privilege
permission for a role to use an object, checked before RLS.
JWT
a signed token carrying claims.
OTP
one-time password.
pg_temp
the per-session temporary schema.
Permissive policy
a policy combined with others by OR.
PostgREST
the server that turns HTTP requests into SQL under the caller's role.
PUBLIC
the pseudo-role meaning every role.
Rate limit
a cap on requests per time window.
Search path
the list of schemas searched for unqualified names.
Threat model
assets, attackers, entry points and the defences for each.
Trust boundary
the line beyond which input can't be trusted.
