The ranked test I: intro, attempt storage and starting a test

In two sentences: Before the runner exists, we need a durable record of the attempt in the browser (so a reload doesn't lose 50 answers) and an intro screen that walks every kind of user to the right next step. This lesson builds both and wires the "Start test" button to start_test.

2

The problem this solves

A 100-question test takes 12–25 minutes on a phone. In that time a call comes in, the browser gets killed in the background, or the user swipes away by accident. Losing everything would be cruel. So the attempt lives in localStorage from the first second. And users arrive in many states (signed out, no name yet, test half done), each needing a different button.

3

Concepts

3.1 Two clocks, two jobs

Field Set by Used for Trusted for ranking?
started_at Postgres now() in start_test The real duration in submit_test Yes
client_started Date.now() in the browser at start The on-screen timer (now − client_started) No

Why not show now − started_at in the UI? Because the phone's clock and the server's clock differ. A phone 40 seconds fast would show the timer starting at 0:40. The UI timer measures from the phone's own start moment, so it always starts at 0:00, while the server measures the official time.

3.2 Client-side expiry mirrors the server

The server refuses submits older than 3 hours. If the browser kept a 5-hour-old attempt, the user would answer 100 questions and then get "This test expired" on submit. So loadAttempt() discards attempts older than 3 hours (by the client clock) before offering "Resume". Mirroring a server rule on the client is a UX courtesy; the server's check is the real one.

3.3 Nested routes

App.tsx routes /test/* to <Test/>. Inside, <Routes> resolves paths relative to /test:

  • index (exactly /test) → Intro
  • run → Run
  • result → ResultView
  • * (anything else under /test/) → Intro

Because AnimatedRoutes keys by the first segment (test), moving between these doesn't replay the page transition (L2.05).

function Intro() {  const { session, profile, ready } = useAuth();  const nav = useNavigate();  const [busy, setBusy] = useState(false);  const [err, setErr] = useState<string | null>(null);  const pending = loadAttempt();  const last = load<Result | null>(RESULT_KEY, null);   const start = async () => {    setBusy(true);    setErr(null);    const { data, error } = await supabase.rpc("start_test");    setBusy(false);    if (error) return setErr(friendlyError(error));    const d = data as { attempt_id: string; question_ids: number[]; started_at: string };    const a: Attempt = {      ...d,      client_started: Date.now(),      answers: d.question_ids.map(() => null),      flags: [],      pos: 0,    };    save(ATTEMPT_KEY, a);    haptic(20);    nav("/test/run");  };
  • L6–7pending and last are read during render. Cheap (a storage read) and always current. They don't need to be state, because nothing on this screen changes them except start(), which navigates away.
  • L12supabase.rpc("start_test") sends POST /rest/v1/rpc/start_test with the user's token (L1.02 §8).
  • L14Errors through friendlyError. Possible messages: "Choose a display name first" (shouldn't happen, since the UI gates on profile), "The database isn't set up yet…" (setup.sql not run, seen live before the user ran it), network errors.
  • Building the local attempt:
    • ...d spreads the server fields (attempt_id, question_ids, started_at);
    • client_started: Date.now() (§3.1);
    • answers: d.question_ids.map(() => null): 100 nulls, one per question.
  • Save before navigating, so Run finds it in storage on mount.
  • L24haptic(20): a satisfying "go" buzz.
  • Starting again while an attempt is pending ("Start over") calls the same start(). The server deletes the old open attempt, and the new one overwrites the local key.

Why this design

Decision Alternatives Why this one Trade-off Choose differently when
Attempt in localStorage Server-side autosave of each answer Survives reloads and offline moments; zero network per answer Not resumable on another device Cross-device resume → save answers to the server
Two clocks Server time only The UI timer starts at 0:00 regardless of clock skew Two fields —
Client-side 3 h expiry None Avoids a wasted attempt that would fail on submit Duplicates the server rule —
Gate on name before starting Ask for a name at submit No ranked result without a board identity One more step for newcomers —

Q1
A user's phone clock is 2 minutes fast. What does the on-screen timer show right after starting? What duration does the leaderboard record for a 15-minute test?
Did you have it?
The timer shows 0:00 (it measures from the phone's own start). The leaderboard records about 15:00 (server now() minus server started_at). Clock skew affects neither.
Q2
Why are answers and flags indexed by position rather than question id?
Did you have it?
submit_test takes an array aligned with question_ids; positions also match the "Question N of 100" UI and the grid.
Q3
You reorder the ternary to check pending before session. Who is harmed?
Did you have it?
Someone who signed out mid-test: they'd see "Resume", answer more, and then fail at submit (no session, so the RPC is denied).
Q4
A 4-hour-old attempt is in storage. What does the intro show?
Did you have it?
"Start test". loadAttempt deleted the stale attempt and returned null.

Flashcards

See all 6 cards as a listfor a quick scan
  1. Which start time ranks you?
    started_at from Postgres now(); client_started only drives the on-screen timer.
  2. Why store the attempt in localStorage immediately?
    So reloads, background kills or accidental exits don't lose answers.
  3. Why mirror the 3 h expiry on the client?
    To avoid offering "Resume" for an attempt the server would reject on submit.
  4. What does path="run" mean under /test/*?
    /test/run; nested route paths are relative.
  5. Order of the intro's checks?
    Configured → auth ready → session → profile → pending attempt → start.
  6. What does Result carry besides the server's fields?
    The attempt's question_ids and answers, for the review list.
