L4.07

Test it VII: accessibility audits, Lighthouse and flaky-test forensics

Recipe card65 min
You need
L3.04 (contrast maths, what axe can and can't check), L3.05 (Lighthouse metrics), L4.03–L4.06 (the suite and its bugs)
You'll produce
tests/e2e/a11y.spec.ts (63 lines) from a blank file, a repeatable Lighthouse procedure with a script that reads its JSON, and a forensic method for any failing or flaky test, applied to every flake in this series

In two sentences: The accessibility spec turns axe-core into a gate: three tests per theme scan every screen and state, and fail on any serious or critical violation with a one-line summary per rule. The rest of the lesson is about trust: how to run Lighthouse so its numbers mean something, and how to work out why a test fails or flakes, a method distilled from eleven real incidents in this build, including one where the "frozen app" was actually a development server and a throttled background tab.

By the end, without notes, you can

  1. Write the accessibility spec from memory: theme forcing, the scan helper, the three scan tests, and the waits.
  2. Run Lighthouse on mobile and desktop and extract scores, metrics and failing audits from its JSON with a script.
  3. Apply a forensic checklist to a failing test: reproduce, classify (deterministic, timing, environment, shared state), gather evidence, fix the cause.
  4. Recognise environment artefacts (dev server reloads, background-tab throttling, cold builds) and remove them from the test setup.

2

The problem this solves

Two kinds of test results are hard to act on:

  • Audits with hundreds of findings (axe, Lighthouse) are ignored unless they're turned into a short, specific pass/fail.
  • Failures that come and go erode trust in the whole suite. After the third "just rerun it", real failures get rerun too.

The idea: make audits gates with readable summaries, and treat every flaky or confusing failure as a bug with a cause, found by a method rather than by retrying.

3

Concepts

3.1 axe in Playwright

@axe-core/playwright injects axe-core into the page and runs its rules against the current DOM. new AxeBuilder({ page }).withTags([...]).exclude(selector).analyze() returns { violations, passes, incomplete, … }. Each violation has an id (the rule, e.g. color-contrast), an impact (minor, moderate, serious, critical) and nodes (each failing element, with target selectors and a failureSummary).

3.2 Lighthouse from the command line

npx lighthouse <url> --output=json --output-path=report.json runs a full audit in a headless Chrome and writes a JSON report: categories.<name>.score (0–1), audits.<id> with score, displayValue and details.items (the evidence: URLs, bytes, milliseconds). --preset=desktop switches the throttling and screen.

3.3 Four kinds of failure

Kind Signature Examples in this series
Deterministic Fails every time, same line pdftotext -v skips (L4.01); the 8-digit sign-in bug; the tab-bar overlap on iPhone SE
Timing Fails on slower engines or under load; passes with an added pause The 1 ms swipe (L4.04); the quiz reading the sliding card (L4.05); the extra "Next" (L4.06); scans mid-fade
Shared state Passes alone, fails in the full run The cleanup race between workers (L4.06)
Environment Depends on how and where it runs, not on the code Git Bash path conversion (L4.03); HTTP tests pointed at production (L4.03); the dev server and background tab (§7)

Reading the real code: tests/e2e/a11y.spec.ts

4.1 The scan helper (lines 1–14)

TypeScript14 lines
// Automated accessibility checks (axe-core, WCAG 2.1 A/AA) on every screen, both themes.import { test, expect, type Page } from "@playwright/test";import AxeBuilder from "@axe-core/playwright";import { QUESTIONS, goto } from "./support"; async function scan(page: Page, label: string) {  const r = await new AxeBuilder({ page })    .withTags(["wcag2a", "wcag2aa", "wcag21a", "wcag21aa"])    .exclude(".splash")    .analyze();  const bad = r.violations.filter((v) => v.impact === "serious" || v.impact === "critical");  const summary = bad.map((v) => `${v.id} (${v.impact}): ${v.nodes.length}× e.g. ${v.nodes[0]?.target.join(" ")} — ${v.nodes[0]?.failureSummary?.split("\n")[1]?.trim()}`);  expect(summary, `${label}: serious/critical accessibility issues`).toEqual([]);}
  • Tags: WCAG 2.0 and 2.1, levels A and AA. axe has other rule sets (best practices, WCAG 2.2, experimental); these four match the legal and common target.
  • .exclude(".splash"): the first-load splash is decorative and fading; it's also aria-hidden once it starts fading.
  • Only serious and critical fail the test. Minor and moderate findings exist (for example "region" landmarks) but don't block; the summary format makes adding them a one-word change.
  • The summary line per rule: id (impact): N× e.g. <first node's selector> — <first line of its failure summary>. Compact enough to read in a terminal, specific enough to act on. Its limitation, showing only the first node, is exactly what hid two of the contrast failures until the first ones were fixed (L3.04 §5).
  • toEqual([]) with a label: on failure, Playwright prints the received array, so the summary lines are the error message.

  • Main screens: the five routes, 700 ms after each navigation (the page transition is ~0.52 s; the rest is margin for entry animations).
  • States, not just pages: the flashcard back (a dark surface with its own colours), quiz feedback (green and red options), and list search with highlights. Each state has colours the default page doesn't.
  • The runner from injected state (the L4.05 technique): an attempt with 3 answers and 1 flag at question 3, and a result with mixed answers. Then the runner, the question grid (sheet), and the results page after 2 s (count-up, mascot and mood line all finished).
  • Coverage: 3 tests×2 themes×9 projects=54 scan runs, and 11 distinct screen states per theme.

5.1 The procedure

Terminal8 lines
npm run buildnpx vite preview --port 4174 --strictPort --host 127.0.0.1 &      # the production buildnpx -y lighthouse@12.8.2 http://127.0.0.1:4174/ --quiet --chrome-flags="--headless=new" \    --output=json --output-path=lh/mobile-home.jsonnpx -y lighthouse@12.8.2 http://127.0.0.1:4174/ --preset=desktop --quiet --chrome-flags="--headless=new" \    --output=json --output-path=lh/desktop-home.jsonnpx -y lighthouse@12.8.2 https://psychology-of-learning-nptel.vercel.app/ --quiet --chrome-flags="--headless=new" \    --output=json --output-path=lh/mobile-prod.json
  • Pin the version (lighthouse@12.8.2): scoring curves change between major versions, so comparisons across versions are meaningless.
  • Headless Chrome: a visible window that goes to the background gets throttled (§7).
  • Same build, same machine, nothing else running for before/after comparisons; run three times and take the median.

5.2 Reading the JSON with a script

The session's summary script, as a standalone file:

Python13 lines
# lhsum.py — usage: python lhsum.py lh/*.jsonimport json, sys, osfor f in sys.argv[1:]:    d = json.load(open(f, encoding="utf-8"))           # UTF-8: reports contain non-ASCII    c, a = d["categories"], d["audits"]    dv = lambda k: a[k]["displayValue"].replace("\xa0", " ")    print(os.path.basename(f).ljust(16),          " ".join(f"{k}={round(v['score'] * 100)}" for k, v in c.items()),          "| FCP", dv("first-contentful-paint"), "LCP", dv("largest-contentful-paint"),          "CLS", dv("cumulative-layout-shift"), "TBT", dv("total-blocking-time"))    weak = [k for k, v in a.items() if v.get("score") is not None and v["score"] < 0.9            and v.get("scoreDisplayMode") in ("binary", "numeric", "metricSavings")]    print("   below 0.9:", ", ".join(weak))
  • L4encoding="utf-8": the first version of this script crashed on Windows with UnicodeDecodeError: 'charmap' codec can't decode byte 0x9d, because Python's default encoding there is cp1252 and the report contains non-ASCII characters. Always open JSON reports as UTF-8.
  • L6\xa0: Lighthouse's display values use a non-breaking space ("2.1\xa0s").
  • "below 0.9" lists the audits worth reading. Then read audits[id].details.items for the evidence (which URL, how many bytes or ms).

5.3 Why Lighthouse isn't in the test suite

Lab scores vary by machine load, so a hard threshold ("performance ≥ 90") would flake on a busy laptop or CI runner. The suite instead tests the causes Lighthouse flagged, deterministically: images are WebP with sizes (HTTP spec checks content types), hashed assets are immutable (on production), accessibility is gated by axe. Lighthouse is run by hand around performance work, with the procedure above. (A CI budget with tolerances, using Lighthouse CI, is the step up; see Go further.)

Running and testing

Terminal4 lines
npx playwright test tests/e2e/a11y.spec.ts                                   # 54 runsnpx playwright test tests/e2e/a11y.spec.ts --project=galaxy-s9-320 -g "dark"npx playwright test -g "quiz" --retries=0 --repeat-each=10 --project=iphone-13   # hunt a flakenpx playwright show-trace test-results/<folder>/trace.zip
  • L3--repeat-each=10 runs each selected test 10 times: the fastest way to turn "sometimes" into a rate (3/10 fails is a timing bug; 10/10 is deterministic).
  • --workers=1 isolates shared-state problems: if a flake disappears with one worker, look for cross-test interference.
  • The trace shows each action with a DOM snapshot before and after, the network log and the console. Most timing bugs are visible as "the assertion read the DOM one snapshot too early".

Bug journal

Incident ticket · #01

Vite's reload loop plus background-tab throttling looked like a frozen app

Fixed
  1. Symptom
    During the first hands-on check in a real Chrome window (driven through a browser extension), the app seemed to freeze after a swipe: the "AGAIN" stamp stayed half-visible and the card didn't move on; the page still reported the splash as present ("splash": true). A later command to the tab failed outright:
    Text2 lines
    Failed to execute JavaScript: CDP sendCommand "Runtime.evaluate" timed out after 45000ms on tab 1133474601.The renderer may be frozen or unresponsive.
  2. Diagnosis
    • Hypothesis: an infinite render loop in the app. The console did show a real bug, destroy is not a function (the useEffect returning a Promise of L2.05), which was fixed. The "freeze" continued after the fix.
    • What else was in the console? Repeated [vite] connecting... / [vite] connected. lines: the dev server's live-reload socket dropping and reconnecting, reloading modules under the running page.
    • Why did animations stop? The Chrome window was in the background while the tests ran. Chrome stops requestAnimationFrame in hidden tabs and throttles their timers, so Motion's springs, the stamp fade and the splash's timers all paused. The app wasn't frozen; its clock was.
    • Taking screenshots with headless Chrome of a production build instead: both swipe directions worked, and the stamp only "froze" when the tab was hidden.
  3. Root cause
    Two environment artefacts at once: a development server that reloads code mid-test, and a browser that deliberately starves background tabs of frames and timers. Neither exists for a user looking at the app.
  4. Fix
    (to the test setup, not the app):
    Diff5 lines
    # check by hand in the visible browser against the dev servernpm run dev            # http://127.0.0.1:5173, live reload# test the production build in a headless browsernpm run build && npx vite preview --port 4174 --strictPort --host 127.0.0.1npx playwright test     # headless Chromium / WebKit / Firefox, never backgrounded
    This became the webServer block of playwright.config.ts (L4.03). The related real app bug, the splash never disappearing in headless and background tabs (its unmount waited for an exit animation those environments never completed), was fixed separately with a timer-driven fade and a 4 s cap (L2.05, incident 2).
  5. Lesson
    Before debugging the app, rule out the harness: is this the production build? Is the tab visible? Is anything reloading? A test environment should differ from a user's only in ways you chose.

Check yourself

Answer each one before you look. Multiple-choice questions mark your pick and let you try again; for open questions, answer aloud, then reveal and grade yourself honestly.

Q1
A test fails 3 times in --repeat-each=10 on WebKit and never on Chromium. Which kind is it most likely, and what do you look for first?
Did you have it?
Timing. Look for an assertion that reads state before a transition finishes, or input faster than an animation frame; open the trace of a failing repeat.
Q2
A test passes alone and fails in the full run. What do you try first?
Did you have it?
--workers=1 on the full run. If it passes, look for shared state: cleanup by pattern, shared users or data, a fixed port, a global setting.
Q3
Why does addInitScript set the theme instead of page.evaluate after goto?
Did you have it?
addInitScript runs before the page's own scripts, so the first paint uses the forced theme. Setting it after load would scan during a theme transition, or in the wrong theme.
Q4
The Lighthouse summary script crashes with UnicodeDecodeError: 'charmap' codec… on Windows. Fix?
Did you have it?
Open the report with encoding="utf-8"; Windows' default (cp1252) can't decode some characters in the report.
Q5
Predict: you run the UI suite against npm run dev instead of the build. Name two ways results could mislead you.
Did you have it?
Module reloads can reset state mid-test; dev-only warnings and React's StrictMode double effects change timing; files aren't hashed, so cache and HTTP checks don't reflect production; performance numbers are meaningless.
Q6
Why isn't "performance ≥ 90" an assertion in the suite?
Did you have it?
Lab scores vary with machine load, so it would flake. The suite tests the deterministic causes instead (image formats and sizes, cache headers), and Lighthouse is run by hand with a pinned version.
