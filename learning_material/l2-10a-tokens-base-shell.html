L2.10a

Styling I: tokens, themes, base and the shell

Recipe card70 min
You need
L1.02 (cascade, custom properties, media queries), L2.04 (theme.tsx, index.html meta tags), L2.05 (the Topbar and TabBar markup)
You'll produce
Lines 1–315 of src/styles.css: the design tokens for both themes, the base reset, the type helpers, the sticky top bar and the floating tab bar

In two sentences: Every colour, shadow, radius and size in the app is a named variable (a token) defined once at the top of styles.css, and dark mode is nothing more than a second set of values for the same names. Below the tokens sit a small reset that makes buttons, inputs and images behave the same in every browser, and the two pieces of chrome that frame every page: a frosted sticky top bar and a floating tab bar that respects the iPhone's notch and home indicator.

By the end, without notes, you can

  1. Write the token block from memory and explain the three-selector pattern that gives you "System / Light / Dark" with no JavaScript in the cascade.
  2. Explain what color-scheme, color-mix(), backdrop-filter, env(safe-area-inset-*) and 100dvh each do, and what breaks without each.
  3. Explain why overflow-x is set twice (hidden, then clip) on both html and body, and diagnose the iPhone sideways-scroll bug from its symptom.
  4. Compute the shell's bottom padding and the tab bar's width on a given phone.

2

The problem this solves

A naive stylesheet writes colours where they are used: background: #fffdf9 on cards, #17110e on text, and so on, hundreds of times. Then you add dark mode and must find and duplicate every one of those rules under a dark selector. You will miss some, and the app ends up with white boxes in dark mode.

The idea: name every design decision once (--surface, --ink, --red) and write every component against the names. A theme is then a list of values for those names. Switching theme changes about 25 values in one place, and the whole app follows.

3

Concepts

3.1 Custom properties are variables the cascade resolves

  1. Definition. A custom property is a CSS property whose name starts with --. You read it with var(--name).
  2. Why here. Two themes, one set of component rules.
  3. How it works. Custom properties inherit like color does. Define them on :root (the <html> element) and every element in the page sees them. var() is resolved per element at computed-value time, so if a higher-specificity rule redefines --ink on :root, every color: var(--ink) in the app changes at once. Analogy: the tokens are a price list pinned at the café door. The menu items say "one espresso", not "₹120"; reprint the price list and every menu item updates.
  4. Minimal example.
    HTML7 lines
    <style>  :root { --ink: black; }  :root.dark { --ink: white; background: black; }  p { color: var(--ink); }</style><p>Hello</p><button onclick="document.documentElement.classList.toggle('dark')">toggle</button>
  5. In the project. Every component uses tokens: .card { background: var(--surface); border: 1px solid var(--border); }.
  6. Without it. Every component needs a second dark rule; one forgotten rule gives a cream card on a black page.
  7. Try it. In DevTools on the live site, select <html> and change --red to blue. Buttons, the focus ring, text selection and the tab dot all turn blue.

3.2 Three selectors give three theme states

The app offers System, Light and Dark. "System" must follow the OS setting live, with no JavaScript in the styling path. The pattern is three rules:

Rule Matches when Effect
:root { … } Always Light values (the default)
@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) { … } } OS is dark and the user did not force Light Dark values
:root[data-theme="dark"] { … } The user forced Dark (any OS) Dark values

Why :not([data-theme="light"])? Without it, a user on a dark OS who picks "Light" would still get dark values from the media query. The :not() makes the media rule step aside when Light is forced.

Why is the dark block written twice? CSS has no way to say "media query OR attribute" in one selector. So the 23 dark declarations appear twice, once inside the media query and once under [data-theme="dark"]. They are byte-for-byte identical (checked with diff). Duplication is the price of a no-JS theme path; a build step or a mixin could remove it, but this project has no CSS preprocessor.

Specificity check. :root is 0-1-0. :root:not([data-theme="light"]) is 0-2-0 (:not() counts as its argument, an attribute selector). :root[data-theme="dark"] is 0-2-0. Both dark rules beat the light rule, so dark values win whenever a dark rule matches.

3.3 color-scheme tells the browser which built-in palette to use

color-scheme: light or dark changes the browser's own UI colours: scrollbars, the date-picker, form-control defaults and the default page background before your CSS paints. It is set inside each token block, so it flips with the theme. index.html also has <meta name="color-scheme" content="dark light">, which applies before any CSS loads and prevents a white flash on dark phones.

3.4 color-mix() makes translucent versions of tokens

color-mix(in srgb, var(--bg) 82%, transparent) gives "the background colour at 82% opacity". You cannot write rgba(var(--bg), 0.82) because --bg is a hex string, not three numbers. color-mix works on any colour value, so the top bar and tab bar stay correct in both themes. Supported in Safari 16.2+ and Chrome 111+; older browsers get the fallback in responsive.css (L2.10c).

3.5 backdrop-filter frosts what is behind an element

backdrop-filter: saturate(1.4) blur(14px) blurs and boosts the colour of whatever is behind the element (content scrolling under the top bar), not the element itself. It only shows if the element's own background is translucent, which is why it is paired with color-mix(… 82%, transparent). Safari needs the -webkit- prefix, so both lines are written.

3.6 Safe areas: viewport-fit=cover + env()

An iPhone screen has a notch or Dynamic Island at the top and a home indicator bar at the bottom. By default Safari letterboxes the page away from them. index.html opts out with viewport-fit=cover, so the page fills the whole screen, and in return the CSS must keep content clear of the hardware itself:

  • env(safe-area-inset-top): the notch height (about 47 px on an iPhone 13 in portrait).
  • env(safe-area-inset-bottom): the home-indicator height (34 px on Face-ID iPhones).
  • On phones without these, and on desktops, they are 0px.

3.7 100dvh: the viewport height that tracks the browser bar

On mobile, 100vh is the height with the address bar hidden, so a 100vh element is taller than the screen while the bar is showing. 100dvh (dynamic viewport height) follows the visible area as the bar slides. min-height: 100dvh makes short pages fill the screen exactly. Browsers older than Safari 15.4 ignore dvh; L2.10c adds vh fallbacks and L3.04 explains the three viewport units.

3.8 overflow-x: clip versus hidden

Both stop content from showing outside the box. The difference:

hidden clip
Content outside is painted? No No
Box becomes a scroll container? Yes (scrollable by code, by focus, and on iOS sometimes by finger) No
position: sticky inside still sticks to the viewport? No, it sticks to this box instead Yes
Browser support Everywhere Safari 16+, Chrome 90+, Firefox 81+

The app needs no sideways scrolling ever and a sticky top bar. clip gives both. Writing overflow-x: hidden; then overflow-x: clip; is a fallback: a browser that doesn't know clip drops the second line as invalid and keeps hidden. The deep dive on why WebKit needed it on html as well as body is in the bug journal below and in L3.03.

3.9 A variable font with a width axis

main.tsx imports @fontsource-variable/archivo/wdth.css: one font file containing every weight (100–900) and every width (62%–125%). font-stretch: 125% on .display selects the widest cut for headings, and 112% for the brand title. One file, many styles, one download.

The tokens fall into families. Learn them as families, not as 37 separate lines.

Family Tokens Role What breaks if you change it

Why four reds? One red cannot do every job. Measured against the light page #f6f0e6:

  • --red #d7262f is the brand red but only reaches 4.40:1, just under the 4.5:1 needed for small text. It is used for large or decorative things: icons, the focus ring, dots.
  • --red-ink #b51e27 is darker and is used whenever red is text.
  • --red-fill #c01f29 is the background for red buttons with white text.
  • --red-soft #fbe3e1 is a tint for backgrounds (the "you" leaderboard row).

The ratio formula and every measured pair are in L3.04.

The font stack reads left to right: the self-hosted variable font ("Archivo Variable"), a locally installed Archivo if one exists, then the OS UI fonts. system-ui and -apple-system (the older Safari name) give San Francisco on Apple devices, "Segoe UI" on Windows and Roboto on Android. If the web font fails, text still looks native rather than falling back to Times.

--ease-out: cubic-bezier(0.22, 1, 0.36, 1) is the "ease-out quint"-like curve: it starts fast and settles gently. Motion's transitions in the TSX use the same four numbers (ease: [0.22, 1, 0.36, 1], seen in the podium blocks), so CSS and JS animations feel like one system.

  • Only 23 tokens are redefined. Shape, size, font, motion, medals, --cream, --coffee, --mug and --mug-line don't change with theme, so they are not repeated. A token you forget here keeps its light value: that is the failure mode to watch for when you add a new colour token.
  • Dark is not "invert". The page is #0e0c0b (espresso, not pure black), surfaces step up in lightness (#171413 → #211d1b → #2c2725) because in the dark, raised things are lighter. Text is cream #f4eadb, not white, to avoid glare.

  • Shadows become pure black and stronger (0.4/0.35/0.7 alpha): brown shadows are invisible on a near-black page.
  • --primary inverts: the main button becomes cream with espresso text.

4.3 Dark tokens, the forced copy (lines 74–100)

CSS4 lines
:root[data-theme="dark"] {  color-scheme: dark;  /* …the same 23 declarations as lines 47–71, character for character… */}

The body of this rule is identical to the block above (verify it yourself: diff <(sed -n 47,71p src/styles.css | sed 's/^ //') <(sed -n 75,99p src/styles.css) prints nothing). It exists because a @media rule cannot be combined with an attribute selector using "or" (§3.2). If you change a dark colour, change it in both places. A test can't catch a mismatch between them yet; the axe scans in L4.07 force dark through data-theme, so only the forced copy is scanned.

4.4 The reset (lines 102–155)

CSS27 lines
/* ---------- base ---------- */*,*::before,*::after {  box-sizing: border-box;}html {  overscroll-behavior-x: none;  overflow-x: hidden;  overflow-x: clip;  -webkit-text-size-adjust: 100%;  -webkit-tap-highlight-color: transparent;}body {  margin: 0;  background: var(--bg);  background-image: radial-gradient(120% 60% at 50% -10%, var(--bg-glow), transparent 60%);  background-attachment: fixed;  color: var(--ink);  font: 400 16px/1.5 var(--font);  min-height: 100dvh;  overscroll-behavior: none;  /* slide animations must never make the page scroll sideways (clip keeps position: sticky working) */  overflow-x: hidden;  overflow-x: clip;  transition: background-color 0.3s, color 0.3s;}
  • L5box-sizing: border-box everywhere. width then includes padding and border. Without it, width: 100%; padding: 16px is 32 px wider than its parent: the classic cause of sideways scrolling. Pseudo-elements are included because they are boxes too.
  • L7html:
    • overscroll-behavior-x: none stops a horizontal overscroll from triggering the browser's back/forward gesture (that was the "a swipe triggered go back" bug in L2.08a; the card also sets touch-action, this is the page-level backstop).
    • overflow-x: hidden then clip: the fallback pair from §3.8, on the root, because of the WebKit bug below.
    • -webkit-text-size-adjust: 100% stops iOS from enlarging text when you rotate to landscape.
    • -webkit-tap-highlight-color: transparent removes the grey flash iOS and Android draw over tapped links and buttons; the app gives its own pressed states (:active, whileTap).
  • L14body:
    • margin: 0: browsers default to 8 px.
    • The background is a solid token plus a radial gradient centred 10% above the top edge (at 50% -10%), 120% wide and 60% tall, fading from the red glow to transparent by 60% of its radius. On screen that is a faint warm light at the top of the page.
    • background-attachment: fixed keeps the glow at the top of the screen while content scrolls. (iOS ignores fixed on backgrounds and treats it as scroll; the glow then scrolls away, which is harmless.)
    • font: 400 16px/1.5 var(--font): weight 400, size 16 px, line height 1.5, family from the token. 16 px matters on iOS: inputs with smaller text make Safari zoom in when focused.
    • overscroll-behavior: none stops the rubber-band bounce and pull-to-refresh, which feel wrong in an app-like UI and could reload the page mid-test.
    • overflow-x again, on body, for the slide animations (bug journal).
    • transition on background and text colour makes the theme switch a 0.3 s cross-fade instead of a flash.

4.5 Type helpers (lines 157–186)

CSS30 lines

4.7 The floating tab bar (lines 264–315)

CSS19 lines
/* ---------- tab bar ---------- */.tabbar {  position: fixed;  z-index: 30;  left: 50%;  transform: translateX(-50%);  bottom: calc(12px + env(safe-area-inset-bottom));  width: min(528px, calc(100% - 24px));  height: var(--tab-h);  display: grid;  grid-template-columns: repeat(5, 1fr);  padding: 6px;  border-radius: 24px;  background: color-mix(in srgb, var(--surface) 95%, transparent);  backdrop-filter: saturate(1.5) blur(18px);  -webkit-backdrop-filter: saturate(1.5) blur(18px);  border: 1px solid var(--border);  box-shadow: var(--shadow-2);}
  • L3position: fixed pins it to the screen, not the page.
  • Centring a fixed element: left: 50% puts its left edge at the middle; translateX(-50%) moves it back by half its own width. (Note: this transform is why responsive.css must reset it when the bar becomes a side rail.)
  • bottom: 12px + home indicator: it floats 12 px above the indicator on iPhones and 12 px above the edge elsewhere.
  • width: min(528px, 100% − 24px): 12 px margins on phones, capped at the 560 px shell minus 32 px on wide screens.

  • 95% surface plus blur: almost solid, so labels stay readable over busy content.
  • L18--shadow-2: the "floating" depth.

Bug journal

Incident ticket · #01

iPhones could scroll the page sideways during slide animations

Fixed
  1. Symptom
    The layout test passed on every Chromium and Firefox device but failed on the three WebKit iPhones:
    Text5 lines
    ✘ [iphone-se]  › ui.spec.ts › no page scrolls sideways and nothing hides under the tab bar    Expected: <= 1    Received:    4✘ [iphone-13]  › … Received: 14✘ [iphone-14-pro-max] › … Received: 14
  2. Diagnosis
    • Which page? A throwaway debug test visited each route and listed elements whose right edge passed the viewport:
      Text2 lines
      OVER /study {"over":0,"vw":390,"offenders":["button.chip right=412", …]}OVER /me    {"over":13,"vw":390,"offenders":["form.stack right=403", "h1.display right=403", …]}
      The Study chips are inside their own horizontally scrolling row, so they don't count (over is 0). The real offender is /me: the sign-in form was 13 px past the edge.
    • Why 13 px? The form enters with initial={{ x: 30 }} (it slides in from the right, L2.07a). Mid-animation its right edge is past the viewport, and WebKit counts the transformed box toward the page's scroll width. Chromium does too, but the test caught WebKit mid-slide because its animation ran slightly later.
    • Hypothesis 1: clip the body. Added overflow-x: hidden; overflow-x: clip to body. The test still failed (12–18 px).
    • Was the test right? scrollWidth − innerWidth is a proxy: it says content reaches past the edge, not that anyone can scroll there. The test was rewritten to measure the property itself, by trying to scroll: scrollTo(400, y), read scrollX, scroll back, at 0 ms and again at 600 ms. It still reported 8–14 px on iPhones, so the page really was scrollable. (The test change is its own story in L4.04.)
    • Hypothesis 2: the root. Putting the same pair on html makes the root's own value control the viewport. The test then passed on all 11 devices.
    • Re-checked for this series in a minimal page (a 100 px box translated 330 px right in a 390 px viewport), Chromium and WebKit behave identically: with no rule, or with hidden or clip on body only, the viewport scrolls by 40 px; with the rule on html and body, it scrolls by 0. The Chromium projects had passed in the session only because their slide animation had finished by the time they measured.
  3. Root cause
    A transformed child (translateX(30px)) extends the page's scrollable overflow even though it is only temporarily off-screen. overflow-x on body alone does not stop the viewport from scrolling; the rule has to be on the root element (html).
  4. Fix
    Diff5 lines
    html {  overscroll-behavior-x: none;  overflow-x: hidden;   /* fallback for browsers without clip */  overflow-x: clip;     /* the root controls the viewport: no sideways panning, and no scroll container */  -webkit-text-size-adjust: 100%;
    Diff8 lines
    body {  …  overscroll-behavior: none;  /* slide animations must never make the page scroll sideways (clip keeps position: sticky working) */  overflow-x: hidden;  overflow-x: clip;  transition: background-color 0.3s, color 0.3s;}
  5. Lesson
    Any x slide animation can make a phone page wobble sideways for a moment. Clip horizontal overflow at the root, use clip rather than hidden so position: sticky keeps working, and test "can the page actually scroll sideways?" by trying to scroll, during and after animations, on real WebKit.

Check yourself

Answer each one before you look. Multiple-choice questions mark your pick and let you try again; for open questions, answer aloud, then reveal and grade yourself honestly.

Q1
A user's phone is in dark mode and the app is on "Light". You add a new token --chip-bg only to the light :root block and to :root[data-theme="dark"]. What does this user see?
b. Forced Light means neither dark rule applies (§5.1 row 3), so the light value is used, which is correct for this user. The bug you introduced affects a different user: dark OS + "System" gets the light --chip-bg, because you forgot the media-query copy. (c) is wrong: the light block always defines it.
Q2
Someone "simplifies" body { overflow-x: hidden; overflow-x: clip } to just overflow-x: hidden. What can break?
Did you have it?
Because html now has its own non-visible overflow-x, the body's value is no longer propagated to the viewport; it applies to body itself. hidden makes body a scroll container, so the sticky top bar would stick inside body instead of the viewport, and code or focus could scroll body sideways. clip hides the overflow without creating a scroll container. Keep clip, with hidden only as the fallback line before it.
Q3
Why is .tab .tab-pill given z-index: -1 instead of placing it after the label in the DOM with a higher z-index on the label?
Did you have it?
The pill is rendered first in the JSX and must sit behind the icon and text. With z-index: -1 inside the tab bar's stacking context, it paints above the bar's background but below the tab's normal-flow content, with no z-index needed on the icon or label. Changing the order of the elements wouldn't help on its own: absolutely positioned elements paint above normal content unless you give them a negative z-index.
Q4
On an iPhone with a 34 px home indicator, you set --tab-h: 54px for landscape. What is the shell's bottom padding now?
Did you have it?
54 + 28 + 34 = 116 px (in landscape the bottom inset is usually 21 px, giving 103 px). Because the padding is calculated from the token, changing the token is enough; no other rule needs editing. That is the reason --tab-h is a token.
Q5
The top bar loses its blur on an old Android browser but stays readable. Why?
Did you have it?
Its background is 82% opaque --bg, so even without backdrop-filter the content underneath shows only faintly. (On browsers without color-mix, responsive.css supplies a solid fallback background.) Progressive enhancement: the blur is a bonus, readability doesn't depend on it.

Flashcards

See all 12 cards as a listfor a quick scan
  1. What three selectors implement System / Light / Dark?
    :root (light); @media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) }; :root[data-theme="dark"].
  2. Why does the dark block appear twice?
    CSS can't OR a media query with an attribute selector, so the same declarations go under both.
  3. What does color-scheme change?
    The browser's built-in colours: scrollbars, form controls, default background.
  4. Why color-mix(in srgb, var(--bg) 82%, transparent) and not rgba(var(--bg), .82)?
    --bg is a hex string; rgba() needs separate channels. color-mix accepts any colour.
  5. overflow-x: clip vs hidden?
    Both hide overflow; only hidden makes a scroll container, which breaks position: sticky inside and can still be scrolled by code or touch.
  6. Why write overflow-x twice in one rule?
    Fallback: browsers that don't know clip drop that line and keep hidden.
  7. What does viewport-fit=cover require from the CSS?
    Padding with env(safe-area-inset-*) so content clears the notch and home indicator.
  8. 100vh vs 100dvh on a phone?
    vh assumes the address bar is hidden (too tall while it shows); dvh follows the visible height.
  9. Shell bottom padding formula?
    --tab-h + 28 px + env(safe-area-inset-bottom).
  10. Why four red tokens?
    Brand red is 4.40:1 on cream (fails small text). Separate tokens for text (--red-ink), button fill (--red-fill) and tint (--red-soft).
  11. Why does the brand link need min-width: 0?
    Flex items won't shrink below their content by default; on 280 px screens the header would overflow.
  12. What does .tnum fix?
    Digits of different widths make timers and scores jiggle; tabular numerals are equal width.

Glossary

Backdrop filter
a filter applied to what is behind an element.
Box-sizing
whether width includes padding and border.
Cascade
the rules for choosing which declaration wins.
color-mix()
mixes two colours in a colour space; with transparent it makes a translucent colour.
color-scheme
tells the browser which built-in palette to use.
Custom property / token
a --name variable holding a design decision.
dvh
dynamic viewport height, follows the visible area.
Fallback declaration
an earlier line a browser keeps when it doesn't understand a later one.
Full bleed
a background that reaches the screen edges inside a padded container.
Safe area
the part of the screen not covered by the notch or home indicator.
Scroll container
a box whose overflow can be scrolled.
Specificity
a selector's weight (ids-classes-types).
Stacking context
a group of elements whose z-indexes are compared only with each other.
Sticky positioning
normal flow until a threshold, then fixed within its scroll container.
Tabular numerals
digits with equal widths.
Variable font
one font file with continuous axes such as weight and width.
